Building: targets, debug and release builds, and what a build does

`gd++ build` turns a package into GDExtension libraries, which Godot loads. This page explains builds in depth: what they do step by step, the targets you can build for, and the kinds of builds. For a short list of the command's options, see `gd++ man build`.

# A first build

```sh
gd++ build
```

This builds the package that contains the current directory, for this machine, in debug mode. The first build of a package takes a while, since it compiles godot-cpp too. Later builds only compile what changed.

```out
[•] Registering classes for res:// [my_game]...
[•] Building res:// [my_game] for linux.x86_64, debug, unoptimized, with docs.
[•] Generating .gdextension for res:// [my_game]...
```

The build writes the library (e.g. `libmy_game.linux.debug.x86_64.so`), `my_game.gdextension` and `my_game.gdextension.uid` into the package root. Godot loads them from there, so the classes show up in the editor right away.

# What a build does

For each package, `gd++`:

1. Checks that the package's bindings and spec are in the project's caches.
2. Syncs its build cache, `.gd++pkg`: copies the bindings and the spec into it, if they changed. If the package's settings changed since the last build (its id, bindings, spec, syntax, C++ standard, prefix or quit timeout), it first cleans the package, so the build starts from scratch. See `gd++ man build-cache`.
3. Writes the build script, `SConstruct`, into the build cache. It lists the package's C and C++ sources.
4. If the package has GD++ files: finds out what godot-cpp declares, and transpiles each GD++ file into C++. The first time, this generates godot-cpp's bindings from the spec and scans their headers, and the result is cached. Transpiling stops at the first error in any GD++ file. See `gd++ man lang`.
5. Writes `__register_types__.cpp`, the code that registers the package's classes with Godot when the library loads, including the package's class of tasks, if a GD++ class uses `Async`. See `gd++ man async`.
6. Runs SCons for each target. It compiles godot-cpp, the generated C++ and your C++ sources, and links the library into the package root.
7. Writes the `.gdextension` file and its `.uid` file.

Each step only rewrites the files whose contents change, so SCons and the Godot editor don't see needless changes. The one exception is the `.gdextension` file, which is rewritten on every build: its new modification time makes the editor reload the library.

# Targets

A target is a platform and a CPU architecture, written `PLATFORM.ARCH`, e.g. `linux.x86_64`. By default, `gd++` builds for the machine it runs on. To build for other targets, e.g. to cross-compile for Windows on Linux:

```sh
gd++ build --for windows.x86_64
gd++ build --for l.x64 w.x64 m.a64        # three targets in one run
gd++ build -w                             # Windows, this machine's architecture
gd++ build --platform macos --arch arm64
```

Platforms, with their short names:

```
windows   win, w
linux     lin, l
macos     mac, m
```

Architectures, with their short names:

```
x86_32    x32
x86_64    x64
arm64     a64
```

`macos.x86_32` doesn't exist, since godot-cpp doesn't support it. Cross-compiling needs a compiler for the target: `gd++ install` sets up MinGW-w64 on Linux and macOS, to build for Windows. Building for macOS generally needs a Mac.

`--for` takes any number of targets, and can't be used with `-w`, `--platform` or `--arch`. The build compiles the targets one after another. Steps 1 to 5 above happen only once, before the first target.

# Debug and release builds

A debug build, the default, is for development:

- Built with godot-cpp's `template_debug` target, as a dev build with debug symbols, so you can step through your code in a debugger.
- Unoptimized by default, so it compiles fast and is easy to debug, but runs slower, sometimes even slower than GDScript. See `gd++ man performance`.
- Hot reload: rebuild while the editor runs, and the editor reloads the library when its window gets focus, without a restart.
- Loaded by the editor, and by games run from the editor or exported in debug mode.
- Includes the documentation of GD++ classes, for the editor's help. See `gd++ man docs`.

A release build, with `--ship`, is for the game you ship:

- Built with godot-cpp's `template_release` target, with link-time optimization.
- Optimized for speed by default.
- Loaded by games exported in release mode.
- Has no documentation by default, since only the editor shows it.

Debug and release libraries have different names, e.g. `libmy_game.linux.debug.x86_64.so` and `libmy_game.linux.release.x86_64.so`, so both can exist side by side. The `.gdextension` file lists both, for every target, and Godot picks the right one.

```sh
gd++ build --ship                        # release, optimized for speed
gd++ build --ship --small                # release, optimized for size
gd++ build --opt                         # debug, but optimized for speed
```

Optimization can be chosen independently of `--ship`:

```
--opt     optimize for speed (default with --ship)
--small   optimize for binary size
--noopt   don't optimize (default without --ship)
```

So can documentation:

```
--doc     compile the documentation of GD++ classes into the library (default without --ship)
--nodoc   don't (default with --ship)
```

The task name of each build says what it builds, e.g. "Building res:// [my_game] for windows.x86_64, release, optimized, no docs...", and whether tracing or profiling is on. On a terminal, the values that differ from the defaults are highlighted.

# Editor and runtime code

Like GDScript, GD++ runs the code of a class in the editor only if the class has `@tool`:

- A class without `@tool` is a runtime class. In the editor, Godot shows placeholders for its objects: they keep their property values, but run none of the class's code.
- A class with `@game_only` is a runtime class too. In debug builds, its functions also return right away when something calls them in the editor, e.g. a `@tool` class.
- A class with `@tool` runs in the editor too, e.g. to draw gizmos or react to property changes.

C++ classes work the same way, with `tool = true` in `gd++pkg.toml` in place of `@tool`. Games run from the editor and exported games run all code. See `gd++ man classes` and `gd++ man cpp-classes`.

# Tracing and profiling builds

The `@trace` and `@profile` annotations in GD++ code generate nothing, unless a build turns on their groups:

```sh
gd++ build --trace combat                        # the @trace annotations of the group combat
gd++ build --trace Player Enemy                  # of the classes Player and Enemy
gd++ build --profile all                         # all @profile annotations
gd++ build --opt --profile all --print           # optimized, with a table of timings every 10 seconds
gd++ build                                       # back to none
```

`--trace GROUP...` and `--profile GROUP...` take group names, or `all`. Every annotation is in the group named after its class, and in the groups that its arguments name. With `--profile`, the editor's Debugger > Monitors tab shows the time per frame of each profiled function. `--print` also prints a table of the timings every 10 seconds, `--period SECONDS` changes how often, and `--fps FPS` sets the frame rate that the table's budget column assumes, 60 by default.

These options work in debug and release builds, and with any other option. Switching them only recompiles the files whose code changes, and hot reload picks up the result while the editor runs. `gd++ trans` takes the same options, to show the code they generate. See `gd++ man debugging`.

# Parallel jobs

```sh
gd++ build -j 8
```

Runs 8 compile jobs at once. By default, SCons runs one job per CPU core, minus one.

# Building every package

```sh
gd++ build --proj
```

Builds every package in the project, one after another, in the order of their paths. It can't be used with a path. If the project has no packages, it warns "Nothing to build.".

# Clean builds

```sh
gd++ build --clean
```

Deletes the package's build cache and libraries first, like `gd++ clean --bin`, so the build starts from scratch. This helps when something in the build cache went wrong. A clean build compiles godot-cpp again, so it is slow.

# Errors

If a GD++ file has an error, the build stops before compiling anything, and shows the error in the GD++ file. See `gd++ man errors`.

If the C++ compiler fails, the build shows its whole output. Errors in the C++ code of GD++ files are reported at their lines in the GD++ files, thanks to `#line` directives in the generated code. Errors in generated code are reported in the generated files, in the build cache's `gdpp` directory. See `gd++ man generated`.

If SCons isn't installed, builds fail with "Failed to find SCons, see https://scons.org to install it: ...". Run `gd++ install` to fix this.

# SCons

`gd++` compiles with SCons, godot-cpp's build system. You never need to run it yourself: `gd++` writes the build script, and runs it in the build cache. The build script is rewritten on every build, so don't edit it. For a custom build step, write a separate script that runs `gd++ build`.
