Externs: using classes of other packages, GDExtensions and scripts at runtime

Each package is compiled on its own, so its code can't use the classes of another package: the C++ compiler never sees them. An extern solves this at runtime: it declares a class that lives somewhere else, and GD++ lets your code use it like any other class, calling its members by name.

# Declaring an extern

```gd++
extern Terrain {
  extends Node3D
  func height_at(x: float, z: float) -> float
  @const func size() -> int
  @deferred func rebuild() -> void
  var seed: int
  signal changed
}
```

An extern lists what your code needs of the class: its base class and some of its functions, variables and signals, with their types, like the class declares them. The class itself can be anything that Godot knows by that name at runtime:

- a GD++ class of another package,
- a class of any other GDExtension, written with GD++ or not,
- a GDScript class with a class_name, or a class of any other scripting language.

The extern's name must be the name of that class. It must not be the name of a class the package already knows: Godot's own classes, and the package's own classes, can be used directly.

Externs can be file-level, with extern_name, or inline, like classes. See `gd++ man files`.

# Base class

extends names the extern's base class: a Godot class, a GD++ class of the package, or another extern. Without extends, it's RefCounted. The base decides:

- what your code can do with the object without calling by name: everything the base class can,
- whether the extern is used through a pointer, gdpp::ExtPtr<Terrain>, if the base isn't refcounted, or through a reference, gdpp::ExtRef<Terrain>, if it is,
- how Godot sees it: as an object of the base class.

Use the class's real base class, or any class above it, e.g. Node3D or Node, as long as it's true of the object.

An extern that extends another extern has that extern's members too, and converts to it, e.g. to pass a gdpp::ExtPtr<Car> where a gdpp::ExtPtr<Vehicle> is expected:

```gd++
extern Vehicle {
  extends Node3D
  func speed() -> float
}

extern Car {
  extends Vehicle
  func honk() -> void
}
```

The chain of bases must end with a Godot class or a GD++ class of the package, e.g. Node3D here, which decides the three points above.

# Members

Externs can only declare:

func
  Functions, without a body and without default values. They can have @const, and two attributes only externs have: @deferred, and @rpc without arguments. The return type must match what the class returns.

var
  Variables, without an initial value or a property body, and without annotations. They're read with get_NAME() and written with set_NAME(value).

signal
  Signals, to send them on the object, with emit.

Everything else, e.g. ctor, dtor, enums, decl and impl blocks, is an error: "Externs can't contain ...". You only need to declare the members that your code uses.

# Using an extern

An extern is a type, like a class:

```gd++
class_name Car
extends Node3D

@export var terrain: Terrain

@override
func _physics_process(delta: float) -> void {
  Vector3 pos = get_position();
  pos.y = terrain->height_at(pos.x, pos.z);
  set_position(pos);
}

func regenerate(seed: int) -> void {
  terrain->set_seed(seed);
  terrain->rebuild();
  emit terrain->changed();
}
```

- Functions: `terrain->height_at(x, z)` calls height_at on the object, by name, and converts the result to the declared return type.
- Variables: `terrain->get_seed()` and `terrain->set_seed(5)` get and set the property by name.
- Signals: `emit terrain->changed()` emits the signal on the object.
- The base class: `terrain.base()` returns the object as its base class, Node3D*, to use anything else, e.g. `add_child(terrain.base())` or `terrain.base()->get_position()`.

In C++, an ExtPtr<T>:

- starts null, and can be set from a pointer to the base class or nullptr: `terrain = get_node<Node3D>("Terrain");`,
- tests as a bool: `if (terrain) { ... }`,
- compares with == to another ExtPtr<T>,
- converts to a Variant, e.g. to pass it to Godot.

An ExtRef<T> is the same, but holds a reference, which keeps the object alive, and base() returns a Ref<Base>. gdpp::Ext<T> is whichever of the two fits T.

Converting a base class pointer to an extern doesn't check the object's class: if it's not really a Terrain, calls fail at runtime, with Godot's errors about missing methods. For exported variables, the editor checks it for you, see below.

# Exported externs

```gd++
@export var terrain: Terrain
```

In Godot, the variable's type is the base class, Node3D, but the editor only accepts objects whose class is named Terrain, if the base is a Node or a Resource: the node picker only offers Terrain nodes, and the resource picker only Terrain resources. That's the usual way to connect objects of different packages: in the editor, not in code.

# Creating and deleting objects

```cpp
gdpp::Ext<Terrain> terrain = memnew_ext(Terrain);
add_child(terrain.base());

memdelete_ext(some_terrain);      // only for ExtPtr, like memdelete
```

memnew_ext(T) creates an object of the class named like the extern: a class that Godot's ClassDB knows, e.g. of a GDExtension, or else a global script class, i.e. a script with a class_name, which it loads and calls new() on. If there's no such class, it prints an error and returns null. memdelete_ext deletes an ExtPtr's object, like memdelete; refcounted objects delete themselves when their last ExtRef goes away.

# @deferred

```gd++
extern Terrain {
  extends Node3D
  @deferred func rebuild() -> void
}
```

Calls to a @deferred function go through call_deferred instead of call: they run later, at the end of the frame. So @deferred functions must return void. @deferred only exists in externs.

# @rpc

```gd++
extern Lobby {
  extends Node
  @rpc func join(name: String) -> void
}

rpc_id(1) lobby->join("Me");
```

An @rpc function of an extern can be called over the network with rpc and rpc_id, like one of your own classes. It takes no arguments, since the class that defines the function configures it. The extern must extend Node. See `gd++ man rpc`.

# Speed

Every call on an extern goes through Godot's call by name: the arguments are packed into Variants, the method is looked up by name, and the result is unpacked. That's much slower than a C++ call, though the names are interned only once. Use externs where you need them, e.g. to connect packages, not in hot loops.

# How it works

For each extern, GD++ generates a header, e.g. Terrain.h, with a small wrapper class in namespace godot. It holds a pointer to the object, and has a method for each declared member, which calls the object's call, call_deferred, get, set or emit_signal with the member's name. ExtPtr<T> and ExtRef<T> hold the object, and their operator-> returns such a wrapper. Externs aren't registered with Godot: they're only names for classes that are registered elsewhere. See `gd++ man runtime` and `gd++ man generated`.

# Example

Two packages: res://world builds the terrain, and res://vehicles uses it.

res://world/terrain.gd++:

```gd++
class_name Terrain
extends Node3D

signal changed

func height_at(x: float, z: float) -> float {
  return Math::sin(x) * Math::cos(z);
}
```

res://vehicles/terrain.gd++:

```gd++
extern_name Terrain
extends Node3D

func height_at(x: float, z: float) -> float
signal changed
```

res://vehicles/car.gd++:

```gd++
class_name Car
extends Node3D

@export var terrain: Terrain

@override
func _process(delta: float) -> void {
  if (!terrain) {
    return;
  }
  Vector3 pos = get_position();
  pos.y = terrain->height_at(pos.x, pos.z);
  set_position(pos);
}
```
