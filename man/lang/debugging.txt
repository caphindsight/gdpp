Debugging: tracing calls and changes with @trace, and timing code with @profile

Two annotations help you see what your code does while the game runs:

- @trace prints what happens: the calls of functions, with their arguments, results and times, the changes of variables, the signals objects emit, and the creation and destruction of objects.
- @profile measures how long functions take, and shows it live in the editor's monitors, and if you want, in a table printed every few seconds.

Both are off unless a build turns them on, and then they generate no code at all. So you can leave them in your code for good, like switched-off log statements, and turn on the ones you need, with a flag, when you need them.

# A first example

```gd++
class_name Player
extends CharacterBody3D

@trace
var health: int = 100

@trace
@profile
func take_damage(amount: int) -> bool {
  health -= amount;
  return health <= 0;
}
```

Build with tracing on, for the class Player:

```sh
gd++ build --trace Player
```

Run the game, and the Output panel shows every call of take_damage, and every change of health:

```out
[f812] ▶ Player "Hero".take_damage(amount: 5)
[f812]   Player "Hero".health: 100 → 95  (in take_damage)
[f812] ◀ Player "Hero".take_damage → false  12.4 µs
```

Build without the flag, and all of it is gone again, at no cost:

```sh
gd++ build
```

# Groups: choosing what to turn on

Every @trace and @profile annotation belongs to one or more groups:

- the group named after its class, always, e.g. Player,
- the groups that its arguments name: @trace("combat") is in the groups Player and combat, and @trace("combat", "ai") in Player, combat and ai.

Builds turn groups on with two flags, each followed by any number of group names:

```sh
gd++ build --trace combat                  # @trace annotations in the group combat
gd++ build --trace combat ai               # in combat or ai
gd++ build --trace Player                  # all @trace annotations in the class Player
gd++ build --trace all                     # all @trace annotations
gd++ build --profile all                   # all @profile annotations
gd++ build --trace ai --profile all        # both at once
```

`all` turns on every annotation of its kind. The flags are independent: --trace only turns on @trace annotations, and --profile only @profile ones. An annotation whose groups are all off generates nothing.

The arguments of the annotations are names in double quotes, e.g. @trace("combat"). Without arguments, an annotation is only in its class's group. Group names are made of letters, digits and underscores, and don't start with a digit.

A member is on if its own annotation is on, or its class's annotation is. With this class:

```gd++
@profile("ai")
class_name Enemy
extends CharacterBody3D

@profile("physics")
func steer(delta: float) -> void { ... }

func think() -> void { ... }
```

`--profile ai` profiles steer and think, through the class's annotation, and `--profile physics` only steer. `--profile Enemy` and `--profile all` profile both.

The build's task name says when tracing or profiling is on, e.g. "Building res://game for linux.x86_64, debug, unoptimized, with docs, trace combat ai, profiling...". Changing the flags only recompiles the files whose generated code changes, and with hot reload, the editor picks up the new library without a restart. See `gd++ man building`.

To see the code that the annotations generate, pass the same flags to `gd++ trans`:

```sh
gd++ trans player.gd++ --trace all --profile all
```

A group name that no annotation uses turns nothing on, without an error. If a build prints nothing, check the group names, e.g. with `gd++ trans`.

# @trace on functions

@trace on a function prints two lines per call: one when it starts, with its arguments, and one when it returns, with its result, if it has one, and how long it took.

```gd++
@trace
func pick_up(item: Item, count: int = 1) -> bool {
  ...
}
```

```out
[f1204] ▶ Player "Hero".pick_up(item: Item#28347, count: 1)
[f1204] ◀ Player "Hero".pick_up → true  3.1 µs
```

The parts of a line:

[f1204]
  The frame in which the line was printed, from Engine.get_process_frames(). Lines of the same frame have the same number, so you can see what happens together. Off the main thread, the thread's id follows, e.g. [f1204] [thread 13985]. These parts are gray.

▶ and ◀
  The start and the end of a call.

Player "Hero".pick_up
  The object and the function. A node is named by its class and its name, e.g. Player "Hero". Other objects, e.g. resources, by their class and instance id, e.g. Item#28347. The class is the object's own, so a function of Player, called on an object of its subclass Boss, shows Boss "Hero". Static functions show only the class, e.g. Player.create.

(item: Item#28347, count: 1)
  The arguments, by name. Strings, StringNames and NodePaths are quoted, objects are named like above, enums show as numbers, and other values in their text form, e.g. (1.0, 2.0, 3.0) for a Vector3. Values longer than 60 characters are cut, with "…".

→ true
  The result, like an argument. Functions that return void have none.

3.1 µs
  How long the call took: in µs below one millisecond, in ms above. It includes the functions it called, but not the time spent printing and measuring. See "How accurate the times are", below.

Calls made during a traced call are indented, so nested calls read as a tree:

```out
[f1204] ▶ Player "Hero".take_damage(amount: 30)
[f1204]   ▶ Player "Hero".play_hurt_animation()
[f1204]   ◀ Player "Hero".play_hurt_animation  48.0 µs
[f1204]   ▶ Player "Hero".die()
[f1204]   ◀ Player "Hero".die  210.5 µs
[f1204] ◀ Player "Hero".take_damage → true  301.2 µs
```

Every call of the function is traced, however it's called: from your C++ code, from GDScript, from a signal, or with call_deferred. Some functions have details:

- A @deferred or @thread_safe function is traced when its body runs, later, not when the call is queued. It shows with its own name.
- A @virtual function is traced even when a script overrides it, and its time includes the script's code.
- A function that returns early, with return, prints its end line all the same.

# @trace on variables

@trace on a variable prints each change of its value, with the function of its class that made it:

```gd++
@trace
var health: int = 100

@trace
var inventory: Array[Item]
```

```out
[f1204]   Player "Hero".health: 100 → 70  (in take_damage)
[f1377]   Player "Hero".inventory: [] → [<Item#28347>]  (in pick_up)
```

Every function of the class that could change the variable compares its value before and after the call, and prints the changes just before the call's end line. That makes it the fastest way to answer "who changes this value?": you don't need to trace any function, and only changes print.

- The functions that check are the class's non-static, non-const functions, including the setters of its variables, @override functions like _process, and the bodies of @deferred functions. So a change from GDScript, e.g. `player.health = 5`, shows as made in set_health.
- A change made in a function that another function of the same object called shows once, in the innermost function.
- Arrays and dictionaries are copied deeply and compared item by item, so a change of an item inside them shows too. Objects are compared by identity: which object the variable points to, not what's in it.
- A property with a get block is read through its getter.

Some changes show late, or not at all:

- A change made by code outside the class's own functions, e.g. by another class that writes the field directly in C++, or by a subclass, shows at the next call of one of the class's functions, as made there.
- Initial values, set in the constructor, don't show.

Checking takes time in every checking function, most of all for big arrays and dictionaries, which are copied twice per call. This time doesn't count in trace and profile times, but it slows the game down. Trace big collections only when you need to.

# @trace on signals

@trace on a signal prints each emission, with its arguments, before the handlers run:

```gd++
@trace
signal died(cause: DeathCause)
```

```out
[f1204]   ⚡ Player "Hero" emits died(cause: 2)
```

Only emissions with emit show, since GD++ traces them in the signal's emit function. Code that calls emit_signal("died") by name, and GDScript that emits the signal, bypass it. See `gd++ man signals`.

# @trace on classes

@trace on a class works like @trace on all its functions, variables and signals, and also prints the creation and destruction of its objects:

```gd++
@trace("loot")
class_name Chest
extends Node3D
```

```out
[f3] + Chest#28347 created
[f3] ▶ Chest "Chest2"._ready()
[f3] ◀ Chest "Chest2"._ready  8.2 µs
[f901] ▶ Chest "Chest2".open(by: Player "Hero")
[f901]   Chest "Chest2".is_open: false → true  (in open)
[f901]   ⚡ Chest "Chest2" emits opened(by: Player "Hero")
[f901] ◀ Chest "Chest2".open  15.7 µs
[f902] - Chest#28347 freed
```

Creation and destruction lines name the object by its instance id: a node has no name yet when it's created, and can't be asked for it any more while it's destroyed. Match them to the other lines with the id, or with the frame numbers. A "created" line without a "freed" line, once the object should be gone, points to a leak.

A class's @trace leaves out _process and _physics_process, since they run every frame and would bury everything else. They still check the traced variables. To trace them anyway, put @trace on them too:

```gd++
@trace("frame")
@override
func _physics_process(delta: float) -> void { ... }
```

# @profile on functions, variables and classes

@profile measures how long every call takes, and prints nothing per call:

- On a function, it times the function. Like with @trace, a @deferred function is timed when its body runs, and a @virtual one includes a script's override.
- On a variable, it times the variable's getter and setter, e.g. Player.get_ammo and Player.set_ammo. That's useful for properties whose get or set block does real work. A simple variable's getter and setter only copy a value, and your C++ code uses the field directly, not them.
- On a class, it times all its functions, and the getters and setters of its properties with get and set blocks.

The timings show in the editor's monitors, and with --profile-print, in a table printed every few seconds.

# Profile monitors

While the game runs from the editor, open the Debugger panel, then its Monitors tab. Each profiled function has a graph there, in the GD++ category, e.g. "Player.take_damage (ms)": the milliseconds per frame that the function took, averaged since the graph's last point. A function shows up in the list once it has run for the first time.

The graphs show when a cost changes, e.g. when a fight starts, and how the functions compare to each other, and to Godot's own monitors, like the frame time.

# Profile tables

With `--profile-print`, the game also prints a table of the profiled functions every 10 seconds, or with `--profile-period SECONDS`, every SECONDS seconds:

```sh
gd++ build --profile all --profile-print
gd++ build --profile all --profile-print --profile-period 5
```

```out
━━ GD++ profile · last 10.0 s · 600 frames · debug, unoptimized ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Function                     Thread       Calls    Total ms     Self ms      Avg µs      Max µs    ms/frame   Budget (60 FPS)
──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
Enemy._physics_process         main       24000      950.40      412.77       39.60     1822.11       1.584              9.5%
Enemy.find_path                main         310      537.63      537.63     1734.29     9807.40       0.896              5.4%

Player.take_damage         80% main           4        0.05        0.05       12.40       31.02       0.000              0.0%
```

The title line says how much time the table covers, in seconds of real time and in frames, and what kind of build measured it. Each table covers only the time since the table before it, so it shows what the game does now, not averages since the start. It lists the functions that ran in that time, the slowest first, by total time. If none ran, it prints nothing.

The columns:

Thread
  Where the function ran, counting all its calls since the game started: "main" if always on the main thread, "subthread" if never, or else the share of its calls on the main thread, e.g. "80% main".

Calls
  How often the function ran.

Total ms
  The time it took in all, including the time of the functions it called.

Self ms
  Total minus the time of the profiled functions it called. Functions without @profile count as its own time.

Avg µs
  The average time of a call: Total divided by Calls.

Max µs
  The longest call.

ms/frame
  Total divided by the frames: the time it takes per frame, on average.

Budget (60 FPS)
  ms/frame as a share of a frame's time at 60 frames per second, 16.7 ms. It's green below 10%, yellow up to 50%, and red above. `--profile-fps FPS` sets another frame rate, e.g. `--profile-fps 144` for 6.9 ms frames, and the column's name says which.

A recursive call's time is already in the time of the call it's inside, so Total, Max, ms/frame and Budget only count the outermost call. Calls and Self count every call, so for recursive functions, Avg is lower than the time of an outermost call.

The table is one message, after a blank line, in a monospace font, so it lines up in the editor's Output panel, and other output can't land inside it. The first table prints one period after the first profiled function ran.

--profile-print needs --profile, and --profile-period and --profile-fps need --profile-print.

# How accurate the times are

The times that @trace prints and @profile measures are the real times of the calls, measured with the system's steady clock, at nanosecond resolution. GD++ takes care that measuring doesn't count as your code's time:

- Timing a call costs a few tens of nanoseconds. GD++ measures that cost once, when the first profiled function runs, and subtracts it from every call, and from the calls around it. So even functions that take less than a microsecond show their own time.
- The time spent printing traces and checking variables doesn't count, neither in trace times nor in profile times. So --trace and --profile can be on together, even on the same functions.

What GD++ can't take out:

- Optimization. A debug build is unoptimized by default, and unoptimized C++ is often several times slower. The table's title line then says "unoptimized". Compare functions with each other in such a build, but for times close to the shipped game's, build with `--opt`, which keeps the debug build's other features, or with `--ship`.
- The game around your code. Tracing slows the whole game down, since printing takes time: frames take longer, and fewer of them run. Profile without --trace to see the game at its real speed.
- The machine. Other programs, power saving and cold caches all change times. Look at several tables, not one.

# Recipes

Who changes a value? Trace the variable, and build with its class's group:

```gd++
@trace
var health: int = 100
```

```sh
gd++ build --trace Player
```

Each change prints with the function that made it, and nothing else prints, since no function is traced.

Is a function called at all, and with what? Trace it:

```gd++
@trace
func _on_body_entered(body: Node3D) -> void { ... }
```

In what order do things happen? Trace the functions involved, and read the frames and the indentation: calls in the same frame have the same [f...] number, and calls made inside other calls are indented under them. Traced @deferred functions show when their bodies run, at the end of the frame.

Which signal handlers run? Trace the signal and its handlers:

```gd++
@trace
signal died(cause: DeathCause)
```

The handlers' calls print right under the emission.

Do objects leak? Trace the class, e.g. @trace on class Bullet, and build with `--trace Bullet`. In a long session, every id that has a "created" line should get a "freed" line.

What eats my frame? Profile the systems, in an optimized build:

```gd++
@profile("perf")
class_name Enemy
extends CharacterBody3D
```

```sh
gd++ build --opt --profile perf --profile-print --profile-period 5
```

Play the slow part of the game, and read the Budget column first: the share of the frame each function takes. Then:

- Total much bigger than Self: the time goes into the profiled functions it calls. Look at their rows.
- Self close to Total, although the function does little itself: the time goes into functions that aren't profiled, e.g. engine calls or helpers. Profile the helpers too.
- Max much bigger than Avg: the function is usually fast, but sometimes very slow, which shows as stutter. Trace it, and its variables, to see what differs in the slow calls.
- Many calls of a cheap function: calling it less may help more than making it faster.

Does my code run on threads? The Thread column says where each profiled function ran, and trace lines of calls off the main thread show the thread's id.

# Best practices

- Leave the annotations in your code. Off, they cost nothing, and the next time something breaks, the tracing is already in place. Remove the ones that turn out to be noise.
- Name groups after the game's features and systems, e.g. combat, ai, save, ui or net, not after a bug. Then `--trace combat` means the same thing a month later, to everyone on the team.
- Use a class's own group for a quick look, e.g. `--trace Player`, and named groups for features that span classes.
- Trace narrowly, profile broadly. Traces of many functions are hard to read, while profiling many functions costs little, and the table sorts them for you. Start with `--profile all`, then trace the few functions that matter.
- Keep functions that run every frame out of your usual trace groups, e.g. in a group of their own, like @trace("frame"), and turn it on only when needed. At 60 frames per second, one traced _process prints 120 lines per second.
- To find who changes a value, trace the variable, not the functions.
- Profile optimized code, with --opt, when absolute times matter, and profile without --trace when frame rates matter.
- Look at more than one table. The first ones include loading and warming up.
- Turn everything off with a plain `gd++ build` when you're done, before you measure the game's real speed, and before you ship.
- When output looks wrong or is missing, run `gd++ trans FILE` with the same flags, to see what the annotations generate.

# Limits

- @trace and @profile work on classes, and on their functions, variables and signals. Externs and their members can't have them, and neither can C++ code in decl and impl blocks.
- @trace on a function traces that function, not the functions that override it in subclasses: to trace an override, put @trace on the override.
- A @game_only class returns right away in the editor, before any tracing or profiling, and other classes without @tool don't run in the editor at all. So only @tool classes trace and profile in the editor, e.g. while you edit a scene.
- Both work in debug and release builds, but the monitors only show while the editor's debugger is connected to the game.
- Trace lines of different threads can mix. Each line is printed whole.

# What GD++ generates

The annotations add a few lines at the start of each function they apply to. With --trace and --profile on, take_damage from the first example becomes:

```cpp
bool Player::take_damage(int64_t amount) {
	static gdpp::ProfileStats _gdpp_stats("Player.take_damage");
	gdpp::Profile _gdpp_profile(_gdpp_stats);
	gdpp::Trace _gdpp_trace("Player", this, "take_damage", "amount", amount);
	gdpp::Watch _gdpp_watch(this, "take_damage", "health", [&] { return health; });
	return _gdpp_trace.ret([&]() -> bool {
		// Your body, unchanged.
	}());
}
```

- gdpp::ProfileStats holds the function's timings, and gdpp::Profile times the call. With --profile-print, the table's period follows the name, and with --profile-fps, the frame rate, e.g. `_gdpp_stats("Player.take_damage", 10, 144)`.
- gdpp::Trace prints the start and end lines. A traced function that returns a value runs its body as a lambda, so the trace gets the result of every return.
- gdpp::Watch checks the class's traced variables.
- A traced signal's emit function calls gdpp::trace_emit, and the constructor and destructor of a traced class call gdpp::trace_lifetime.

A source file that uses any of these defines GDPP_DEBUGGING before its includes, which makes the runtime header include what they need. See `gd++ man runtime` and `gd++ man generated`.
