Generated code: the C++ that GD++ writes, file by file

GD++ turns each GD++ file into ordinary C++, which you can read, debug and include. This page describes that C++ in detail: which files there are, what's in them, and the names of the helpers GD++ adds. To see the C++ of a file, run `gd++ trans FILE`. In a build, it's in the package's build cache, in `.gd++pkg/gdpp`. See `gd++ man trans` and `gd++ man build-cache`.

# Files

Each declaration of a GD++ file gets its own files, named after it:

- a class NAME: `NAME.h`, its definition, and `NAME.cpp`, its methods and bindings,
- an extern NAME: `NAME.h`, its wrapper class,
- an enum NAME: `NAME.h`, its enum class.

Plus, for the whole package:

- `gd++/syntax_0.hpp`, the runtime header. See `gd++ man runtime`.
- `doc_classes/NAME.xml` per class, its documentation, in debug builds, and one for each class that GD++ adds, e.g. the class of tasks. See `gd++ man docs`.

Every generated file starts with "// Generated by GD++ from FILE, do not edit.". Headers use `#pragma once`, and everything is in namespace `godot`, except `@global` blocks.

# An example

`counter.gd++`:

```gd++
class_name Counter
extends Node

signal changed(value: int)

var count: int = 1

func add(amount: int = 1) -> void {
  count += amount;
  emit changed(count);
}
```

`Counter.h`:

```cpp
// Generated by GD++ from counter.gd++, do not edit.

#pragma once

#include <gd++/syntax_0.hpp>
#include <godot_cpp/classes/node.hpp>

namespace godot {

#define This Counter
class Counter : public Node {
  GDCLASS(Counter, Node)

public:
  int64_t count{};

public:
  Counter();
  void add(int64_t amount = _gdpp_default_add_amount());
  int64_t get_count() const;
  void set_count(int64_t p_value);
  gdpp::Emitted changed(int64_t value);

protected:
  static void _bind_methods();

private:
  static int64_t _gdpp_default_add_amount();
};
#undef This

} // namespace godot
```

# The class header

In order:

1. The `#include` lines: the runtime header, then the headers of the names the header uses, sorted. See `gd++ man includes`.
2. `@global decl` blocks.
3. In namespace `godot`: forward declarations of the package's GD++ classes, externs and enums that the header uses, e.g. `class Enemy;` or `enum class Suit : int64_t;`.
4. The enum stand-ins of the class, one per enum it exposes: `enum _gdpp_Counter_Suit : int64_t {};` and `GDPP_ENUM_TAG`, or `GDPP_BITFIELD_TAG` for a bitfield. See `gd++ man enums`.
5. The class, between `#define This NAME` and `#undef This`:
   - `GDCLASS(NAME, BASE)`,
   - each `decl` block, after `private:`,
   - `public:` the fields of simple variables, value-initialized with `{}`,
   - `private:` the `decl` blocks of properties,
   - `public:` integer constants as `static constexpr int64_t`, the constructor and destructor if any, `GDVIRTUAL` declarations of `@virtual` functions, the functions, RPC helpers, getters and setters, and the emit functions of signals,
   - `protected:` `static void _bind_methods()`, and `void _notification(int WHAT)` if the class has `notif` blocks,
   - `private:` the generated helpers: enum wrappers, and default value functions.
6. The `#include` lines of the GD++ names that were only forward-declared, at the end, after namespace `godot`.

# The class source

In order:

1. `#define GDPP_DEBUGGING`, if a `@trace` or `@profile` annotation of the file's classes is on, then `#include "NAME.h"`, then the headers of names that only the source uses.
2. `@global impl` blocks.
3. In namespace `godot`, between `#define This NAME` and `#undef This`:
   - `_bind_methods`: binds each function (with its default values, and except the bodies of `@onthread` functions, which their tasks call directly), each variable's getter and setter and its property (after the inspector sections it starts), each signal, each integer constant, and each value of each exposed enum (as a bitfield flag for a bitfield),
   - the constructor, if needed: the creation line of a class whose `@trace` is on, RPC configurations, `set_process(true)` and `set_physics_process(true)` for overrides and engine functions, the initial values of variables, then the `ctor` block. See `gd++ man lifecycle`.
   - the destructor, with the `dtor` block, if the class has one or a `@trace` that's on,
   - `_notification`, if the class has `notif` blocks, engine functions or `@onready` variables: the `@onready` initial values, as `if (WHAT == NOTIFICATION_POST_ENTER_TREE && !is_node_ready()) { ... }`, then the call of `_ready`, then each block, as `if (WHAT == NOTIFICATION_A || ...) [&] { ... }();`, and the call of each other engine function, as `if (WHAT == NOTIFICATION_PROCESS) { _gdpp_body__process(get_process_delta_time()); }`, in order. An engine function is a method `_gdpp_body_NAME`, since godot-cpp would make a method named `_process` an override. See `gd++ man lifecycle`.
   - each function: the `GDVIRTUAL_CALL` of a `@virtual` function, or of an `@override` of one without `"final"`, then the body (or for `"super"`, the call of `_super_NAME`, which has the body, for the function that GD++ binds for a `@virtual` function, e.g. `think` for `_think`, the call of the `@virtual` function, for `@deferred` and `@thread_safe`, the call that runs `_gdpp_body_NAME` later, and for `@onthread`, `gdpp::run_task`, which starts a task that runs it on the `WorkerThreadPool`; see `gd++ man async`); then its enum wrapper, default value functions and RPC helper,
   - each variable's getter and setter, and their enum wrappers,
   - each signal's emit function,
   - the `impl` blocks.

In a `@game_only` class, each of these functions except `_bind_methods` starts with an editor check, in debug builds. Outside one, the functions of a `@game_only` function or variable do. See `gd++ man classes`.

When `@trace` or `@profile` annotations are on, the functions they apply to start with their code, after the editor check: `gdpp::ProfileStats` and `gdpp::Profile` for `@profile`, `gdpp::Trace` for `@trace`, and `gdpp::Watch` in each function that checks the class's `@trace` variables. A traced function that returns a value runs its body in a lambda, `return _gdpp_trace.ret([&]() -> T { ... }());`, so the trace sees every result. The constructor and destructor of a traced class call `gdpp::trace_lifetime`, and the emit function of a traced signal `gdpp::trace_emit`. See `gd++ man debugging`, and `gd++ trans FILE --trace all --profile all` for your own files.

# Generated names

GD++ names its helpers with the prefix `_gdpp_`, which is reserved: don't use it for your own names.

```
get_NAME, set_NAME           a variable's getter and setter
NAME (of a signal)           a signal's emit function, returning gdpp::Emitted
_gdpp_default_FUNC_PARAM     a static function that returns a parameter's default value
_gdpp_rpc_FUNC               an @rpc function's helper, which rpc calls
_gdpp_body_FUNC              the body of a @deferred, @thread_safe or @onthread function, which its deferred call or task runs
_gdpp_FUNC                   the wrapper that binds a function with enums in its signature
_gdpp_get_NAME, _gdpp_set_NAME   the wrappers that bind a variable of an enum type
_gdpp_CLASS_ENUM             a class's stand-in type for an enum
_gdpp_ret                    a local variable in @virtual functions
_gdpp_base                   an extern wrapper's object
```

`This` is a macro, defined around each class's code. The setter's parameter is `p_value`, unless a property's `set` block names it.

# #line directives

Every piece of your code, e.g. a function body or an initial value, is wrapped in `#line` directives: one before it, with its line in the GD++ file, and one after it, which switches back to the generated file. So compiler errors, warnings and debuggers point to the right line in the right file. In builds, the GD++ file is named relative to the build cache, e.g. `../src/player.gd++`.

Your code is copied with its line breaks, so a body's text starts on the line of its `{`.

# Extern headers

An extern NAME gets a header with a wrapper class NAME, in namespace `godot`:

```cpp
class Terrain {
public:
  using Base = Node3D;
  static constexpr const char *gdpp_name = "Terrain";
  explicit Terrain(Base *p_object);
  double height_at(double x, double z) const;
  int64_t get_seed() const;
  void set_seed(int64_t p_value) const;
  gdpp::Emitted changed() const;
protected:
  Base *_gdpp_base;
};
```

Its methods are defined inline, after the classes they may use, and call `_gdpp_base->call`, `call_deferred`, `get`, `set` or `emit_signal` with the member's name. See `gd++ man externs`.

If a `@trace` or `@profile` annotation of the extern is on, the header starts with `#define GDPP_DEBUGGING`, and the methods start with the same lines as a class's functions, with `gdpp::via_extern` and "extern" names:

```cpp
inline double Terrain::height_at(double x, double z) const {
  static gdpp::ProfileStats _gdpp_stats("extern Terrain.height_at");
  gdpp::Profile _gdpp_profile(_gdpp_stats);
  gdpp::Trace _gdpp_trace(gdpp::via_extern, _gdpp_base, "height_at", "x", x, "z", z);
  return _gdpp_trace.ret(gdpp::cast<double>(_gdpp_base->call(GDPP_STRING_NAME("height_at"), x, z)));
}
```

See `gd++ man debugging`.

The wrapper of an extern that extends another extern derives from that one's wrapper, e.g. `class Car : public Vehicle`, and shares its `Base` and `_gdpp_base`.

# Enum headers

An enum NAME gets a header with an enum class:

```cpp
enum class Suit : int64_t {
  DIAMONDS = 0,
  CLUBS = 1,
  SPADES = 2,
  HEARTS = 3,
};
```

A bitfield's enum class is followed by `GDPP_BITFIELD(Name)`, which gives it the bitwise operators, and lets `&` test as a `bool`.

# Registration

The build also generates `__register_types__.cpp`, in the build cache, outside `gdpp/`. It includes every class's header, and registers each class when the library loads, bases first, with `GDREGISTER_RUNTIME_CLASS` for runtime classes, i.e. GD++ classes without `@tool` and C++ classes without `tool = true`, and `GDREGISTER_CLASS` for the others. Its entry point is `gdpp_library_init`. See `gd++ man cpp-classes`.

In a package with GD++ classes, `__register_types__.cpp` also includes the GD++ runtime, and calls `gdpp::uninitialize()` when the library is unloaded: it waits for the package's running tasks, and removes the engine's hooks into the package's code, e.g. signal connections, so the editor doesn't call the old code after a hot reload. A package whose GD++ classes use `Async` also registers its class of tasks there, first, e.g. `FooAsync`, which `Async` types name: the GD++ runtime defines it. `SConstruct` defines `GDPP_ASYNC_CLASS` as the class's name, and `GDPP_QUIT_TIMEOUT_USEC` as the package's `quit_timeout`, for all the package's C++. See `gd++ man async`.

# Using generated classes from C++

Plain C++ files of the package can include a GD++ class's header, e.g. `#include "Counter.h"`, and use the class: its functions, getters and setters are public methods, and the fields of simple variables are public too.
