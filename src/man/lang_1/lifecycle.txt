Lifecycle: what runs when

This page explains what runs when an object of a GD++ class is created, gets ready, and is deleted: constructors, destructors, initial values of variables, `@onready`, and `notif` blocks.

# ctor and dtor

```gd++
class_name Enemy
extends Node3D

ctor {
  gd::print("An enemy was created.");
}

dtor {
  gd::print("An enemy was deleted.");
}
```

`ctor { ... }` is the class's constructor, and `dtor { ... }` its destructor. Their bodies are C++. A class has at most one of each, and neither takes arguments, since Godot creates objects without any:

```out
[×] res://enemy.gd++:4:5: Expected "{" to start the ctor block, but found "(".
     4 | ctor(int hp) {
       |     ^
    Hint: Constructors and destructors take no arguments: "ctor { ... }".
```

For objects that need arguments, write a `@static` function that creates and sets them up:

```gd++
@static
func with_health(hp: int) -> Enemy {
  Enemy *enemy = create Enemy;
  enemy->health = hp;
  return enemy;
}
```

The constructor runs whenever an object is created: by `create` in C++, by `Enemy.new()` in GDScript, and when Godot loads a scene or resource that holds it. The destructor runs when the object is deleted: for nodes, when they're freed, e.g. with `queue_destroy` or `queue_free()`, and for refcounted objects, when the last reference goes away. A `@pool` class can also have `@recycle ctor` and `@recycle dtor` blocks, which run each time an object is put to use and stops being used: when it's created or taken from the pool, and when it's returned to the pool or deleted. See `gd++ man pools`.

# What the constructor does

GD++ generates a constructor if the class needs one: if it has a `ctor`, a `@recycle ctor`, a variable with an initial value that isn't `@onready`, an `@rpc` function, or an override of `_process` or `_physics_process`. The constructor does this, in order:

1. For each `@rpc` function, set its RPC configuration. See `gd++ man rpc`.
2. If the class overrides `_process` or `_physics_process`, turn it on with `set_process(true)` or `set_physics_process(true)`.
3. Assign the initial values of the variables that aren't `@onready`, in the order of their declarations.
4. Run the body of `ctor`, in a block of its own.
5. In a `@pool` class, run the body of `@recycle ctor`, unless it has `@recycle("only")`. See `gd++ man pools`.

So the body of `ctor` sees every variable with its initial value.

```gd++
var speed: float = 5.0
var max_speed: float = speed * 2       // speed is set already

ctor {
  gd::print(speed, " ", max_speed);    // 5 10
}
```

# @onready and _ready

A node gets ready when it and all its children have entered the scene tree, which is when Godot calls `_ready`. Variables with `@onready` get their initial values right before that, in the order of their declarations, since their initial values often need the node's children:

```gd++
@onready
var label: Label = $Label

func _ready() -> void {
  label->set_text("Ready.");    // label is set already
}
```

GD++ assigns them in the class's `_notification`, at `NOTIFICATION_POST_ENTER_TREE`, the last notification before `NOTIFICATION_READY`, once the children are ready. So they're set before any `_ready` runs, even a script's that replaces the class's. `@onready` only works in classes that extend `Node`, since only nodes get ready: elsewhere, it's an error.

The class's `_ready` runs right after them, also before `NOTIFICATION_READY`, so it runs before a script's `_ready`. An `@override("engine") _ready` runs at `NOTIFICATION_READY` instead, unless a script replaces it. See `gd++ man functions`.

In a `@pool` class, a reused node gets ready again, but its `@onready` values and `_ready` only run the first time, unless they have `@recycle`. See "Getting ready again" in `gd++ man pools`.

# The order of everything

For a node created by a scene, Godot:

1. creates the object: the constructor runs, with the initial values of variables, then `notif POSTINITIALIZE`,
2. sets the properties saved in the scene, i.e. the exported variables, through their setters,
3. adds it to the scene tree: `_enter_tree` runs,
4. once its children are ready: the `@onready` initial values are set, then the class's `_ready` runs, then a script's,
5. every frame: `_process` and `_physics_process` run,
6. removes it from the tree: `_exit_tree` runs,
7. deletes it: `notif PREDELETE` runs, then the destructor.

Note step 2: values from the scene overwrite the initial values, since they're set after the constructor runs.

# In the editor

In the editor, Godot doesn't create objects of classes without `@tool`: it creates placeholders, which hold property values but run no code. So neither their constructor nor their destructor, nor any other of their functions, runs in the editor. Classes with `@tool` run everything in the editor too. Other code can still create an object of a runtime class with `create`, and then its code runs: `@game_only` classes check for the editor in every function, to prevent that. See `gd++ man classes`.

# Tracing objects' lives

With `@trace` on a class, in a build that turns it on, the constructor prints a line when an object is created, and the destructor when it's freed, e.g. `+ Bullet#28347 created` and `- Bullet#28347 freed`. They name the object by its instance id, since a node has no name yet in its constructor. An id without a "freed" line, once the object should be gone, points to a leak. For a `@pool` class, "created" and "freed" lines only show objects that are actually created and deleted: an object waiting in its pool is still alive. Its reuse and its return to the pool get lines of their own, marked `↻`. See `gd++ man debugging`.

# Notifications

Godot tells an object about events with notifications, e.g. `NOTIFICATION_READY` or `NOTIFICATION_PREDELETE`. A `notif` block runs when the object gets one of the notifications it lists:

```gd++
notif PREDELETE {
  gd::print("About to be deleted.");
}

notif ENTER_TREE, EXIT_TREE {
  gd::print(WHAT == NOTIFICATION_ENTER_TREE ? "Entered the tree." : "Left the tree.");
}
```

The names can also go in parentheses, as in `notif(ENTER_TREE, EXIT_TREE) { ... }`. Write them without `NOTIFICATION_`: GD++ adds it. They're the notifications of the class and its bases, e.g. `Object`'s `POSTINITIALIZE` and `PREDELETE`, and `Node`'s `ENTER_TREE`, `READY` and `PROCESS`, or the class's own constants named `NOTIFICATION_...`, e.g. `enum NOTIFICATION_HIT = 2000`. The body is C++, and `WHAT`, an `int`, is the notification that it's handling. `GENERATION`, an unsigned integer, is how many times a `@pool` class's pool took the object back, and always `0` in other classes. See "Getting ready again" in `gd++ man pools`.

A class can have any number of `notif` blocks, and a notification can be in more than one. When the object gets a notification, every block that lists it runs, in the order of the file. Each block runs on its own, so a `return` ends only that block.

Two notifications are worth knowing:

- `POSTINITIALIZE` comes right after the constructor, once the object is fully created.
- `PREDELETE` comes when the object is about to be deleted, before the destructor. The object is still whole, e.g. a node is still in the tree, so it can still emit signals and call the engine.

GD++ generates the class's `_notification` method from its `notif` blocks, its engine functions, e.g. `_process`, and its `@onready` variables, so a class can't declare its own `_notification`. Godot calls the `_notification` of each class in the chain of bases itself, so a subclass's `notif` blocks don't replace its base's: both run. A script's `_notification` doesn't replace them either: it runs after them.

# notif and engine functions

The engine functions, `_ready`, `_enter_tree`, `_exit_tree`, `_process`, `_physics_process` and `_draw`, are handlers of notifications too, written as functions: see `gd++ man functions`. In `_notification`, GD++ first sets the `@onready` variables, then runs `_ready`, and then the `notif` blocks and the other engine functions, in the order of the file:

```gd++
notif PROCESS {
  gd::print("first");
}

func _process(delta: float) -> void {
  gd::print("second");
}

notif PROCESS {
  gd::print("third");
}
```

Use the engine functions for their notifications, and `notif` blocks for every other notification, e.g. `PREDELETE`.

# Pools

A `@pool` class reuses its objects: `destroy` keeps an object in the pool, and `create` reuses it later. Its `ctor` and `dtor` still run only when an object is actually created or deleted, while its `@recycle ctor` and `@recycle dtor` run each time an object is put to use and stops being used: when it's created or taken from the pool, and when it's returned to the pool or deleted, unless they have `@recycle("only")`. Its `@recycle` variables get their initial values again when an object is reused. A reused node gets ready again, but its `@onready` values and `_ready` only run the first time, unless they have `@recycle`. See `gd++ man pools`.
