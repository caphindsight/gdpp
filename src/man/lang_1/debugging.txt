Debugging: @trace and @profile

Two annotations show what your code does while the game runs:

- `@trace` prints what happens: function calls, with their arguments, results and times, variable changes, signal emissions, and the creation and destruction of objects.
- `@profile` measures how long functions take. It shows the times live in the editor's monitors, and optionally in a table printed every few seconds.

Both are off unless a build turns them on. Off, they generate no code at all.

- So leave them in your code for good, like switched-off log statements.
- Turn on the ones you need, with a flag, when you need them.

# A first example

```gd++
class_name Player
extends CharacterBody3D

@trace
var health: int = 100

@trace
@profile
func take_damage(amount: int) -> bool {
  health -= amount;
  return health <= 0;
}
```

Build with tracing on, for the class `Player`:

```sh
gd++ build --trace Player
```

Run the game. The Output panel shows every call of `take_damage`, and every change of `health`:

```out
[f812] ▶ Player "Hero".take_damage(amount: 5)
[f812]   Player "Hero".health: 100 → 95  (in take_damage)
[f812] ◀ Player "Hero".take_damage → false  12.4 µs
```

Build without the flag, and all of it is gone again, at no cost:

```sh
gd++ build
```

# Groups: choosing what to turn on

Every `@trace` and `@profile` annotation belongs to one or more groups:

- always, the group named after its class, e.g. `Player`,
- the groups that its arguments name: `@trace("combat")` is in `Player` and `combat`, and `@trace("combat", "ai")` in `Player`, `combat` and `ai`.

Two groups need no annotation:

- `process`: every `on process` block and `_process` override, of all classes.
- `physics_process`: every `on physics_process` block and `_physics_process` override, of all classes.
- So `--profile process` times all of them.

Builds turn groups on with two flags, each followed by any number of group names:

```sh
gd++ build --trace combat                  # @trace annotations in the group combat
gd++ build --trace combat ai               # in combat or ai
gd++ build --trace Player                  # all @trace annotations in the class Player
gd++ build --trace all                     # all @trace annotations
gd++ build --profile all                   # all @profile annotations
gd++ build --profile process               # all _process functions, without annotations
gd++ build --trace ai --profile all        # both at once
```

- `all` turns on every annotation of its kind.
- The flags are independent: `--trace` only turns on `@trace`, and `--profile` only `@profile`.
- An annotation whose groups are all off generates nothing.
- Annotation arguments are names in double quotes, e.g. `@trace("combat")`.
- Without arguments, an annotation is only in its class's group.
- Group names are made of letters, digits and underscores, and don't start with a digit.

A member is on if its own annotation is on, or its class's annotation is:

```gd++
@profile("ai")
class_name Enemy
extends CharacterBody3D

@profile("physics")
func steer(delta: float) -> void { ... }

func think() -> void { ... }
```

- `--profile ai` profiles `steer` and `think`, through the class's annotation.
- `--profile physics` profiles only `steer`.
- `--profile Enemy` and `--profile all` profile both.

Other facts:

- The build parameters, which the build logs first, say when tracing or profiling is on, e.g. "Build parameters: linux.x86_64, debug, unoptimized, with docs, trace combat ai, profiling.".
- Changing the flags recompiles only the files whose generated code changes. With hot reload, the editor picks up the new library without a restart. See `gd++ man building`.
- A group name that no annotation uses turns nothing on, without an error. If a build prints nothing, check the group names, e.g. with `gd++ trans`.
- To see the generated code, pass the same flags to `gd++ trans`:

```sh
gd++ trans player.gd++ --trace all --profile all
```

# @trace on functions

`@trace` on a function prints two lines per call:

- one when it starts, with its arguments,
- one when it returns, with its result, if any, and how long it took.

```gd++
@trace
func pick_up(item: Item, count: int = 1) -> bool {
  ...
}
```

```out
[f1204] ▶ Player "Hero".pick_up(item: Item#28347, count: 1)
[f1204] ◀ Player "Hero".pick_up → true  3.1 µs
```

The parts of a line:

[f1204]
  The frame in which the line was printed, from `Engine.get_process_frames()`. Lines of the same frame have the same number. Off the main thread, the thread's id follows, e.g. `[f1204] [thread 13985]`. These parts are gray.

▶ and ◀
  The start and the end of a call.

Player "Hero".pick_up
  The object and the function.
  - A node: its class and name, e.g. `Player "Hero"`.
  - Other objects, e.g. resources: their class and instance id, e.g. `Item#28347`.
  - The class is the object's own. So a function of `Player`, called on an object of its subclass `Boss`, shows `Boss "Hero"`.
  - Static functions show only the class, e.g. `Player.create`.

(item: Item#28347, count: 1)
  The arguments, by name.
  - `String`, `StringName` and `NodePath` values are quoted.
  - Objects are named like above.
  - Enums show as numbers.
  - Other values show in their text form, e.g. `(1.0, 2.0, 3.0)` for a `Vector3`.
  - Values longer than 60 characters are cut, with "…".

→ true
  The result, shown like an argument. `void` functions have none.

3.1 µs
  How long the call took: in µs below one millisecond, in ms above. It includes the functions it called, but not the time spent printing and measuring. See "How accurate the times are" below.

Calls made during a traced call are indented, so nested calls read as a tree:

```out
[f1204] ▶ Player "Hero".take_damage(amount: 30)
[f1204]   ▶ Player "Hero".play_hurt_animation()
[f1204]   ◀ Player "Hero".play_hurt_animation  48.0 µs
[f1204]   ▶ Player "Hero".die()
[f1204]   ◀ Player "Hero".die  210.5 µs
[f1204] ◀ Player "Hero".take_damage → true  301.2 µs
```

Every call is traced, however it's called: from C++, from GDScript, from a signal, or with `call_deferred`. Details:

- `@deferred` and `@thread_safe` functions are traced when their body runs, later, not when the call is queued. They show with their own name.
- `@onthread` functions are traced when their body runs, on a worker thread, not when the call starts the task.
  - Their lines show the thread, and are indented by the calls on that thread.
  - Their result is the body's, not the `Async`. See `gd++ man async`.
- `@virtual` functions are traced when C++ code calls them, also when a script overrides them. Then the time includes the script's code.
  - Scripts usually call them without the underscore, e.g. `think` for `_think`, which goes through C++. Those calls are traced, as both functions.
  - Calls of an overridden function by its own name, e.g. `_think`, from GDScript, with `call()`, or from a signal, go straight to the script's version. They never reach the C++ function, so they aren't traced. To catch them, call `think` instead.
- A function that returns early still prints its end line.

# @trace on variables

`@trace` on a variable prints each change of its value, with the class's function that made it:

```gd++
@trace
var health: int = 100

@trace
var inventory: Array[Item]
```

```out
[f1204]   Player "Hero".health: 100 → 70  (in take_damage)
[f1377]   Player "Hero".inventory: [] → [<Item#28347>]  (in pick_up)
```

How it works:

- Every function of the class that could change the variable compares its value before and after the call.
- It prints the changes just before the call's end line.
- So it's the fastest way to answer "who changes this value?": no function needs tracing, and only changes print.

Details:

- The checking functions are the class's non-static, non-const functions, including the setters of its variables, `on` blocks, `@override` functions, and the bodies of `@deferred` and `@onthread` functions.
- So a change from GDScript, e.g. `player.health = 5`, shows as made in `set_health`.
- An `@onthread` body runs on another thread. Changes that other threads make while it runs show as its changes too.
- A change made in a function that another function of the same object called shows once, in the innermost function.
- Arrays and dictionaries are copied deeply and compared item by item. So a change of an item inside them shows too.
- Objects are compared by identity: which object the variable points to, not what's in it.
- A property with a get block is read through its getter.

Changes that show late, or not at all:

- A change made outside the class's own functions, e.g. by another class that writes the field directly in C++, or by a subclass, shows at the next call of one of the class's functions, as made there.
- Initial values, set in the constructor, don't show.

Cost:

- Checking takes time in every checking function, most of all for big arrays and dictionaries, which are copied twice per call.
- That time doesn't count in trace and profile times, but slows the game down.
- Trace big collections only when you need to.

# @trace on signals

`@trace` on a signal prints each emission, with its arguments, before the handlers run:

```gd++
@trace
signal died(cause: DeathCause)
```

```out
[f1204]   ⚡ Player "Hero" emits died(cause: 2)
```

- Only emissions with `emit` show, since GD++ traces them in the signal's emit function.
- Code that calls `emit_signal(string_name "died")` by name, and GDScript that emits the signal, bypass it.

See `gd++ man signals`.

# Failed assertions

With `--trace`, a failed `assert` also prints a trace line, in red, with the condition and its place in the GD++ file, since trace lines don't show where Godot's errors come from:

```out
[f1204] ▶ Player "Hero".aim()
[f1204]   ✖ Failed GD++ assertion: `target != nullptr`, at player.gd++:2.
[f1204] ◀ Player "Hero".aim  12.4 µs
```

This works in every class with assertions, with any groups, even where no annotation is on. See `gd++ man rewrites`.

# @trace on classes

`@trace` on a class works like `@trace` on all its functions, variables and signals. It also prints the creation and destruction of its objects:

```gd++
@trace("loot")
class_name Chest
extends Node3D
```

```out
[f3] + Chest#28347 created
[f3] ▶ Chest "Chest2"._ready()
[f3] ◀ Chest "Chest2"._ready  8.2 µs
[f901] ▶ Chest "Chest2".open(by: Player "Hero")
[f901]   Chest "Chest2".is_open: false → true  (in open)
[f901]   ⚡ Chest "Chest2" emits opened(by: Player "Hero")
[f901] ◀ Chest "Chest2".open  15.7 µs
[f902] - Chest#28347 freed
```

- Creation and destruction lines name the object by its instance id. A node has no name yet when it's created, and can't be asked for it any more while it's destroyed.
- Match them to the other lines with the id, or with the frame numbers.
- A "created" line without a "freed" line, once the object should be gone, points to a leak.

For a `@pool` class, reuse and return to the pool get lines too, marked `↻`:

```out
[f40] + Bullet#3001 created
[f95] ↻ Bullet#3001 returned to its pool
[f96] ↻ Bullet#3001 reused
[f150] ↻ Bullet#3001 returned to its pool
```

- They come right before the `@recycle dtor` and the `@recycle ctor` run.
- An object waiting in its pool is still alive. It has no "freed" line until the pool deletes it, e.g. when the game quits.

See `gd++ man pools`.

A class's `@trace` leaves out `on process`, `on physics_process`, and overrides of `_process` and `_physics_process`:

- They run every frame, and would bury everything else.
- They still check the traced variables.
- To trace them anyway, put `@trace` on them too:

```gd++
@trace("frame")
on physics_process(delta: float) { ... }
```

# @profile on functions, variables and classes

`@profile` measures how long every call takes, and prints nothing per call:

- On a function: times the function.
  - Like with `@trace`, `@deferred` and `@onthread` functions are timed when their body runs.
  - A `@virtual` one includes a script's override when C++ code calls it.
  - Calls of an overridden `@virtual` function by its own name, e.g. `_think`, aren't timed. See "@trace on functions" above.
- On a variable: times its getter and setter, e.g. `Player.get_ammo` and `Player.set_ammo`.
  - Useful for properties whose get or set block does real work.
  - A simple variable's getter and setter only copy a value, and your C++ code uses the field directly.
- On a class: times all its functions, and the getters and setters of its properties with get and set blocks.

The timings show in the editor's monitors, and with `--print`, in a table printed every few seconds.

# Leaving members out: @notrace and @noprofile

A class's `@trace` or `@profile` covers all its members. To leave one out, e.g. a small function that's called all the time, mark it `@notrace` or `@noprofile`:

```gd++
@trace("combat")
@profile
class_name Player
extends CharacterBody3D

@notrace
func distance_to_target() -> float { ... }      // never in the class's trace

@noprofile
var stamina: float { ... }                      // its getter and setter aren't timed

@notrace @trace("frame")
func update_aim() -> void { ... }               // traced with --trace frame, not --trace combat
```

`@notrace` works on functions, variables and signals:

- On a function: leaves it out of every group that its class's `@trace` puts it in.
  - That's the class's own group, e.g. `Player`, the groups that the class's `@trace` names, e.g. `combat`, and `all`.
  - Also the groups `process` and `physics_process`, which otherwise trace every `_process` and `_physics_process` function.
  - The function still reports changes it makes to the traced variables.
- On a variable: the class's `@trace` stops watching it, so its changes aren't printed.
- On a signal: the class's `@trace` stops printing its emissions.

`@noprofile` does the same for `@profile`, on functions and variables:

- A function isn't timed.
- A property's getter and setter aren't timed.
- Signals aren't profiled, so they don't take it.

Rules:

- A member's own `@trace` or `@profile` still applies. So `@notrace @trace("frame")` moves a function from the class's groups to the group `frame`.
- Like any `@trace`, the member's own annotation is also in the class's own group and in `all`. So `--trace Player` and `--trace all` still turn it on.
- `@notrace` needs a `@trace` on the member's class or extern, and `@noprofile` a `@profile`. Without one, there's nothing to leave the member out of, so it's an error.
- The class only needs the annotation, not a build that turns it on.

# Externs

`@trace` and `@profile` work on externs too, to watch the calls from your package into other packages, GDExtensions and scripts:

```gd++
@profile("net")
extern Lobby {
  extends Node

  @trace
  func join(name: String) -> bool

  var players: int

  @trace
  signal chat(text: String)
}
```

- On a function: `@trace` prints each call through the extern, and `@profile` times it, including the time of the call by name, which is often most of it. See "Speed" in `gd++ man externs`.
- On a variable: `@profile` times its getter and setter, e.g. `extern Lobby.get_players`. Variables can't have `@trace`: the extern can't see their changes.
- On a signal: `@trace` prints each emit through the extern.
- On the extern: like on all of its functions, variables and signals, except:
  - `@profile` leaves out `@deferred` and `@thread_safe` functions,
  - `@trace` leaves out variables,
  - objects of externs have no creation and destruction lines.
- `@profile` can't be used on `@deferred` and `@thread_safe` functions: a call through the extern only queues them, so there's nothing to time.
- The extern's group is its name, e.g. `--trace Lobby`, like a class's. If the class is a GD++ class of another package, the same flag turns on its own annotations in that package's build too.

The hooks are in the extern's wrapper. So they only see calls through this extern, not those from elsewhere, e.g. from the class's own package, from GDScript, or from signals. They look different from the class's own traces and timings, to keep the two apart:

```out
[f1204] ▷ extern Lobby "Lobby".join(name: "Me")
[f1204]   ▶ Lobby "Lobby".join(name: "Me")
[f1204]   ◀ Lobby "Lobby".join → true  31.0 µs
[f1204] ◁ extern Lobby "Lobby".join → true  36.4 µs
[f1210]   ⚡ extern Lobby "Lobby" emits chat(text: "hi")
```

- Calls through an extern use ▷ and ◁, and say "extern" before the object.
- Emissions through an extern say "extern" too.
- Their profile rows and monitors are named `extern Lobby.join`, next to the class's `Lobby.join`, if that's profiled too.
- Here, the class `Lobby` is traced in its own package too, so its lines show inside the extern's. The difference in time is the cost of the call by name.
- If two packages profile the same member of the same extern, the editor's monitors only show the first package's: they share the name.

# Profile monitors

While the game runs from the editor, open the Debugger panel, then its Monitors tab.

- Each profiled function has a graph there, in the GD++ category, e.g. "Player.take_damage (ms)".
- The graph shows the milliseconds per frame that the function took, averaged since the graph's last point.
- A function shows up once it has first run.
- The graphs show when a cost changes, e.g. when a fight starts, and how the functions compare to each other, and to Godot's own monitors, like the frame time.
- Pools have monitors too, in debug builds. See "Monitors" in `gd++ man pools`.

Caveat: the editor reformats every monitor's name like property names. The category shows as "Gd++", and "Player.take_damage (ms)" as "Player. Take Damage (ms)". GD++ can't turn this off. The profile tables below show the names as they are.

# Profile tables

With `--print`, the game also prints a table of the profiled functions every 10 seconds, or with `--period SECONDS`, every SECONDS seconds:

```sh
gd++ build --profile all --print
gd++ build --profile all --print --period 5
```

```out
━━ GD++ profile · last 10.0 s · 600 frames · debug, unoptimized ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Function                     Thread       Calls    Total ms     Self ms      Avg µs      Max µs    ms/frame        Budget (60 FPS)
───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
Enemy._physics_process         main       24000      950.40      412.77       39.60     1822.11       1.584                   9.5%
Enemy.find_path                main         310      537.63      537.63     1734.29     9807.40       0.896                   5.4%
Chunk.generate            subthread          12      402.00      402.00    33500.00    51220.87       0.670   4.0% (on background)
Player._physics_process        main         600       68.75       66.34      114.59      903.17       0.115                   0.7%
Player.take_damage         80% main           4        0.05        0.05       12.40       31.02       0.000   0.0% (on background)
```

- The title line says how much time the table covers, in seconds of real time and in frames, and what kind of build measured it.
- Each table covers only the time since the table before it. So it shows what the game does now, not averages since the start.
- It lists the functions that ran in that time, the slowest first, by total time. If none ran, it prints nothing.

The columns:

Thread
  Where the function ran, counting all its calls since the game started: "main" if always on the main thread, "subthread" if never, or else the share of its calls on the main thread, e.g. "80% main".

Calls
  How often the function ran.

Total ms
  The time it took in all, including the functions it called.

Self ms
  Total minus the time of the profiled functions it called. Functions without `@profile` count as its own time.

Avg µs
  The average time of a call: Total divided by Calls.

Max µs
  The longest call.

ms/frame
  Total divided by the frames: the time it takes per frame, on average.

Budget (60 FPS)
  ms/frame as a share of a frame's time at 60 frames per second, 16.7 ms.
  - For a function that only ran on the main thread: green below 10%, yellow up to 50%, red above.
  - A function that ran on other threads, e.g. an `@onthread` body, doesn't hold up the main thread's frames, or not all the time. Its share isn't colored, and says "(on background)", e.g. "4.0% (on background)".
  - `--fps FPS` sets another frame rate, e.g. `--fps 144` for 6.9 ms frames. The column's name says which.

Other facts:

- A recursive call's time is already in the time of the call it's inside. So Total, Max, ms/frame and Budget only count the outermost call.
- Calls and Self count every call. So for recursive functions, Avg is lower than the time of an outermost call.
- The table is one message, after a blank line, in a monospace font. It lines up in the editor's Output panel, and other output can't land inside it.
- The first table prints one period after the first profiled function ran.
- `--print` needs `--profile`. `--period` and `--fps` need `--print`.

# How accurate the times are

The times are the real times of the calls, measured with the system's steady clock, at nanosecond resolution. GD++ keeps measuring from counting as your code's time:

- Timing a call costs a few tens of nanoseconds. GD++ measures that cost once, when the first profiled function runs, and subtracts it from every call, and from the calls around it. So even functions under a microsecond show their own time.
- Printing traces and checking variables don't count, in trace times or in profile times. So `--trace` and `--profile` can be on together, even on the same functions.

What GD++ can't take out:

- Optimization. A debug build is unoptimized by default, and unoptimized C++ is often several times slower. The table's title line then says "unoptimized". Compare functions with each other in such a build. For times close to the shipped game's, build with `--opt`, which keeps the debug build's other features, or with `--ship`.
- The game around your code. Tracing slows the whole game down, since printing takes time: frames take longer, and fewer run. Profile without `--trace` to see the game at its real speed.
- The machine. Other programs, power saving and cold caches all change times. Look at several tables, not one.

# Recipes

Who changes a value? Trace the variable, and build with its class's group:

```gd++
@trace
var health: int = 100
```

```sh
gd++ build --trace Player
```

Each change prints with the function that made it. Nothing else prints, since no function is traced.

Is a function called at all, and with what? Trace it:

```gd++
@trace
func _on_body_entered(body: Node3D) -> void { ... }
```

In what order do things happen? Trace the functions involved, and read the frames and the indentation:

- Calls in the same frame have the same `[f...]` number.
- Calls made inside other calls are indented under them.
- Traced `@deferred` functions show when their bodies run, at the end of the frame.

Which signal handlers run? Trace the signal and its handlers. The handlers' calls print right under the emission.

```gd++
@trace
signal died(cause: DeathCause)
```

Do objects leak? Trace the class, e.g. `@trace` on class `Bullet`, and build with `--trace Bullet`. In a long session, every id with a "created" line should get a "freed" line.

What eats my frame? Profile the systems, in an optimized build:

```gd++
@profile("perf")
class_name Enemy
extends CharacterBody3D
```

```sh
gd++ build --opt --profile perf --print --period 5
```

Play the slow part of the game, and read the Budget column first: the share of the frame each function takes. Then:

- Total much bigger than Self: the time goes into the profiled functions it calls. Look at their rows.
- Self close to Total, although the function does little itself: the time goes into functions that aren't profiled, e.g. engine calls or helpers. Profile the helpers too.
- Max much bigger than Avg: the function is usually fast, but sometimes very slow, which shows as stutter. Trace it, and its variables, to see what differs in the slow calls.
- Many calls of a cheap function: calling it less may help more than making it faster.

Does my code run on threads? The Thread column says where each profiled function ran. Trace lines of calls off the main thread show the thread's id.

# Best practices

- Leave the annotations in your code. Off, they cost nothing, and the next time something breaks, the tracing is in place. Remove the ones that turn out to be noise.
- Name groups after the game's features and systems, e.g. `combat`, `ai`, `save`, `ui` or `net`, not after a bug. Then `--trace combat` means the same a month later, to everyone on the team.
- Use a class's own group for a quick look, e.g. `--trace Player`, and named groups for features that span classes.
- Trace narrowly, profile broadly. Traces of many functions are hard to read. Profiling many functions costs little, and the table sorts them. Start with `--profile all`, then trace the few functions that matter.
- Keep per-frame functions out of your usual trace groups, e.g. in a group of their own, like `@trace("frame")`. At 60 frames per second, one traced `_process` prints 120 lines per second.
- To find who changes a value, trace the variable, not the functions.
- Profile optimized code, with `--opt`, when absolute times matter. Profile without `--trace` when frame rates matter.
- Look at more than one table. The first ones include loading and warming up.
- Turn everything off with a plain `gd++ build` when you're done, before you measure the game's real speed, and before you ship.
- When output looks wrong or is missing, run `gd++ trans FILE` with the same flags, to see what the annotations generate.

# Limits

- They work on classes and externs, and on their functions, variables and signals, except `@trace` on extern variables.
- C++ code in `decl` and `impl` blocks can't have them.
- `@trace` on a function doesn't trace its overrides in subclasses. Put `@trace` on the override.
- Only `@tool` classes trace and profile in the editor, e.g. while you edit a scene:
  - A `@game_only` class, function or variable returns right away in the editor, before any tracing or profiling.
  - An `@editor_only` one returns right away in the game, the same way.
  - Other classes without `@tool` don't run in the editor at all.
- They work in debug and release builds. The monitors only show while the editor's debugger is connected to the game.
- Calls by its own name, e.g. `_think` from GDScript, of a `@virtual` function that a script overrides go straight to the script. They aren't traced or timed. Calls from C++ are, and so are calls of `think`.
- Trace lines of different threads can mix. Each line is printed whole.
- On a shader, they trace and time the whole call, copies to and from the GPU included, not each cell. To step through a shader's body, build with `gd++ build --nogpu`, which runs shaders on the CPU, and set a breakpoint in the body, like in C++ code. See "Without a GPU" in `gd++ man shaders`.

# What GD++ generates

The annotations add a few lines at the start of each function they apply to. With `--trace` and `--profile` on, `take_damage` from the first example becomes:

```cpp
bool Player::take_damage(int64_t amount) {
	static gdpp::ProfileStats _gdpp_stats("Player.take_damage");
	gdpp::Profile _gdpp_profile(_gdpp_stats);
	gdpp::Trace _gdpp_trace("Player", this, "take_damage", "amount", amount);
	gdpp::Watch _gdpp_watch(this, "take_damage", "health", [&] { return health; });
	return _gdpp_trace.ret([&]() -> bool {
		// Your body, unchanged.
	}());
}
```

- `gdpp::ProfileStats` holds the function's timings. With `--print`, the table's period follows the name, and with `--fps`, the frame rate, e.g. `_gdpp_stats("Player.take_damage", 10, 144)`.
- `gdpp::Profile` times the call.
- `gdpp::Trace` prints the start and end lines. A traced function that returns a value runs its body as a lambda, so the trace gets the result of every return.
- `gdpp::Watch` checks the class's traced variables.
- A traced signal's emit function calls `gdpp::trace_emit`.
- The constructor and destructor of a traced class call `gdpp::trace_lifetime`.
- The wrappers of externs use the same, with `gdpp::via_extern` for their traces, and names that start with "extern" for their profiles.
- A source file or an extern's header that uses any of these defines `GDPP_DEBUGGING` before its includes. That makes the runtime header include what they need.
- With `--trace`, the headers of classes with assertions also define `GDPP_TRACING`, for failed assertions.

See `gd++ man runtime` and `gd++ man generated`.
