Functions: func, parameters and overrides

A function is a method of its class that Godot knows. GDScript can call it, e.g. `player.jump()`, and so can `call()`, signals and the editor. Its signature is GD++, and its body is C++.

A shader is a special function, declared with `shader` instead of `func`, whose body is GLSL and runs on the GPU. To C++ and scripts, it's a static function like any other. See `gd++ man shaders`.

# Syntax

```gd++
func greet(name: String, times: int = 1) -> void {
  for (int64_t i = 0; i < times; i++) {
    gd::print("Hello, ", name, "!");
  }
}
```

- `func`, the name, then the parameters in parentheses, separated by commas. A trailing comma is allowed.
- A parameter is `name: Type`, or just `name` for a `Variant`, with an optional default value after `=`.
- Optionally, `->` and the return type. Without it, the function returns a `Variant`.
- Then the body: C++ code in braces. Optional.
- In the body, parameters have their C++ types. Here, `name` is a `const String &` and `times` an `int64_t`. See `gd++ man types`.

```gd++
func area(width: float, height: float) -> float {
  return width * height;
}

func describe(value) -> String {        // value is a Variant
  return String("Got: ") + String(value);
}

func random_thing() {                   // returns a Variant
  return Variant(42);
}
```

# Functions without a body

```gd++
func not_done_yet() -> int
```

- A function without a body gets a generated one.
- It returns the type's default value: `0`, `false`, an empty `String`, `nullptr`, and so on, or nothing for `void`.
- Handy for `@virtual` functions, and to sketch a class's API.

# What GD++ does with a function

- Declares it as a public method of the C++ class, or a private one with `@private`, and defines it in the class's source file, with your body.
- Binds it in `_bind_methods`, so Godot can call it:
  - plain functions: with `ClassDB::bind_method`, with parameter names and default values,
  - `@static`: with `ClassDB::bind_static_method`,
  - `@virtual`: with `GDVIRTUAL_BIND`, next to a function that calls them,
  - `@virtual("noscript")`: like plain functions,
  - `@override`: not at all, since the engine binds them,
  - `@private`: not at all, so only C++ code calls them.
- With `@game_only`, or in a `@game_only` class, starts the body with a check that returns right away in the editor, in debug builds. See `gd++ man classes`.
- With `@editor_only`, or in an `@editor_only` class, starts the body with a check that returns right away in the game.

Facts:

- Functions are plain C++ methods. C++ code calls them directly, e.g. `jump();` or `player->jump();`, at full speed.
- No overloading: function names must be unique in their class, including the getters and setters of variables and the emit functions of signals.

# Default values

```gd++
func spawn(count: int = 1, at: Vector3 = Vector3(0, 1, 0), kind: Kind = Kind::BIG) -> void { ... }
```

A default value is:

- a C++ expression, up to the `,` or `)` that ends it,
- or a block of C++ that returns the value,
- or, for a parameter of a GD++ enum type, one of the enum's values, e.g. `suit: Suit = HEARTS`, or for a bitfield, several combined, e.g. `mask: Layer = WORLD | PLAYER`. See `gd++ man enums`.

```gd++
func shout(text: String = {
  return String("HEY").repeat(3);
}) -> void { ... }
```

Parameters with default values must come last:

```out
[×] res://a.gd++:4:20: Parameter b needs a default value, since a parameter before it has one.
     4 | func f(a: int = 1, b: int) -> void {}
       |                    ^
    Hint: Parameters with default values must come last.
```

How they work:

- GD++ puts each default value into a static method of the class.
- Godot calls it once, when it registers the class, and uses the result whenever GDScript leaves the parameter out.
- C++ callers get the default values too: the C++ declaration has them.
- Since it's a static method, a default value can't use the object (`this`) or the other parameters.
- The editor's help shows an expression default as written.

# @override

```gd++
@override
func _unhandled_input(event: InputEvent) -> void {
  if (event->is_action_pressed(string_name "jump")) {
    jump();
  }
}

@const @override
func _get_configuration_warnings() -> PackedStringArray {
  return {};
}
```

`@override` overrides:

- a virtual function of the engine, i.e. of the base class, e.g. `_input`, `_unhandled_input`, `_gui_input` or `_get_configuration_warnings`. The engine calls it, like in GDScript.
- a `@virtual` function of a GD++ base class. See "@virtual" below.
- a `@virtual("noscript")` function of a GD++ base class, with `@override("noscript")`. See the `@virtual("noscript")` section below.

Rules:

- A function named like a virtual function of the base class must have `@override`. So a function never overrides one by accident.
- Other functions can't have `@override`: a plain function isn't virtual, so there's nothing to override.
- Functions that implement or override a trait's function never take `@override` or `@virtual`. They're always implicitly virtual. See `gd++ man traits`.
- GD++ knows the engine's virtual functions from the package's API spec. See `gd++ man dependencies`.
- The signature must match the engine's exactly, in C++ terms, including the return type. Without `-> void`, the function returns a `Variant`, and the C++ compiler reports that it doesn't override anything.
- `gd++ doc Node._input` shows a signature.
- A const engine function, e.g. `_get_configuration_warnings`, needs `@const` too: `@const @override`.
- The engine's `float` parameters are `double`, like GD++'s `float`.

```out
[×] res://player.gd++:4:1: Function _unhandled_input overrides a virtual function of Node, so it needs @override.
     4 | func _unhandled_input(event: InputEvent) -> void {
       | ^^^^
    Hint: Add @override, or rename the function.
```

Facts:

- Overrides are not bound: the base class binds them already.
- Overriding `_process` or `_physics_process` turns processing on in the constructor, with `set_process(true)` or `set_physics_process(true)`, since godot-cpp doesn't.

Scripts:

- A script that extends the class and defines a function of the same name replaces the override. The engine calls the script's version, never the GD++ one.
- A script can't call the GD++ version with `super`, e.g. `super._unhandled_input(event)`: Godot doesn't allow `super` calls of the engine's virtual functions.
- For `_ready`, `_process` and the like, use `on` blocks instead, which scripts can't replace. See `gd++ man notifications`.
- For the others, use `@override("super")`.

# @override("super")

```gd++
@override("super")
func _unhandled_input(event: InputEvent) -> void {
  gd::print(event);
}
```

- GD++ also binds the body as a function of its own, `_super_NAME`, which a script calls in place of `super`. Here: `_super_unhandled_input(event)`.
- Works on every `@override` function, of the engine or of a GD++ `@virtual` function.
- Works on `@virtual` functions too. See the `@virtual("super")` section below.
- The bound function's name, e.g. `_super_unhandled_input`, must be free.

```gdscript
extends Player

func _unhandled_input(event):
    _super_unhandled_input(event)
    print("and more")
```

# on blocks

- An override replaces the base's function. Only the most derived one runs, unless it calls the base's. A script's function of the same name replaces it in turn.
- An `on` block adds to the base's. The base's and the subclass's both run, and scripts can't replace them.
- So to run code at `_ready`, `_process` and the like, write `on` blocks, e.g. `on ready { ... }` and `on process(delta: float) { ... }`, not overrides.

See `gd++ man notifications`.

# @virtual

```gd++
@virtual
func _can_pick(item: Item) -> bool {
  return true;
}

@virtual
func _on_hit(damage: int) -> void
```

`@virtual` declares a function that scripts can override, like the engine's virtual functions.

- Its name must start with `_`.
- A GDScript that extends the class overrides it by defining a function of the same name.
- When C++ code calls it:
  - a script's version runs, if a script overrides it,
  - else the body runs, as a fallback,
  - else, without a body, the type's default value is returned.
- GD++ generates a `GDVIRTUAL` declaration, and binds it with `GDVIRTUAL_BIND`.
- The editor's help marks it "virtual".
- In C++, it's a virtual method.

```gdscript
extends Player

func _can_pick(item):
    return item.price < 10
```

Scripts call it without the underscore:

- GD++ also binds `can_pick`, which calls `_can_pick`. So the script's version or the body runs, like from C++.
- Godot doesn't bind virtual functions. Calling `_can_pick` by name only works on objects whose script overrides it.
- `can_pick` is a function of the class like any other, so its name must be free.
- `@virtual("private")` leaves it out.

```gdscript
if player.can_pick(item):
    print("Picked.")
```

A GD++ subclass overrides the function with `@override`, and a script can then override it again:

```gd++
class_name Hero
extends Player

@override
func _can_pick(item: Item) -> bool {
  return item->is_light();
}
```

- When C++ code calls `_can_pick`, through a `Player` or a `Hero`, a script's version runs first, if a script overrides it. Otherwise `Hero`'s body runs.
- A script's call of `can_pick` does the same.
- The override doesn't redeclare the function for scripts: `Player`'s `GDVIRTUAL` and `can_pick` do that.

# @virtual("private")

```gd++
@virtual("private")
func _on_hit(damage: int) -> void
```

- GD++ doesn't bind `on_hit`.
- Scripts can override `_on_hit`, but only C++ code calls it.
- Use it for hooks that the class calls itself.

# @virtual("super")

```gd++
@virtual("super")
func _can_pick(item: Item) -> bool {
  return item->get_weight() < 10;
}
```

- GD++ also binds the body as `_super_can_pick`, which a script's override calls in place of `super`, like with `@override("super")`.
- The override must not call `can_pick` instead: that calls the override again, forever.
- Combines with `"private"`: `@virtual("private", "super")`.

```gdscript
extends Player

func _can_pick(item):
    return item.price < 10 and _super_can_pick(item)
```

# @virtual("noscript")

```gd++
@virtual("noscript")
func damage_of(item: Item) -> int {
  return 1;
}
```

`"noscript"` makes a virtual function for C++ only:

- In C++, it's a virtual method, like with plain `@virtual`.
- GD++ generates no `GDVIRTUAL`: scripts can't override it.
- Its name doesn't need to start with `_`.
- GD++ binds it like a plain function, so scripts can still call it, by its own name.
- It takes no other arguments: `"private"` and `"super"` are about scripts' overrides.
- Faster than plain `@virtual`: a call is a plain C++ virtual call, without a check for a script's version.

A GD++ subclass overrides it with `@override("noscript")`:

```gd++
class_name Hero
extends Player

@override("noscript")
func damage_of(item: Item) -> int {
  return item->get_weight() * 2;
}
```

- The override must say `"noscript"`, and only overrides of a `@virtual("noscript")` function take it.
- In C++, it's `override`.
- Combines with `"final"`: `@override("noscript", "final")`. In C++, it's `override final`.
- Not with `"super"`, which is for scripts.

# @override("final")

```gd++
@override("final")
func _can_pick(item: Item) -> bool {
  return true;
}
```

On an `@override` of a GD++ `@virtual` function, plain or `"noscript"`, `"final"` makes it the last version:

- Subclasses can't override it. In C++, it's `override final`.
- C++ calls never run a script's version.
- A script can still define a function of that name. Only calls of it by name reach it, e.g. `player._can_pick(item)` from GDScript. `can_pick` runs the final version.
- It only works there: the engine runs scripts' overrides of its own virtual functions, e.g. `_input`, and GD++ can't stop that.
- Combines with `"super"`: `@override("final", "super")`.

# @const

```gd++
@const
func is_alive() -> bool {
  return health > 0;
}
```

- Makes the function a const method in C++: it can't change the object's fields, and can be called through const pointers and references.
- The editor's help marks it "const".
- With `@virtual`: a const virtual function.

# @static

```gd++
@static
func lerp_angle(from: float, to: float, weight: float) -> float {
  return Math::lerp_angle(from, to, weight);
}
```

- Makes the function static: it belongs to the class, not to an object.
- It has no `this`, and can't use the object's fields.
- GDScript calls it on the class: `Player.lerp_angle(0, 1, 0.5)`.

# @private

```gd++
func hurt(damage: int) -> void {
  health -= clamped(damage);
}

@private
func clamped(damage: int) -> int {
  return damage < health ? damage : health;
}
```

- Makes the function a private method in C++: only the class's own C++ code calls it.
- GD++ doesn't bind it, so Godot doesn't know it: scripts, `call()` and signals connected by name can't reach it, and the editor's help leaves it out.
- To connect it to a signal, use `callable_mp(this, &This::clamped)`.
- Like a method in a `decl` block, but written as a `func`. See `gd++ man code`.
- Combines with `@static`, `@const`, `@deferred`, `@thread_safe` and `@onthread`. Their `_gdpp_body_NAME` is still bound, since their calls run it by name or from a task.

# @rpc

`@rpc` makes the function callable over the network. See `gd++ man rpc`.

# @deferred and @thread_safe

```gd++
@deferred
func respawn(at: Vector3) -> void {
  set_position(at);
}
```

- `@deferred`: every call goes through `call_deferred`, from C++, from scripts, and over the network. The body runs later, at the end of the frame.
- `@thread_safe`: the same, with `call_thread_safe`. A call from another thread runs later on the main thread. A call from the main thread runs right away. Only for classes that extend `Node`.
- The function must return `void`, since the body runs later.
- GD++ puts the body in a second method, `_gdpp_body_NAME`, which the call runs by name. See `gd++ man generated`.
- A property's `set` block takes them too. See "Properties" in `gd++ man variables`.

# @onthread

```gd++
@onthread
func find_path(from: Vector2, to: Vector2) -> PackedVector2Array {
  ...
}
```

- Every call, from C++ or from scripts, runs the body on Godot's `WorkerThreadPool`.
- The call returns right away, with an `Async` of the function's return type. Here: an `Async[PackedVector2Array]`.
- The caller:
  - tests whether the task is done with `is_done`,
  - takes the result with `claim`,
  - can ask the task to stop with `cancel`, which the body notices with `is_cancelled`.
- GD++ puts the body in a second method, `_gdpp_body_NAME`, which the task calls.

`@onthread("detached")`:

- The function must return `void`.
- Its calls return nothing: they start the task, and forget it.
- Once the body is done, the task schedules a deferred call that finishes it.

See `gd++ man async`.

# @game_only

```gd++
@tool
class_name Turntable
extends Node3D

on process(delta: float) {
  rotate_y(delta);          // Spins in the editor too.
}

@game_only
func launch() -> void {
  gd::print("Launched!");   // Only in the game.
}
```

- The function only runs in the game, never in the editor. E.g. to keep a few functions of a `@tool` class out of the editor.
- In debug builds, which the editor loads, its body starts with a check. In the editor, the function returns right away, with a default value. An `@onthread` function returns an empty `Async`.
- `on` blocks, e.g. `on process(delta: float) { ... }`, take it too.
- In a `@game_only` class, every function already has it.
- `@editor_only` is the opposite: the function only runs in the editor. Only in a `@tool` class.

See `gd++ man classes`.

# @trace and @profile

```gd++
@trace
func take_damage(amount: int) -> bool {
  health -= amount;
  return health <= 0;
}

@profile("ai")
func find_path(to: Vector3) -> PackedVector3Array {
  ...
}
```

For debugging:

- `@trace`: in builds with `--trace Player` (the class's name) or `--trace all`, prints each call of `take_damage` when it starts, with its arguments, and when it returns, with its result and how long it took.
- `@profile`: in builds with `--profile ai`, times each call of `find_path`, for the editor's monitors and a table of timings.
- In other builds, they generate nothing.
- Their arguments name groups, which the options choose.
- They work on every kind of function, including static, `@virtual`, `@override`, `@deferred` and `@onthread` ones.
- Calls by name of a `@virtual` function that a script overrides, e.g. `player._can_pick(item)` from GDScript, go straight to the script, and aren't traced or timed. Calls from C++ are, and so are calls of `can_pick`, which go through C++.

See `gd++ man debugging`.

# Combining annotations

Annotations combine where it makes sense, e.g. `@virtual @const`. These are errors:

```
@static with @virtual, @override, @const, @rpc, @deferred or @thread_safe
@virtual with @override, @rpc, @deferred, @thread_safe or @onthread
@override on a function that overrides no virtual function
@override("final") without a GD++ @virtual function to override
@override("noscript") without a @virtual("noscript") function to override, and @override without "noscript" with one
"noscript" with "private" or "super"
@virtual without "noscript", on a function whose name doesn't start with _
A function with the name of a virtual function of the base class, without @override
@virtual or @override on a function that implements or overrides a trait's function
@recycle on a function other than an @override _ready
@override with @rpc, @deferred, @thread_safe or @onthread
@rpc with @onthread
@private with @virtual, @override or @rpc
@deferred with @thread_safe or @onthread
@thread_safe with @onthread
```

- `@trace`, `@profile`, `@game_only` and `@editor_only` combine with all of them.
- `@game_only` doesn't combine with `@editor_only`.
- Each annotation can be used once per function.
- Only `@override`, `@virtual`, `@rpc`, `@trace` and `@profile` take arguments.

# Enums in signatures

- A function whose parameters or return type use a GD++ enum is bound through a generated wrapper, named `_gdpp_` followed by the function's name.
- The wrapper converts between the enum and the class's own copy of it, which Godot sees.
- Your function keeps the plain enum type.

See `gd++ man enums`.

# Doc comments

```gd++
/// Deals [param damage] to the player.
/// Returns [code]true[/code] if the player died.
func hurt(damage: int) -> bool { ... }
```

- A doc comment before a function becomes its description in the editor's help.
- Annotations and the doc comment can come in any order.

See `gd++ man docs`.

# Examples

```gd++
class_name Inventory
extends Node

var items: Array[Item]

/// Adds an item, unless the inventory is full.
func add(item: Item, max_size: int = 20) -> bool {
  if (items.size() >= max_size) {
    return false;
  }
  items.push_back(item);
  return true;
}

@const
func total_price() -> int {
  int64_t total = 0;
  for (int64_t i = 0; i < items.size(); i++) {
    Gd<Item> item = items[i];
    total += item->get_price();
  }
  return total;
}

@static
func max_items() -> int {
  return 20;
}

@virtual
func _accepts(item: Item) -> bool {
  return true;
}
```
