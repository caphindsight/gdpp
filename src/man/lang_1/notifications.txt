Notifications: on ready, on process and the like

`on` blocks run code when an object gets a notification from the engine, e.g. when a node gets ready, processes a frame, draws, or is about to be deleted.

# Syntax

```gd++
on ready {
  gd::print("Ready.");
}

on process(delta: float) {
  rotate_y(delta);
}

on predelete {
  gd::print("About to be deleted.");
}
```

- `on`, the notification's name, then the body: C++ in braces.
- With a variable and a dot, e.g. `on button.pressed`, an `on` block runs at a signal instead. See "Connecting to signals" in `gd++ man signals`.
- The name is the engine's constant without `NOTIFICATION_`, in lower case: `on predelete` runs at `NOTIFICATION_PREDELETE`.
- No return type. Property callbacks return a value, whose type GD++ knows. See "Property callbacks" below.
- A class has at most one `on` block per notification.
- Notification names stay free as names elsewhere, e.g. `var ready: bool`.

# Adding, not replacing

`on` blocks add up:

- Godot sends each notification to every class in the chain of bases.
- So a base's `on ready` and a subclass's both run: the base's first, or last for notifications that Godot sends in reverse, e.g. `predelete`.
- A script that extends the class can't replace them.

An `@override` function does the opposite: it replaces the base's function, and a script's function of the same name replaces it in turn.

```gd++
class Base {
  extends Node

  on ready {
    gd::print("Base is ready.");
  }
}

class Sub {
  extends Base

  on ready {
    gd::print("Sub is ready.");
  }
}
```

- A `Sub` prints both lines.
- With `@override func _ready() -> void` in both classes instead, it would only print "Sub is ready.".
- So use `on` to run code at an event, and `@override` only to change what a virtual function does. See "@override" in `gd++ man functions`.

# Which notifications

An `on` block works for every notification of its class and of its bases.

- GD++ looks up `NOTIFICATION_` constants in the package's API spec, which comes from the project's Godot version, and in the GD++ classes.
- So it also works for the notifications of newer Godot versions, and for the class's own ones.
- Any other name is an error:

```out
[×] res://a.gd++:4:1: Class Mob and its bases have no notification redy.
     4 | on redy {}
       | ^^^^^^^
    Hint: Did you mean "ready"?
```

# Special notifications

Most `on` blocks just run at their notification. A few do more:

- `on ready`:
  - Runs at `NOTIFICATION_POST_ENTER_TREE`, the last notification before `NOTIFICATION_READY`, once the node's children are ready, right after the `@onready` initial values.
  - So it runs before a script's `_ready`.
  - It only runs the first time the node gets ready, not when it enters the tree again.
  - In a `@pool` class, it only runs the first time an object gets ready, unless it has `@recycle`. See "Getting ready again" in `gd++ man pools`.
- `on process`, `on physics_process`, `on internal_process` and `on internal_physics_process`:
  - Turn their processing on in the constructor, with `set_process(true)` and the like.
  - Can take the delta time, the seconds since the last frame, as a `float` parameter in parentheses, with a name you choose: `on process(delta)` or `on process(dt: float)`.
  - The parameter and its type are optional: `on process { ... }` works too. GD++ knows the type, so a type, if written, must be `float`.
- Other `on` blocks take no parameters.

# Every notification

An `on` block without a name runs at every notification. Its optional `int` parameter is the notification:

```gd++
on(what: int) {
  if (what == NOTIFICATION_ENTER_TREE || what == NOTIFICATION_EXIT_TREE) {
    gd::print("The tree changed.");
  }
}
```

- `on { ... }`, without the parameter, runs at every notification too.
- A class has at most one of them.
- Use it for notifications without an `on` block of their own, or to handle several in one place, e.g. the engine's own `NOTIFICATION_READY`, at which `on ready` doesn't run.

# Custom notifications

- A class's own constants named `NOTIFICATION_...` are notifications too, e.g. `enum NOTIFICATION_HIT = 2000`.
- `on hit` handles it, in the class and in its subclasses.
- `notification(NOTIFICATION_HIT)` sends it.

See "Integer constants" in `gd++ man enums`.

# Property callbacks

A few more `on` blocks let a class decide about its properties, like the functions `_get`, `_set` and so on of GDScript. E.g. to show properties in the inspector that aren't variables, or to hide some depending on others:

```gd++
@tool
class_name Inventory
extends Node

var items: Array = {
  Array slots;
  slots.resize(3);
  return slots;
}

on get(name) {
  String s = name;
  return s.begins_with("item_") ? items.get(s.get_slice("_", 1).to_int()) : Variant();
}

on set(name, value) {
  String s = name;
  if (!s.begins_with("item_")) {
    return false;
  }
  items.set(s.get_slice("_", 1).to_int(), value);
  return true;
}

on get_property_list {
  TypedArray<Dictionary> list;
  for (int64_t i = 0; i < items.size(); i++) {
    list.push_back(Dictionary(PropertyInfo(Variant::OBJECT, "item_" + String::num_int64(i), PROPERTY_HINT_RESOURCE_TYPE, "Item")));
  }
  return list;
}
```

The blocks, with their full signatures:

```
on get(name: StringName) -> Variant                  the value of the property name, or null if it isn't one of the class's
on set(name: StringName, value: Variant) -> bool     sets the property name, and returns true, or returns false if it isn't one of the class's
on get_property_list -> Array[Dictionary]           more properties, each a Dictionary like those of Object.get_property_list()
on validate_property(property: Dictionary)          changes how the inspector shows a property, e.g. its "usage" or "hint", in place
on property_can_revert(name: StringName) -> bool     whether the inspector shows a revert button for the property name
on property_get_revert(name: StringName) -> Variant  the value that the revert button sets, or null if it isn't one of the class's
on to_string -> String                               the text of the object in print() and str()
```

Like for other `on` blocks, the signature is optional:

- The parameters' names are yours to choose.
- Their types and the return type can be left out: GD++ knows them. If written, they must be those above.
- The parameters at the end can be left out too, e.g. `on property_can_revert { ... }` or `on set(name) { ... }`, if the block doesn't need them.

A wrong type is an error, which explains what the block returns:

```out
[×] res://inventory.gd++:4:45: The on set block is Godot's _set, which returns a bool, not void: true if it set the property, or false if the class doesn't have the property.
     4 | on set(name: StringName, value: Variant) -> void {
       |                                             ^^^^
    Hint: Leave out the return type, which GD++ knows, or write "-> bool".
```

Facts:

- They're the functions `_get`, `_set`, `_get_property_list`, `_validate_property`, `_property_can_revert`, `_property_get_revert` and `_to_string` of godot-cpp, which GD++ generates from the blocks.
- All but `on set` are const: they can't change the object's fields, except mutable ones.
- In `on validate_property`, changes to the `Dictionary` change the property.
- They add up, like other `on` blocks: a base's block runs too, and handles the properties that the subclass's doesn't. Except `on to_string`: the most derived one gives the text.
- They take the annotations of other `on` blocks, except `@async` and `@recycle`: Godot needs their result right away.
- A class's variables don't go through them: Godot handles those itself.
- Without `@tool`, the editor runs none of them, since it runs none of the class's code. To change the inspector, use `@tool`.

# How they work

- GD++ generates the class's `_notification` from its `on` blocks and its `@onready` variables. So a class can't declare its own `_notification`.
- Each `on` block's body is a method of its own, which `_notification` calls when `WHAT` is its notification.
- Within `_notification`: the `@onready` initial values first, then `on ready`, then the other `on` blocks, in file order.
- A `return` ends only its own block.
- `on` blocks aren't functions of the class: C++ code and scripts can't call them.
- They can read `GENERATION`. See "Getting ready again" in `gd++ man pools`.

# Annotations

`on` blocks take only:

- `@trace`, `@profile`, `@notrace` and `@noprofile`,
- `@game_only` or `@editor_only`,
- `@recycle`, on `on ready` in a `@pool` class,
- `@async`, see "Awaiting in on blocks" below.

```gd++
@trace
on physics_process {
  move_and_slide();
}
```

The groups `process` and `physics_process` turn on the tracing and profiling of all `on process` and `on physics_process` blocks, even without annotations. See `gd++ man debugging`.

# Awaiting in on blocks

With `@async`, an `on` block is a coroutine: it can `await` signals and tasks, like an `@async` function.

```gd++
@async
on ready {
  anim->play("intro");
  await anim->animation_finished;
  start_level();
}
```

- At the notification, the block runs until its first `await` that waits. Then the notification goes on, and the rest of the block runs once the signal comes.
- Nothing waits for the block, like for an `@async("detached")` function. So `@async` takes no arguments here.
- Only the part before the first `await` runs in the notification's order, e.g. before a script's `_ready`. The rest runs later.
- If the node is freed while the block waits, the block stops there.
- It doesn't combine with `@profile`. With `@trace`, only its start is traced, like an `@async` function's.
- The nameless block, `on(what: int)`, can't be `@async`: it runs at every notification.
- An `await` in a block without `@async` is an error.

Don't make the per-frame blocks `@async`: `on process`, `on physics_process`, `on internal_process` and `on internal_physics_process`. Unless you know exactly what you're doing:

- Each frame starts another coroutine, while those of earlier frames may still wait.
- So they pile up, and each one runs the rest of the block later, e.g. 60 of them a second after a 1-second `await`.
- GDScript's `await` in `_process` has the same pitfall.
- To run a sequence that spans frames, start one `@async` function from `on ready` instead, and loop in it, e.g. with `await get_tree()->process_frame`.

See `gd++ man async`.

# Overrides

A function named like a notification's engine function, e.g. `func _ready() -> void`, is an override. So it needs `@override`, like any other override:

```out
[×] res://a.gd++:4:1: Function _ready overrides a virtual function of Node, so it needs @override.
     4 | func _ready() -> void {}
       | ^^^^
    Hint: To add code that runs at its notification, write "on ready { ... }" instead. Only to replace the base's _ready, which a script replaces in turn, add @override.
```

- A plain override is rarely what you want: it replaces the base's, and a script's function of the same name replaces it.
- Only if you're sure you need one, write `@override func _ready() -> void`.
- It runs at `NOTIFICATION_READY`, unless a script replaces it.

See "@override" in `gd++ man functions`.

# Not notifications

Some engine callbacks are only virtual functions, not notifications. `on` blocks can't handle them: use `@override` functions, which replace the base's.

- Node: `_input`, `_shortcut_input`, `_unhandled_input` and `_unhandled_key_input`.
- Control: `_gui_input` and `_drop_data`.
- CollisionObject2D and CollisionObject3D: `_input_event`, `_mouse_shape_enter` and `_mouse_shape_exit`.
- MainLoop: `_initialize` and `_finalize`.

`on unhandled_input` says so:

```out
[×] res://a.gd++:4:1: Class Mob and its bases have no notification unhandled_input.
     4 | on unhandled_input {}
       | ^^^^^^^^^^^^^^^^^^
    Hint: unhandled_input isn't a notification, but a virtual function of Node: write "@override func _unhandled_input(...)".
```
