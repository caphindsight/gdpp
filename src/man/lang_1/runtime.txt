The runtime header: GD++'s C++ helpers

Every file that GD++ generates includes one header, the GD++ runtime: `gd++/syntax_1.hpp`, for syntax 1.

- It holds the helpers that generated code needs, and a few that your C++ code can use.
- It doesn't depend on your code: it's the same for every package.
- To read it:

```sh
gd++ trans --runtime --syntax 1
```

- In a build, it's in the build cache, at `gdpp/gd++/syntax_1.hpp`.

# What it includes

The godot-cpp headers that generated code always needs. So your code can use their names without GD++ finding them first:

- `Engine`, `Node`, `Object`, `RefCounted`, `Ref`, `Resource`, `ResourceLoader`, `ProjectSettings`,
- the global constants, e.g. `Error` and `PropertyHint`,
- `ClassDB`, `Variant`, `TypedArray`, `TypedDictionary`, `UtilityFunctions`, `CallableCustom`,
- `SceneTree`, `Window` and `WorkerThreadPool`,
- `<atomic>`, `<chrono>`, `<cstdint>`, `<cstddef>`, `<cstdio>`, `<cstdlib>`, `<functional>`, `<mutex>`, `<thread>` and `<type_traits>`.

`GDPP_DEBUGGING`:

- A source file that defines it before its includes also gets the code of `@trace` and `@profile`, and the headers it needs: `OS`, `Performance`, `SceneTree`, `Window`, and standard headers like `<atomic>`, `<chrono>`, `<functional>`, `<mutex>` and `<vector>`.
- GD++ defines it in the sources of classes, and the headers of externs, whose `@trace` or `@profile` annotations are on. Other files don't compile any of it.
- The debugging code has its own include guard. So an extern's header gets it even when the runtime header was included before without it.

`GDPP_TRACING`:

- With `gd++ build --trace`, the headers of classes with assertions define it.
- It also gets the debugging code, and makes failed assertions print a trace line.
- It has its own include guard too, so it works whatever was included before.

See `gd++ man debugging`.

# For your code

- `gd++ doc NAME` shows the declaration of any of these, with its comments, e.g. `gd++ doc Gd` or `gd++ doc Async.claim`.
- Your code writes these without a prefix.
- Generated code spells most of them with `gdpp::`, e.g. `gdpp::Async`, the namespace where the runtime defines them. So a name of yours can't hide them there.

gd
  An alias of `UtilityFunctions`, Godot's global functions, at global scope: `gd::print("Hello")`, `gd::push_error("Oops")`, `gd::randi_range(1, 6)`, `gd::lerp(a, b, 0.5)`, `gd::is_instance_valid(obj)`, and all the others of GDScript's global scope. `gd++ doc UtilityFunctions` lists them.

float64_t
  A name for `double`, the C++ type of Godot's `float`, to match `int64_t`.

gdpp::cast<T>(VALUE)
  Converts VALUE to T, whatever the two types are: numbers, enums, `Variant`s, and objects. Upcasts are static. Downcasts are checked, giving null if the class doesn't match. Your code writes it `VALUE as T`, which GD++ rewrites into this, so it keeps its prefix. See `gd++ man cast`.

```gd++
Gd<Node3D> node = scene->instantiate() as Gd<Node3D>;
```

GDPP_ASSERT(TEXT, CONDITION), GDPP_ASSERT_VOID(TEXT, CONDITION), GDPP_ASSERT_VALUE(TEXT, CONDITION) and GDPP_ASSERT_REFERENCE(TEXT, CONDITION)
  What an assertion becomes. Your code writes it `assert`, which GD++ rewrites into one of these. See `gd++ man rewrites`.
  - In debug builds, it checks CONDITION. If it's false, it prints an error and returns from the function, with the type's default value if it returns one.
  - A failed assertion is always undefined behavior, even though the game usually goes on.
  - With `GDPP_TRACING`, the error is also a trace line.
  - Release builds don't evaluate CONDITION.
  - `GDPP_ASSERT_VOID`: for functions that return `void`.
  - `GDPP_ASSERT_VALUE`: for functions that return a value.
  - `GDPP_ASSERT_REFERENCE`: for functions that return a reference. They get one to a default value that lives on.
  - `GDPP_ASSERT`: finds out from the function's signature.
  - `GDPP_ASSERT_DEDUCED(TEXT, CONDITION)`: for functions whose return type C++ deduces from a value they return. It doesn't compile, and says why.

```gd++
assert health >= 0;
assert target != nullptr;
```

gdpp::create<T>(), gdpp::destroy(OBJECT) and gdpp::queue_destroy(NODE)
  What `create T`, `destroy OBJECT` and `queue_destroy NODE` become. All three are thread-safe. See `gd++ man classes`.
  - `create` creates an object of the class or extern `T`, and returns a `Gd<T>`. For a `@pool` class, it takes one from the pool. For a `@scene` class, it's an instance of the class's scene. For an extern with `@factory`, it comes from the class's static method.
  - `destroy` gives an object that a pool made back to its pool, and deletes other objects. It does nothing with null.
  - Both take a `Gd`, or a plain pointer. Neither compiles for a refcounted object, which deletes itself, and `queue_destroy` doesn't compile for an object that isn't a node.
  - On threads other than the main one, `destroy` leaves nodes in the scene tree to the main thread, at the end of the frame.
  - `queue_destroy` returns a node of a `@pool` class to its pool at the end of the frame, on the main thread, unless it was returned or freed before. For other classes, it calls `queue_free()`.
  - For an extern with `@factory`, `destroy` and `queue_destroy` call the object's methods that it names.
  - For a trait, `destroy` and `queue_destroy` do what they do for the object's class, through its `_gdpp_destroy` and `_gdpp_queue_destroy`.

Pool<T>
  The pool of the `@pool` class `T`, which `create` and `destroy` use: a static member of `T`. See `gd++ man pools`.
  - `create` and `destroy` are thread-safe, and take constant time.
  - Its `PoolMode`, `FIXED` or `GROW`, says what it does once it has made as many objects as its size, like the arguments of `@pool`.
  - `reserve` and `clear` do what the methods `pool_reserve` and `pool_clear` of `@factory_pool` do. Like those, they must be called from the main thread.

Gd<T>
  The C++ type of every class, extern and trait: it holds an object of `T`, with the same API for every kind of `T`. See `gd++ man gd`.
  - It's null by default, and tests as a `bool`.
  - `->` calls the object's members: directly for a class or a trait, by name for an extern.
  - `ptr()` gives the object as a plain pointer to its class, or to the base class of a trait or an extern.
  - It converts from the pointers, `Ref`s and `Gd`s that are surely a `T`, and to pointers and `Ref`s of its class and its bases, but not to `Object *`.
  - It keeps a refcounted object alive. For other classes, it costs what a pointer does.
  - `Gd<T>::is_class()`, `is_trait()`, `is_extern()`, `is_refcounted()` and `is_node()` tell the kind of `T` at compile time.
  - `Gd<T>::create_new()` returns a new object, like `create T`.
  - `create()`, `destroy()` and `queue_destroy()` do what `create T`, `destroy` and `queue_destroy` do, with the `Gd` itself: `create()` assigns the new object, and logs an error in debug builds if the `Gd` held one; the others make it null.

Weak<T>
  The C++ type of `Weak[T]`: a reference to an object of the class `T` that holds its ID, and doesn't keep it alive. See `gd++ man weak`.
  - It converts to a `Gd<T>`, and to what a `Gd<T>` converts to.
  - That's null once the object is freed, or for a `@pool` class, once it's returned to its pool.
  - Where a conversion is ambiguous, `ptr()` gives a plain `T *`.
  - In a condition, it's true while the object is there.

Async<T>
  The C++ type of `Async[T]`: a task, e.g. a call of an `@onthread` function. See `gd++ man async`.
  - It refers to an object of a class of tasks. It calls that object's methods directly for the package's own tasks, and by name for other packages' tasks. So it works with the tasks of any package.
  - Copies share the task, like references to the task object in scripts.
  - In a condition, it's true while its task is running or done, and false once it's claimed, or when it's empty.
  - `is_done()`: true when its task has finished, and isn't claimed yet.
  - `claim()`: returns the result of a done task, and claims it, for every copy.
  - `result()`: returns the result too, but keeps it.
  - `wait()`: waits for the task to finish, then returns the result, and keeps it, like `result()`.
  - `cancel()`: asks the task to stop. Always safe: for an empty `Async`, or a task that's done or claimed, it does nothing.
  - Claiming or reading the result before the task is done, or once it's claimed, and calling `claim()`, `result()` or `wait()` on an empty `Async`, prints an error in debug builds. It's undefined behavior in release builds.
  - A default-constructed `Async` is empty. Destroying it does nothing.
  - It's `[[nodiscard]]`: the compiler warns when a call's `Async` is dropped right away.
  - In GD++ code, `is_done TASK`, `claim TASK` and `cancel TASK` call these methods. See `gd++ man rewrites`.

is_cancelled
  Whether the task running on this thread should stop: its `Async` was cancelled, or the game is quitting. Outside of tasks, whether the game is quitting. A rewrite, which calls the runtime's `gdpp::is_cancelled()`. See `gd++ man rewrites` and `gd++ man async`.

Emitted
  What a signal's emit function returns: a `[[nodiscard]]` struct with the `Error` of `emit_signal`, in its field `error`. See `gd++ man signals`.

GDPP_STRING_NAME("name")
  A `StringName`, created the first time the expression runs, and reused after, like the engine's `SNAME`.
  - Creating a `StringName` from a string looks it up in a global table, behind a lock. So this is faster for names used over and over, e.g. in calls by name.
  - In GD++ code, `string_name "update"` is short for it. See `gd++ man rewrites`.

```gd++
node->call(GDPP_STRING_NAME("update"));
```

# For generated code

The code that GD++ generates uses these. Your code rarely needs them:

- `gdpp::info<T>(name, ...)` returns the `PropertyInfo` of a value of type T, for bindings. A `Gd` of a node class gets a node-type hint, so the inspector only accepts nodes of that class.
- `gdpp::add_property_category(class, name)` adds an inspector category, for `@export_category`.
- `gdpp::rpc_config<T>(node, method, ...)` configures an RPC, for `@rpc`. It fails to compile if `T` doesn't extend `Node`.
- `gdpp::call_thread_safe(node, method, args...)` calls a method with `call_thread_safe`, for `@thread_safe`. It fails to compile if the node's class doesn't extend `Node`.
- The class of tasks. See `gd++ man async`.
  - `gdpp::GDPP_ASYNC_CLASS` is the package's class of tasks. The build defines its name as `GDPP_ASYNC_CLASS`, e.g. `FooAsync`.
  - `gdpp::async_class` holds the name as a string.
  - The package's generated registration code registers it.
  - `gdpp::run_task(self, name, job)` starts the call of an `@onthread` function with an object of it.
  - `gdpp::TaskCallable` is the `Callable` that runs the body.
- Quitting. See "When the game quits" in `gd++ man async`.
  - `gdpp::watch_quit` notices when the game starts quitting.
  - `gdpp::await_quit` waits for a task within the package's `quit_timeout`, which the build defines as `GDPP_QUIT_TIMEOUT_USEC`. In games, it ends the game when that runs out.
  - `gdpp::finish_tasks` waits for the package's running tasks before its library is unloaded.
- Unloading, e.g. by hot reload:
  - `gdpp::uninitialize()` prepares the package's library to be unloaded. It calls `gdpp::finish_tasks()`, and removes the hooks that `gdpp::on_unload(unhook)` added.
  - `gdpp::connect_until_unload(object, signal, callable)` connects a signal until then.
  - The package's generated registration code calls `gdpp::uninitialize()`.
- Objects. See `gd++ man gd`.
  - `gdpp::kind::Object`, `RefCounted`, `Extern`, `RefCountedExtern`, `Trait` and `RefCountedTrait` are the kinds of `T` that pick how a `Gd<T>` holds its object.
  - Generated headers declare the kind of each class, extern and trait next to its forward declaration, e.g. `gdpp::kind::Object gdpp_kind(Player *);`, so a `Gd<Player>` works while `Player` is incomplete. Other types get their kind from their definition.
- Traits. See `gd++ man traits`.
  - `gdpp::implement<T, C>()` records that class `C` implements trait `T`. A class's `_gdpp_traits` calls it, for each of its traits.
  - `gdpp::register_traits<C>()` calls `C`'s `_gdpp_traits`, if it has one. The generated registration code calls it for each class.
  - `gdpp::find_trait<T>(object)` gives the object as a `T *`, or null if its class doesn't implement `T`.
  - `gdpp::uninitialize()` forgets the recorded traits.
- Enums. See `gd++ man enums`.
  - `GDPP_ENUM_TAG(TAG, NAME)` makes a class's stand-in type for an enum bind as the enum NAME, e.g. `"Player.Suit"`. `GDPP_BITFIELD_TAG` does the same for a bitfield.
  - `GDPP_BITFIELD(ENUM)` gives the enum class of a bitfield the operators `|`, `&`, `^`, `~`, `|=`, `&=` and `^=`. `&` returns a `Masked<ENUM>`, which converts to `ENUM`, and to `bool` in conditions: true if any flag is set.
- Specializations of godot-cpp's `GetTypeInfo`, `PtrToArg` and `VariantCaster`:
  - for `Gd`, so bindings see a class as itself, and a trait or an extern as its base class, and give null for objects whose class doesn't implement the trait,
  - for `Async`, so bindings see it as the package's class of tasks.

With `GDPP_DEBUGGING`, for `@trace` and `@profile` (see `gd++ man debugging`):

- `gdpp::Trace` prints a call of a `@trace` function: its start, with its arguments, when created, and its end, with its result and time, when destroyed. Its `ret(value)` records the result and returns it.
- `gdpp::Watch` checks the `@trace` variables of a class during a call of one of its functions, and prints their changes.
- `gdpp::Trace` and `gdpp::trace_emit` take `gdpp::via_extern` first for calls and emissions through an extern. Their lines mark them with "extern".
- `gdpp::trace_assert(condition, file, line)` prints a failed assertion, with `GDPP_TRACING`.
- `gdpp::trace_emit(object, signal, args...)` prints an emission of a `@trace` signal.
- `gdpp::trace_lifetime(class, object, created)` prints the creation or destruction of an object of a `@trace` class.
- `gdpp::ProfileStats` holds the timings of one `@profile` function, from all threads, and registers its monitor. `gdpp::Profile` times one call.
- `gdpp::print_profile()` prints the table of timings. `gdpp::profile_monitor(index)` returns a monitor's value.
- `gdpp::describe(object)` and `gdpp::repr(value)` turn objects and values into the text that trace lines show.
- `gdpp::now()` returns the steady clock's time in nanoseconds.
- Arguments and variables are passed as alternating names and values, e.g. `gdpp::Trace t("Player", this, "take_damage", "amount", amount);`.
- Don't use these in your own code. They only exist in sources that GD++ compiles with tracing or profiling on, so the same code fails to compile in other builds.

# Stability

The runtime header belongs to a syntax version: code generated with syntax 1 uses `syntax_1.hpp`. Every syntax version has its own runtime header, so packages on an older syntax keep working.
