Macros: Lua code that writes code

A macro is Lua code that generates GD++ and C++ code where your code invokes it.

Warning: macros are the most advanced feature of GD++. Use them seldom in real code.

- Generated code is harder to read, search and debug than code you write out.
- Plain GD++ is the default. A macro is worth it only when it removes a lot of repetition.
- Prefer templates whenever they do the job: a template is GD++ code with holes, and reads like the code it generates. See `gd++ man templates`.
- Macros are more powerful, but also more advanced. Use one only for what templates can't do:
  - loops and conditions, e.g. a declaration for each entry of a table,
  - checks of the arguments, with errors that explain them,
  - C++ code, e.g. in a function body.
- C++ has its own macros, `#define`. On this page, "macro" means a GD++ macro.

# Macros

A macro is a package-level declaration, like a class, an extern or an enum. Its body is Lua code:

```gd++
// The stat template for each entry, with a check of the maxima.
macro stats(list) {
  for name, max in pairs(list) do
    if type(max) ~= "number" or max <= 0 then
      gd.error_at("list", "the max of " .. name .. " must be a positive number", "e.g. invoke stats({health = 100})")
    end
    gd.invoke("stat", { name, max = max })
  end
}
```

Code invokes it with `invoke name(...)`:

```gd++
class_name Player
extends Node

invoke stats({health = 100, mana = 50, stamina = 80})
```

- Each invocation runs the Lua code, and is replaced by what it generates: here, three stats.
- `stat` is the template in `gd++ man templates`. It holds the code of one stat, as readable GD++.
- The macro adds what the template can't: a loop over the table, and a check of each max.

Facts:

- `macro NAME(params) { Lua }` goes wherever an inline class can go. See `gd++ man files`.
- Every file of the package can invoke it.
- Its name shares the package's namespace with classes, externs, enums and templates. It can't be a GD++ or C++ keyword.
- A macro has no doc comment and no annotations: Godot never sees a macro. Use `//` comments.
- The body is Lua 5.1 code. New to Lua? See `gd++ man lua`.
- Its braces must balance, also in Lua comments and long strings.
- GD++ comments, `//` and `/* */`, work in the body, and so do Lua's `--` comments.
- Lua's errors name the line of the GD++ file.

# Parameters and invoking

Macros take parameters and arguments like templates. See "Parameters" and "Invoking" in `gd++ man templates`. In short:

```gd++
invoke stats({health = 100, mana = 50})         // GD++ data
invoke stats { list = { health = 50 + 50 } }    // a Lua table
invoke spawner { enemy = "Slime", waves = 4, count = function(w) return 3 + w * w end }
```

- Parameters have no types: they're Lua values. A macro checks what it needs, and reports problems with `gd.error_at`. See "Lua: errors" below.
- A default is a Lua expression, evaluated at each invocation.
- GD++ data becomes Lua values: numbers, strings, names and types as strings, lists and dictionaries as tables, and C++ code as Code values.
- A Code value converts to its C++ text with `tostring` or `..`. Emitted as a body, it keeps its own line, so compiler errors point at it.
- `invoke name { ... }` takes a Lua table constructor, for data that needs Lua: computed values, nested tables, functions.

# Macro blocks

`macro { Lua }` runs Lua code right where it is. It's a macro without a name or parameters, invoked where it's declared:

```gd++
class_name Grid
extends Node

/// Whether the cell is open to the north, east, south or west.
macro {
  for _, d in ipairs({ "north", "east", "south", "west" }) do
    gd.var { name = "open_" .. d, type = "bool", init = false, doc = ctx.doc }
  end
}
```

- It works like `macro m() { Lua }` and `invoke m()` in its place, without a package-level name.
- It goes wherever an invocation can go, in declarations and in C++ code. See "Where macros work" below.
- In C++ blocks, it's a statement, and ends with `;`: `macro { gd.text("n++;") };`. It starts the code, or follows `;`, `{` or `}`.
- In one-line C++ expressions, it has no `;`: `var cells: int = macro { gd.text(tostring(8 * 8)) }`.
- It can't declare macros or templates. Declare them at the top level of the file.
- `ctx.macro` is `nil`. Errors name it `macro { ... }`.
- Avoid `macro` as a name in C++ code.

# Where macros work

Declarations:

- At the top level of a file without `class_name` or `extern_name`, a macro may generate classes, externs and enum types.
- In a class or extern, it generates members.
- In a file-level class or extern, i.e. after `class_name` or `extern_name`, it may generate inline classes and externs too.

C++ code:

- In any C++ code, a macro generates C++ code with `gd.text`. This includes function bodies, initial values, and `decl`, `impl` and `@global` blocks.
- `invoke name(...)` and `invoke name { ... }` only invoke a macro if `name` is a macro of the package. Other uses of `invoke` stay C++, e.g. `std::invoke(f)` or `invoke(f, x)`.
- Avoid `invoke` as a name in C++ code.
- GD++'s rewrites, e.g. `emit` and `as`, work in generated C++.

In C++ blocks, e.g. function bodies and `decl` blocks, an invocation is a statement:

- It ends with `;`, which is required.
- The generated C++ replaces it, `;` included. So the macro generates complete statements or declarations, with their own `;`.
- The generated C++ goes on the invocation's line, without comments, so the lines after it keep their numbers.
- Unless it holds preprocessor directives, e.g. `#define` or `#ifdef`: then it keeps its lines, and `#line` directives name each of them as the invocation's line. Lines continued with `\` stay together.

```gd++
decl {
  invoke lookup_table(DAMAGE, [10, 20, 40]);
}

// A C++ array of integers.
macro lookup_table(name, values) {
  gd.text("static constexpr int64_t " .. name .. "[] = {" .. gd.join(values, ", ") .. "};")
}
```

Preprocessor directives, e.g. for code that only debug builds compile:

```gd++
func hurt(n: int) -> void {
  invoke debug_only(code { UtilityFunctions::print("hurt: ", n); });
  health -= n;
}

macro debug_only(body) {
  gd.text("#ifdef DEBUG_ENABLED\n" .. tostring(body) .. "\n#endif")
}
```

In one-line C++ expressions, i.e. initial values and parameters' default values, an invocation is an expression:

- It has no `;`.
- The generated C++ must be an expression on one line. Preprocessor directives are an error.

```gd++
var label: String = invoke describe(health)
```

A doc comment before an invocation goes to `ctx.doc`, so the macro can document what it generates, e.g. `gd.var { ..., doc = ctx.doc }`.

# Templates from macros

`gd.invoke` invokes a template, so a macro can generate readable GD++:

```gd++
// A pool class for each entry of the table.
macro pools(classes) {
  for _, c in ipairs(classes) do
    gd.invoke("pool_of", { T = c[1], size = c.size })
  end
}
```

- Put the code that never changes in a template, and only the loops, conditions and checks in the macro.
- See `gd++ man templates`, and "gd.invoke" below.

# File-level macros

Like `class_name`, `macro_name` makes the whole file one macro:

```gd++
macro_name counter(name, start = 0)

// A counter with a function that bumps it.
gd.var { name = name, type = "int", init = start }
gd.func { name = "bump_" .. name, ret = "void", body = name .. "++;" }
```

- The head comes first in the file. Everything after it, to the end of the file, is the body.
- It works the same as `macro counter(name, start = 0) { ... }`.
- `template_name` does the same for templates. See `gd++ man templates`.

# Inline templates and macros

A macro's body may declare templates and macros:

```gd++
macro inventory(slots) {
  template slot(name, type) {
    var ${name}: ${type}
    signal ${name}_changed
  }
  for _, s in ipairs(slots) do
    gd.invoke("slot", { name = s[1], type = s[2] })
  end
}
```

- They are ordinary package-level declarations, like inline classes in a `class_name` file. Writing them inside only keeps them next to their user.
- They can't use the parameters or holes of the body around them.
- They start a line of the body's top level: `macro NAME(` or `template NAME(`.
- A template's body may declare them too. See `gd++ man templates`.

# Lua

Lua code sees its parameters, Lua's `string`, `table` and `math` libraries, and two tables:

- `gd`: functions that generate code, and helpers.
- `ctx`: where and how the macro was invoked.

For the basics of Lua itself: values, tables, loops, functions and strings, see `gd++ man lua`.

# Lua: emitters

Each emitter takes a table, and adds a declaration where the macro was invoked. Fields that hold C++ take a string, a Code value, or a function that writes the C++ with `gd.text`.

gd.class { name, extends, doc, annotations, body }
  A class. `body` is a function, whose emitters add the class's members.
```lua
gd.class { name = "Sword", extends = "Item", annotations = { { "icon", "res://sword.svg" } }, body = function()
  gd.func { name = "_damage", annotations = { "override" }, ret = "int", body = "return 10;" }
end }
```

gd.extern { name, extends, doc, annotations, body }
  An extern, like `gd.class`.

gd.enum { name, extends, doc, annotations, values }
  An enum type. Each value is a name, `{ name, value }`, or `{ name = ..., value = ..., doc = ... }`. A value is an integer, or a string with an expression.
```lua
gd.enum { name = "Suit", values = { "HEARTS", { "SPADES", 10 }, { name = "ALL", value = "HEARTS | SPADES" } } }
```

gd.enum { name, value, doc }
  An integer constant, in a class: `gd.enum { name = "MAX_SPEED", value = 300 }`.

gd.func { name, params, ret, body, doc, annotations }
  A function. Without `body`, e.g. in an extern, it has none.
```lua
gd.func { name = "heal", params = { "amount: int = 1" }, ret = "void", body = "health += amount;" }
```

gd.var { name, type, init, decl, get, set, set_param, doc, annotations }
  A variable with `init`, or a property with `decl`, `get` and `set`. `set_param` names the setter's parameter, `value` by default.
```lua
gd.var { name = "speed", type = "float", init = 5.0, annotations = { "export" } }
```

gd.signal { name, params, doc, annotations }
  A signal: `gd.signal { name = "died", params = { "by: Node" } }`.

gd.ctor { body, annotations } and gd.dtor { body, annotations }
  A `ctor` or `dtor` block.

gd.on { name, param, param_type, body, annotations }
  An `on` block: `gd.on { name = "process", param = "delta", param_type = "float", body = "tick(delta);" }`.

gd.decl { body, annotations }, gd.impl { ... } and gd.decl_impl { ... }
  A `decl`, `impl` or `decl impl` block. `annotations = { "global" }` makes it `@global`.
```lua
gd.impl { body = function()
  for _, s in ipairs(states) do
    gd.text("static void enter_" .. gd.snake(s) .. "(This *self) {}\n")
  end
end }
```

gd.import(type) and gd.noimport(type)
  An `import` or `noimport`: `gd.import("Node3D")`.

gd.invoke(name, args)
  Invokes a macro or template, like the `invoke` keyword, and adds what it generates where the macro was invoked. `args` binds like `invoke name { ... }`: its list entries are the positional arguments, its string keys the named ones. Lua values pass as they are, functions too.
  - In declarations, the output is declarations.
  - In C++ code, e.g. when the calling macro was invoked in a function body, the invoked macro's `gd.text` is C++, and joins the caller's.
  - Templates generate declarations, so `gd.invoke` can't invoke them in C++ code.
  - Each call nests one level deeper, so a macro that invokes itself forever stops with an error. See "The sandbox".
```lua
gd.invoke("pool_of", { T = "Bullet", size = 128 })
gd.invoke("label", { "score", format = function(s) return gd.title(s) .. ":" end })
```

# Lua: plain text (advanced)

`gd.text(s)` emits plain text, which GD++ parses later. Anything can be emitted, but nothing checks it until then, so it's easy to get wrong. Prefer emitters, which check as you build, and templates, which are readable GD++.

- In declarations, the text is GD++. When the macro (or a `body` function) returns, each run of text emitted in a row is joined and parsed.
- A run may be split anywhere: `gd.text("class " .. name .. " {")`, then the members, then `gd.text("}")`. But each run must parse on its own.
- In C++ code, and in the functions of C++ fields, the text is C++.
- The text may invoke macros, which expand like any other invocation.
- If a run doesn't parse, the error points at the invocation, and its hint shows the line that the macro emitted.

```lua
gd.text("class " .. name .. " {\n  extends RefCounted\n")
for _, f in ipairs(flags) do
  gd.text("  var " .. f .. ": bool = false\n")
end
gd.text("}\n")
```

# Lua: field formats

- `name`: a name, e.g. `"health"`.
- `type`, `ret` and `extends`: a type, written like in GD++, e.g. `"Array[int]"`.
- `params`: a list of parameters, written like in GD++, e.g. `{ "x: float", "y: float = 0.0" }`, or as tables: `{ name = "x", type = "float", default = "0.0" }`.
- `annotations`: a list of names, or lists of a name and its arguments: `{ "export", { "export_range", 0, 100, 1 } }`. Strings become GD++ strings. Numbers, booleans and Code values stay as written.
- `doc`: the doc comment's text.

# Lua: case conversion

Each takes a name in any case, and splits it into words at `_`, `-`, spaces and changes of case.

```lua
gd.pascal("max_health")       -- MaxHealth
gd.camel("max_health")        -- maxHealth
gd.snake("MaxHealth")         -- max_health
gd.upper_snake("maxHealth")   -- MAX_HEALTH
gd.kebab("MaxHealth")         -- max-health
gd.title("max_health")        -- Max Health, like the inspector shows names
```

# Lua: quoting

```lua
gd.quote('say "hi"')          -- "say \"hi\"": a C++ string literal
gd.string_name("ready")       -- string_name "ready": a StringName in C++ code
gd.gdquote("res://a.png")     -- "res://a.png": a GD++ string, e.g. for annotation arguments
```

# Lua: strings

```lua
gd.split("a,b", ",")          -- { "a", "b" }
gd.join({ "a", "b" }, ", ")   -- a, b
gd.trim("  x ")               -- x
gd.starts_with("abc", "ab")   -- true
gd.ends_with("abc", "bc")     -- true
gd.replace("a.b", ".", "::")  -- a::b: plain text, not a Lua pattern
gd.lines("a\nb")              -- { "a", "b" }
gd.indent("a\nb", 2)          -- each non-empty line, with 2 spaces before it
```

# Lua: tables

Tables iterate in sorted key order: numbers, then strings, then booleans. So the same input always generates the same code. `pairs` does too.

```lua
gd.keys({ b = 2, a = 1 })                   -- { "a", "b" }
gd.values({ b = 2, a = 1 })                 -- { 1, 2 }
for k, v in gd.sorted_pairs(t) do end      -- like pairs
gd.map({ 1, 2 }, function(v, k) return v * 2 end)        -- { 2, 4 }
gd.filter({ 1, 2, 3 }, function(v, k) return v > 1 end)  -- { 2, 3 }
gd.contains({ "a", "b" }, "b")              -- true
gd.copy(t)                                  -- a deep copy
gd.merge({ a = 1 }, { a = 2, b = 3 })       -- { a = 2, b = 3 }: the second wins
gd.range(3)                                 -- { 1, 2, 3 }
gd.range(2, 4)                              -- { 2, 3, 4 }
```

# Lua: values

```lua
gd.code("a + b")              -- a Code value
gd.is_code(v)                 -- whether v is a Code value
gd.type(v)                    -- "code", or Lua's type(v), e.g. "string"
gd.is_ident("max_hp")         -- true: whether it's a valid name
gd.ident(s)                   -- s, or an error at the invocation if it isn't a valid name
```

# Lua: names and lookup

```lua
gd.unique("tmp")              -- _gdpp_tmp_1, then _gdpp_tmp_2: fresh names for helpers
gd.has_macro("stat")          -- whether the package has a macro of that name
gd.has_template("pool_of")    -- the same, for templates
```

# Lua: errors

A macro checks its arguments itself, and reports problems as GD++ errors:

gd.error(message, hint)
  An error at the invocation. The hint is optional.

gd.error_at(where, message, hint)
  An error at `where`: the argument of a parameter, named by a string, or a Code value. A parameter left to its default puts it at the invocation.

For a macro that another one invokes with `gd.invoke`, "the invocation" is the line of Lua code that calls `gd.invoke`, in its file. Its arguments are Lua values, so `gd.error_at` puts errors about them there too.

For an invocation in a template, "the invocation" is its place in the template, in its file. `gd.error_at` puts errors about its arguments there too. For an invocation in C++ code that a macro generated, it's the outer invocation, in your code.

```lua
if type(max) ~= "number" or max < 0 then
  gd.error_at("max", "a stat's max must be a number of 0 or more", "e.g. invoke stat(health, max = 100)")
end
```

Messages become sentences: capitalized, ending with a period.

# Lua: ctx

```
FIELD            VALUE
ctx.scope        "file", "class", "extern" or "cpp": where the invocation is
ctx.class        the class or extern around the invocation, if any
ctx.doc          the invocation's doc comment, if any
ctx.file         the GD++ file's name
ctx.line         the invocation's line
ctx.macro        the macro's name, or nil in a macro block
ctx.package      the package's settings, see below
```

`ctx.package` holds:

```
FIELD                VALUE
ctx.package.id       the package's id: the name of its directory, e.g. "my_game"
ctx.package.prefix   the prefix of the classes that GD++ adds to the package: prefix in gd++pkg.toml, or the id in PascalCase, e.g. "MyGame"
ctx.package.path     the res:// path of the package's directory, e.g. "res://addons/my_game", or "res://" for a package at the project's root
ctx.package.std      the package's C++ standard: std in gd++pkg.toml, e.g. "c++20"
```

- They are strings.
- Outside a package, e.g. `gd++ trans` on a file that isn't in one, `ctx.package` is an empty table: its fields are `nil`.
- `path` doesn't end with `/`, except `"res://"`.
- E.g. a macro can name a class after the package: `ctx.package.prefix .. "Stats"`.
- See `gd++ man packages` for the settings.

# The sandbox

Lua code can only generate code:

- No I/O, and no loading other code: no `io`, `os`, `require`, `dofile`, `load` or `print`.
- Nothing random: no `math.random`. The same input always generates the same code.
- An invocation may run for 20 seconds at most. `gd++ build --macro-timeout SECONDS` and `gd++ trans --macro-timeout SECONDS` change the limit.
- Invocations nest at most 64 levels deep, e.g. a macro whose output invokes a macro, or a macro that calls `gd.invoke`. Each counts as one level. A package changes the limit with `macro_depth` in `gd++pkg.toml`, see `gd++ man packages`.

# Errors

- A Lua error points at the Lua line.
- An error in generated code points at the invocation.
- A compiler error in C++ that a macro generates points at the invocation's line. In C++ from a template, it points into the template. See `gd++ man templates`.
- Run `gd++ trans FILE --macro` to see the GD++ that a file expands to, and `gd++ trans FILE` for the C++ it generates.

Every error that a macro or template causes ends with its macro call stack: the invocations that led to it, innermost first.

```
player.gd++:17:21: Expected ":", "=" or "{" after the variable name, but found name "float".
 17 |   var ${name}_twice float
    |                     ^^^^^
Hint: Types are written after a colon: "var speed_twice: float".
Macro call stack:
  template broken, invoked with gd.invoke at player.gd++:13
  macro middle, invoked with gd.invoke at player.gd++:8
  macro outer, invoked at player.gd++:4
```

- Each line names a macro or template, and where it was invoked: with `invoke` in your code, with `gd.invoke` in Lua code, or in generated code, i.e. in another invocation's output.
- The last line is the invocation in your code.
- A long stack, e.g. of a macro that invokes itself forever, shows its first and last five lines.
- For an error that GD++ finds in the generated code after expanding it, e.g. a type that doesn't exist, the stack only names the invocation in your code.

# Examples

A state machine: an enum of the states, and a switch that runs the code of the current one.

```gd++
invoke state_machine(Idle, {
  Idle = code { if (Input::get_singleton()->is_action_pressed("jump")) go(State::JUMP); },
  Jump = code { if (is_on_floor()) go(State::IDLE); },
})

macro state_machine(initial, states) {
  local names = gd.keys(states)
  gd.enum { name = "State", values = gd.map(names, gd.upper_snake) }
  gd.signal { name = "state_changed", params = { "to: State" } }
  gd.var { name = "state", type = "State", init = "State::" .. gd.upper_snake(initial) }
  gd.func { name = "go", params = { "to: State" }, ret = "void", body = "state = to; emit state_changed(to);" }
  gd.on { name = "physics_process", param = "delta", param_type = "float", body = function()
    gd.text("switch (state) {\n")
    for _, name in ipairs(names) do
      gd.text("case State::" .. gd.upper_snake(name) .. ": {" .. tostring(states[name]) .. "} break;\n")
    end
    gd.text("}")
  end }
}
```

A data table: a class per item, an enum of their kinds, and a factory.

```gd++
invoke items([
  {name = Sword, damage = 10, icon = "res://icons/sword.svg"},
  {name = Bow, damage = 6, icon = "res://icons/bow.svg"},
])

macro items(list) {
  local kinds = {}
  for _, item in ipairs(list) do
    table.insert(kinds, gd.upper_snake(item.name))
    gd.class { name = item.name, extends = "Item", annotations = { { "icon", item.icon } }, body = function()
      gd.func { name = "_damage", annotations = { "override" }, ret = "int", body = "return " .. item.damage .. ";" }
    end }
  end
  gd.enum { name = "ItemKind", values = kinds }
}
```

Logging in C++ code, with the class's name:

```gd++
func hurt(n: int) -> void {
  health -= n;
  invoke log("hurt", [n, health]);
}

macro log(event, values = {}) {
  local args = { gd.quote("[" .. ctx.class .. "] " .. event .. ":") }
  for i, v in ipairs(values) do
    table.insert(args, gd.quote((i > 1 and ", " or " ") .. v .. "="))
    table.insert(args, v)
  end
  gd.text("UtilityFunctions::print(" .. gd.join(args, ", ") .. ");")
}
```

Values computed by Lua functions:

```gd++
invoke spawner { enemy = "Slime", waves = 4, count = function(w) return 3 + w * w end }

macro spawner(enemy, waves, count) {
  if type(count) ~= "function" then
    gd.error_at("count", "count must be a function of the wave number")
  end
  for w = 1, waves do
    gd.enum { name = "WAVE_" .. w .. "_SIZE", value = count(w) }
  end
}
```
