Files: the layout of a GD++ file

A GD++ file declares any number of classes, externs, enums, macros and templates. Every other GD++ file of the package can use them. This page covers the layout of a file.

# File-level and inline declarations

Each kind of declaration comes in two forms:

```gd++
class_name Player        // file-level: the rest of the file is the class
class Enemy { ... }      // inline: the braces hold the class

extern_name Terrain      // a file-level extern
extern Road { ... }      // an inline extern

enum_name Suit           // a file-level enum: the rest of the file is its values
enum Rank { ... }        // an inline enum

macro_name stat(name)    // a file-level macro: the rest of the file is its Lua code
macro log(event) { ... } // an inline macro

macro_library            // a file-level macro library: the rest of the file is its Lua code
macro { ... }            // an inline macro library

template_name pool(T)    // a file-level template: the rest of the file is its GD++ code
template slot(n) { ... } // an inline template

annotation save          // a user annotation, @@save, for macros
```

- Both forms work the same.
- The file-level form saves a level of braces and indentation, like in GDScript, where a file is a class.
- A file has at most one file-level declaration. It comes first, before anything but comments.

# A file-level class

```gd++
class_name Player
extends CharacterBody3D

var speed: float = 5.0

func jump() -> void {
  // ...
}
```

- `class_name NAME` starts the file.
- `extends`, if any, comes right after it, even on the same line: `class_name Player extends CharacterBody3D`.
- Everything after it, to the end of the file, is a member of the class.
- Exception: inline classes and externs can appear between the members.

```gd++
class_name Player
extends Node

var a: int          // a member of Player

class Weapon {      // an inline class
  var damage: int
}

var b: int          // still a member of Player
```

This is the usual layout: one main class per file, with small helper classes next to it.

# A file-level extern

```gd++
extern_name Terrain
extends Node3D

func height_at(x: float, z: float) -> float
signal changed
```

- Like `class_name`, but for an extern: the rest of the file declares its members.
- Inline classes and externs can appear between them.
- See `gd++ man externs`.

# A file-level enum

```gd++
enum_name Suit
DIAMONDS
CLUBS
SPADES = 10
HEARTS
```

- `enum_name NAME` makes the whole file an enum.
- Everything after it, and after an optional `extends Base` line, is a value of the enum.
- Nothing else can follow, not even inline classes.
- Rarely used: it exists for consistency.
- The file declares no classes, so it adds nothing to Godot by itself. Every GD++ file of the package can use the enum.
- See `gd++ man enums`.

# A file without a file-level declaration

A file can have only inline declarations:

```gd++
class Enemy {
  extends Node3D
  var health: int
}

class Boss {
  extends Enemy
}

enum Difficulty { EASY NORMAL HARD }

extern Terrain {
  extends Node3D
}
```

Its top level can only hold inline classes, externs, enums, macros, templates, annotation declarations, and invocations of macros and templates. Anything else, e.g. a `func`, a `var`, an integer constant or a `decl` block, belongs in a class:

```out
[×] res://enemies.gd++:12:1: This func is outside of any class.
     12 | func spawn() -> void {}
        | ^^^^
    Hint: Add "class_name Name" at the top of the file to make the whole file a class, or move this into an inline class: "class Name { ... }".
```

# No nesting

- Classes and externs can't be nested: an inline class can't be inside another class or extern.
- Enums can be declared inside a class, but they are global types anyway. See `gd++ man enums`.

# Macros and templates

- Inline macros and templates can go anywhere an inline class can, also between the members of a file-level class.
- Macro libraries, `macro { ... }`, can go there too.
- With `macro_name`, `template_name` or `macro_library`, the rest of the file is the body. Like after `enum_name`, nothing else can follow.
- Their bodies may declare more macros and templates. Those are package-level declarations too.
- `annotation NAME` declarations can go there too. See "User annotations" in `gd++ man annotations`.
- See `gd++ man templates` and `gd++ man macros`. Prefer templates whenever they do the job: macros are more powerful, but also more advanced.

# Order

- The order of declarations doesn't matter.
- A class can extend a class declared further down, and use types declared anywhere in the package.
- GD++ generates files in the order of the declarations, and registers classes after their base classes.

# Names

- Every class, extern, enum, macro and template has a name, unique in the package.
  - Two GD++ files can't declare the same name.
  - A name can't be declared twice in one file.
- Names must differ from Godot's classes and from godot-cpp's names, e.g. `Node` or `TypedArray`.
- A declaration's name is the name of its generated files, e.g. `Player.h` and `Player.cpp`.
- A class's name is also its name in Godot.
- It doesn't need to match the file's name: `player.gd++` can declare `Player`, or anything else.

# One file, many outputs

Each declaration generates its own files, as if it were alone in its file:

- a class: `NAME.h` and `NAME.cpp`,
- an extern or an enum: `NAME.h`.

The declarations of one file see each other just like they see those of other files. See `gd++ man generated`.

# Example: a typical file

```gd++
/// A card game's table.
class_name Table
extends Node2D

enum Suit { DIAMONDS CLUBS SPADES HEARTS }

signal card_played(suit: Suit, rank: int)

var cards: Array[Card]

func play(card: Card) -> void {
  cards.erase(card);
  emit card_played(card->get_suit(), card->get_rank());
}

/// A playing card.
class Card {
  extends Resource
  @export var suit: Suit
  @export var rank: int
}
```
