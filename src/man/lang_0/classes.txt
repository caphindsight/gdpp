Classes: declaring Godot classes

A GD++ class is a Godot class, like `Node3D` or `Resource`: once built, it shows up in the editor's "Create New Node" dialog (or in the list of resources), GDScript can use it, and scripts can extend it. This page explains how to declare classes, and what GD++ makes of them.

# Declaring a class

A file-level class takes the rest of the file:

```gd++
class_name Player
extends CharacterBody3D

var speed: float = 5.0
```

An inline class takes a pair of braces, with `extends` first inside them:

```gd++
class Bullet {
  extends Area3D
  var damage: int = 10
}
```

Both are the same kind of class. A file can have one file-level class and any number of inline classes. See `gd++ man files`.

# Base classes

`extends` names the base class. It can be:

- a Godot class from the package's API spec, e.g. `Node`, `Node3D`, `Resource` or `Object`,
- another GD++ class of the same package, from any file.

Without `extends`, the class extends `RefCounted`, like in GDScript.

```gd++
class_name Enemy
extends CharacterBody3D

class Boss {
  extends Enemy        // another GD++ class
}

class Stats {}          // extends RefCounted
```

A class can't extend an extern, an enum, a C++ class of the package, or itself through its bases:

```out
[×] res://a.gd++:2:9: A can't extend Terrain, which is an extern.
     2 | extends Terrain
       |         ^^^^^^^
    Hint: Extend the extern's base class instead.
```

# Objects and references

Godot has two kinds of classes, and GD++ uses them differently in C++:

- Refcounted classes: `RefCounted` and every class that extends it, e.g. `Resource`, `Texture2D` or the class `Stats` above. Godot deletes their objects when the last reference goes away. In C++, GD++ uses them through references, e.g. `Ref<Stats>`.
- Other classes: `Object` and every class that extends it but not `RefCounted`, e.g. `Node` and all nodes. You delete their objects yourself, e.g. with `destroy` or `queue_destroy`. In C++, GD++ uses them through pointers, e.g. `Player *`.

A GD++ class is refcounted if its base is. See `gd++ man types`.

In C++ code, `create` creates an object of any class, yours or Godot's, and `destroy` deletes it:

```gd++
Bullet *bullet = create Bullet;            // an object
add_child(bullet);
destroy bullet;                            // deletes it

Ref<Stats> stats = create Stats;           // a refcounted object, deleted with its last reference
auto mesh = create ArrayMesh;              // a Ref<ArrayMesh>
```

`create T` gives what GD++ uses for `T`: a pointer, a `Ref` for refcounted classes, or an `Ext` for externs (see `gd++ man externs`). For a `@pool` class, `create` takes an object from the class's pool, and `destroy` gives it back (see `gd++ man pools`). `destroy` does nothing with null, and doesn't compile for references, since refcounted objects delete themselves. `destroy` works on any thread: on threads other than the main one, it leaves nodes that are in the scene tree to the main thread, which destroys them at the end of the frame, since only the main thread may change the tree.

`queue_destroy NODE` is like Godot's `queue_free()`: it destroys a node at the end of the frame, e.g. to remove a collision object during a physics callback, which Godot doesn't allow. Unlike `queue_free()`, it works on everything that `destroy` does: a `@pool` class's object goes back to its pool. It only works on nodes, and does nothing if the node is freed, or returned to its pool, before the end of the frame, even if the pool has reused it since, so queueing the same node twice is fine. It works on any thread. Both are rewrites, of `gdpp::create<T>()` and `gdpp::destroy(OBJECT)`, see `gd++ man rewrites`. godot-cpp's `memnew` and `memdelete` work too, but they skip pools.

In GDScript, use them like built-in classes: `Bullet.new()`, `var s: Stats`, `extends Player`, and so on.

# @tool

Like in GDScript, the code of a class runs in the editor only if the class has `@tool`:

```gd++
@tool
class_name Gizmo
extends Node3D

func _process(delta: float) -> void {
  rotate_y(delta);          // Spins in the editor too.
}
```

Without `@tool`, a class is registered with Godot as a runtime class. In the editor, Godot creates placeholders for its objects: they store the property values that you set in the inspector, but run none of the class's code.

So a runtime class can't break the editor, e.g. by moving nodes around in a scene you're editing. Games run from the editor and exported games run all code. Inline classes need their own `@tool`: it's not inherited from the file-level class, nor from the base class.

`gd++ ls` shows `@tool` classes with the tag `@tool`.

# @game_only

Placeholders only stop the code that Godot calls. Code that already runs in the editor, e.g. that of a `@tool` class or of a C++ tool class, can still create an object of a runtime class with `create`, or call its static functions, and then the runtime class's code runs. `@game_only` prevents this: the class's code only ever runs in the game.

```gd++
@game_only
class_name Spawner
extends Node3D
```

A `@game_only` class is a runtime class. In debug builds, which the editor loads, every function that GD++ generates for it starts with a check: in the editor, the function returns right away, with a default value, and an `@onthread` function returns an empty `Async`, without starting a task. This covers the class's functions, constructor, destructor, getters, setters, signal emit functions, and the helpers that GD++ adds, e.g. for enums, default values and RPCs. Your own `decl` and `impl` code isn't checked. Release builds have no checks.

`@game_only` can't be used with `@tool`. Like `@tool`, it's not inherited.

`@game_only` also works on single functions and variables, e.g. to keep a few functions of a `@tool` class out of the editor:

```gd++
@tool
class_name Spawner
extends Node3D

func _process(delta: float) -> void {
  rotate_y(delta);          // Spins in the editor too.
}

@game_only
func spawn() -> void {
  ...                       // Only spawns in the game.
}

@game_only
var wave: int
```

The function gets the same check, and so do its helpers: its enum wrapper, default value functions and RPC helper, and for `@virtual`, `@deferred` and `@onthread`, the functions that GD++ adds for them. A variable's getter and setter get it. The variable's initial value is still assigned in the editor, and C++ code that uses the variable directly isn't checked. A variable with `@game_only` can't have an export annotation, since the editor would read and save the default value. In a `@game_only` class, every function and variable is already `@game_only`.

# @icon

```gd++
@icon("res://icons/player.svg")
class_name Player
extends CharacterBody3D
```

`@icon` sets the class's icon in the editor, e.g. in the scene tree and the "Create New Node" dialog. It takes one argument, a string with the path of the icon, usually an SVG file. The path must start with `res://`, relative to the project, or `pkg://`, relative to the package:

```gd++
@icon("pkg://icons/bullet.svg")
class Bullet {
  extends Area3D
}
```

GD++ writes the icons into the package's `.gdextension` file. `gd++ ls` shows a missing icon file in red.

# @scene

A node's children, e.g. its meshes and collision shapes, and their settings usually live in a scene. With `@scene`, `create` instantiates the class's scene:

```gd++
@scene("pkg://bullet.tscn")
class_name Bullet
extends Area3D
```

```gd++
Bullet *bullet = create Bullet;    // the root of bullet.tscn, with its children
add_child(bullet);
```

The path starts with `res://`, relative to the project, or `pkg://`, relative to the package. The first `create` loads the scene, and keeps it until the library is unloaded, so later ones only instantiate it. The scene's root must be a `Bullet`: if it isn't, or the scene fails to load, `create` prints an error and returns null. `create` is thread-safe, so worker threads may create scenes too, though only the main thread may add them to the tree.

`@scene` works on classes that extend `Node`, since a scene's root is a node. Only `create` uses the scene: `memnew(Bullet)`, `Bullet.new()` in GDScript and scenes that hold a `Bullet` give the node alone. A class that extends a `@scene` class doesn't use its scene, unless it has a `@scene` of its own. With `@pool`, the pool instantiates the scene for each new object, and reuses objects without it. Classes without `@scene` pay nothing for it: `create` decides at compile time.

# @trace and @profile

```gd++
@trace("loot")
@profile
class_name Chest
extends Node3D
```

These are for debugging. `@trace` on a class traces all its functions (except `_process` and `_physics_process`, which run every frame, and have their own groups `process` and `physics_process`), variables and signals, and prints each creation and destruction of its objects. `@profile` times all its functions, and the getters and setters of its properties. They only generate code in builds that turn on one of their groups: here, `--trace loot`, `--trace Chest` or `--trace all` for `@trace`, and `--profile Chest` or `--profile all` for `@profile`. Like `@tool`, they're not inherited. See `gd++ man debugging`.

# Annotations and doc comments

A class can have `@tool` or `@game_only`, `@icon`, `@pool`, `@scene`, `@trace` and `@profile`, in any order, and a doc comment, before `class_name` or `class`:

```gd++
/// The player's character.
///
/// It runs, jumps and collects coins.
@tool
@icon("res://icons/player.svg")
class_name Player
extends CharacterBody3D
```

The first paragraph of a class's doc comment is its brief description, and the rest is its full description. See `gd++ man docs`.

# Members

A class body holds members, in any order:

```
func       functions                      gd++ man functions
var        variables and properties       gd++ man variables
signal     signals                        gd++ man signals
enum       enums and integer constants    gd++ man enums
ctor       the constructor                gd++ man lifecycle
dtor       the destructor                 gd++ man lifecycle
notif      notification handlers          gd++ man lifecycle
decl, impl plain C++                      gd++ man code
import     force an include               gd++ man includes
noimport   prevent an include             gd++ man includes
```

Functions, variables, signals and constants share one namespace, since they all become C++ members of one class:

- A `var x` also declares its getter `get_x` and its setter `set_x`.
- A `signal s` also declares a C++ method `s`, which emits it.
- A `@virtual func _f` also declares `f`, which scripts call. See `gd++ man functions`.

So `var x` and `func get_x()` can't be in the same class:

```out
[×] res://player.gd++:8:1: The name "get_x" is already used by another member.
     8 | func get_x() -> int {
       | ^^^^
    Hint: Members share one namespace. A var x also declares get_x and set_x, a signal declares its emit function, and a @virtual func _x declares x.
```

Names that start with `_gdpp_` are reserved for the code that GD++ generates.

# This

In the C++ code of a class, `This` is the name of the class, like `Self` in Rust:

```gd++
func clone() -> Player {
  This *copy = create This;
  copy->speed = speed;
  return copy;
}
```

It's a macro that GD++ defines around the class's code. See `gd++ man code`.

# What GD++ generates

For a class `Player`, GD++ generates `Player.h` and `Player.cpp`, in namespace `godot`:

```cpp
class Player : public CharacterBody3D {
  GDCLASS(Player, CharacterBody3D)
  ...
protected:
  static void _bind_methods();
};
```

The class has all the members, and `_bind_methods`, which binds them to Godot. The build registers the class when Godot loads the library, after its base class if that's a class of the package too. See `gd++ man generated`.

# Examples

A resource type, for data files edited in the inspector:

```gd++
/// An item that the player can pick up.
@icon("res://icons/item.svg")
class_name Item
extends Resource

@export var title: String
@export var price: int
@export var icon: Texture2D
```

A node with a helper class:

```gd++
class_name Spawner
extends Node3D

@export var scene: PackedScene

func spawn() -> Node3D {
  Node3D *node = scene->instantiate() as Node3D *;
  add_child(node);
  return node;
}

class SpawnInfo {
  var count: int
  var position: Vector3
}
```
