Classes: declaring Godot classes

A GD++ class is a Godot class, like `Node3D` or `Resource`. Once built:

- it shows up in the editor's "Create New Node" dialog, or in the list of resources,
- GDScript can use it,
- scripts can extend it.

# Declaring a class

A file-level class takes the rest of the file:

```gd++
class_name Player
extends CharacterBody3D

var speed: float = 5.0
```

An inline class takes a pair of braces, with `extends` first inside them:

```gd++
class Bullet {
  extends Area3D
  var damage: int = 10
}
```

- Both are the same kind of class.
- A file has at most one file-level class, and any number of inline classes.
- See `gd++ man files`.

# Base classes

`extends` names the base class:

- a Godot class from the package's API spec, e.g. `Node`, `Node3D`, `Resource` or `Object`,
- another GD++ class of the same package, from any file.
- Without `extends`, the class extends `RefCounted`, like in GDScript.

```gd++
class_name Enemy
extends CharacterBody3D

class Boss {
  extends Enemy        // another GD++ class
}

class Stats {}          // extends RefCounted
```

A class can't extend:

- an extern,
- an enum,
- a C++ class of the package that isn't marked `[ptr]` or `[ref]` (see `gd++ man cpp-classes`),
- itself, through its bases.

```out
[×] res://a.gd++:2:9: A can't extend Terrain, which is an extern.
     2 | extends Terrain
       |         ^^^^^^^
    Hint: Extend the extern's base class instead.
```

# Traits

A class has one base class, but it can implement any number of traits. `implements` comes after `extends`, or in its place:

```gd++
class_name Crate
extends RigidBody3D
implements Damageable, Saveable
implements Named
```

- Commas and repeated `implements` mix freely.
- The class defines the traits' functions, except those with a default.
- Code can then use a `Crate` as a `Damageable`, and cast any object to one with `as`.
- See `gd++ man traits`.

# Objects and references

Godot has two kinds of classes:

- Refcounted: `RefCounted` and every class that extends it, e.g. `Resource`, `Texture2D` or `Stats` above.
  - Godot deletes the object when its last reference goes away.
- Not refcounted: `Object` and every class that extends it but not `RefCounted`, e.g. `Node` and all nodes.
  - You delete the object yourself, e.g. with `destroy` or `queue_destroy`.
- A GD++ class is refcounted if its base is.
- In C++, GD++ holds both kinds as a `Gd<T>`, e.g. `Gd<Stats>` or `Gd<Player>`. For a refcounted class, it's a reference that keeps the object alive. For others, it's a plain pointer. See `gd++ man gd`.

In C++ code, `create` creates an object of any class, yours or Godot's, and `destroy` deletes it:

```gd++
Gd<Bullet> bullet = create Bullet;       // an object
add_child(bullet);
destroy bullet;                          // deletes it

Gd<Stats> stats = create Stats;          // a refcounted object, deleted with its last reference
auto mesh = create ArrayMesh;            // a Gd<ArrayMesh>
```

`create T`:

- Gives a `Gd<T>`, for a class or an extern (see `gd++ man externs`).
- `Gd<Bullet>::create_new()` is the same as `create Bullet`.
- `bullet.create();` does the same for a `Gd<Bullet> bullet`, and checks in debug builds that it held no object. See `gd++ man gd`.
- For a `@pool` class, takes an object from the class's pool. See `gd++ man pools`.

`destroy OBJECT`:

- For a `@pool` class, gives the object back to its pool.
- Does nothing with null.
- Doesn't compile for refcounted objects, since they delete themselves.
- Never `destroy` an object twice, except one that a pool made. The second time, the object is already deleted: it's a bug, like deleting it twice in C++. When unsure, use `queue_destroy`.
- Works on any thread. On threads other than the main one, nodes in the scene tree are left to the main thread, which destroys them at the end of the frame, since only the main thread may change the tree.

`queue_destroy NODE`:

- Destroys a node at the end of the frame, like Godot's `queue_free()`. E.g. to remove a collision object during a physics callback, which Godot doesn't allow.
- For a `@pool` class, returns the node to its pool then. It does nothing if the node was returned or freed before, even if the pool has reused it since.
- For other classes, it's simply `queue_free()`, at no extra cost.
- So prefer it to `queue_free()`: it keeps working if the class gets a `@pool` later.
- Only works on nodes: for other objects, it doesn't compile.
- Works on any thread.
- Queueing the same node twice is fine.

`bullet.destroy();` and `bullet.queue_destroy();` do the same for a `Gd<Bullet> bullet`, and then make it null.

All three are rewrites: of `gdpp::create<T>()`, `gdpp::destroy(OBJECT)` and `gdpp::queue_destroy(NODE)`. See `gd++ man rewrites`. godot-cpp's `memnew` and `memdelete` work too, but skip pools.

In GDScript, use GD++ classes like built-in classes: `var s: Stats`, `extends Player`, and so on.

# In scripts

Scripts can't write `create`, `destroy` and `queue_destroy`. `@factory` gives the class methods that do the same:

```gd++
@factory
class_name Bullet
extends Area3D
```

```gdscript
var bullet := Bullet.create()  # create Bullet
if bullet:
    add_child(bullet)

bullet.destroy()               # destroy bullet
bullet.queue_destroy()         # queue_destroy bullet
```

- `create()`: a static method. Not for `@abstract` classes. It returns `null` if a `"fixed"` pool is full, or a scene fails to load, so check it for `@pool` and `@scene` classes.
- `destroy()`: not for refcounted classes.
- `queue_destroy()`: only for classes that extend `Node`.
- Without `@factory`, the class has none of these methods.
- Prefer them to `new()`, `free()` and `queue_free()`: they keep working if the class gets `@pool` or `@scene` later. `new()` creates the object alone, outside the pool and without the scene.
- They make and take objects of the GD++ class itself. Called on a script that extends the class, `create()` still gives an object without the script.
- GD++ code can call them too, e.g. `Bullet::create()`, but `create Bullet` is shorter.
- A class can't have a member named like them.

Other names: `@factory` takes up to three strings, for `create`, `destroy` and `queue_destroy`, in this order. An empty string `""`, or a missing name at the end, leaves that method out:

```gd++
@factory("spawn", "despawn")    # spawn() and despawn(), no queue_destroy()
@factory("", "despawn")         # only despawn()
```

- Give `""` or no name for a method that doesn't apply, e.g. `destroy` in a refcounted class.

# @abstract

Like in GDScript, an `@abstract` class is only a base for other classes:

```gd++
@abstract
class_name Weapon
extends Node3D

@virtual
func _fire() -> void {}

class Sword {
  extends Weapon

  @override
  func _fire() -> void {}
}
```

- The editor's "Create New Node" dialog doesn't show it.
- `@factory` gives it no `create()`, and `create Weapon` fails to compile: "Abstract classes can't be created. Create a subclass instead.".
- Its subclasses work as usual, GD++ classes and scripts alike. Scripts can also use it as a type.
- Unlike in GDScript, `Weapon.new()` in a script still works: Godot registers the class as a virtual class, which only the editor doesn't create.
- Not with `@pool` or `@scene`, since both are about creating objects. Put them on the subclasses.
- Not inherited: `Sword` is a regular class.
- Without `@tool`, the class and its subclasses are guarded classes. See "Guarded classes" below.
- `gd++ ls` shows `@abstract` classes with the tag `@abstract`.
- Only classes are abstract. For functions that subclasses override, use `@virtual`. See `gd++ man functions`.

# @tool

Like in GDScript, a class's code runs in the editor only if the class has `@tool`:

```gd++
@tool
class_name Gizmo
extends Node3D

on process(delta: float) {
  rotate_y(delta);          // Spins in the editor too.
}
```

Without `@tool`:

- The class is registered as a runtime class, unless it's a guarded class. See "Guarded classes" below.
- In the editor, Godot creates placeholders for its objects. They store the property values that you set in the inspector, but run none of the class's code.
- So a runtime class can't break the editor, e.g. by moving nodes around in a scene you're editing.
- Games run from the editor and exported games run all code.

Facts:

- `@tool` is not inherited, neither from the file-level class nor from the base class. Inline classes need their own.
- `gd++ ls` shows `@tool` classes with the tag `@tool`.
- `@editor_only` keeps a `@tool` class's code out of the game. See "@editor_only" below.

# @game_only

Placeholders only stop the code that Godot calls. Code that already runs in the editor, e.g. a `@tool` class's or a C++ tool class's, can still:

- create an object of a runtime class with `create`,
- call its static functions.

Then the runtime class's code runs. `@game_only` prevents this: the class's code only ever runs in the game.

```gd++
@game_only
class_name Spawner
extends Node3D
```

- A `@game_only` class is a runtime class, unless it's a guarded class. See "Guarded classes" below.
- In debug builds, which the editor loads, every function that GD++ generates for it starts with a check. In the editor:
  - the function returns right away, with a default value,
  - getters and setters only read and write their variable,
  - an `@onthread` function returns an empty `Async`, without starting a task.
- In the constructor, the check comes after the initial values of variables, so the editor still sees them.
- The check covers the class's functions, constructor, destructor, getters, setters, signal emit functions, and the helpers that GD++ adds, e.g. for enums, default values and RPCs.
- Your own `decl` and `impl` code isn't checked.
- Release builds have no checks.
- Not with `@tool`.
- Not inherited.

`@game_only` also works on single functions and variables, e.g. to keep a few functions of a `@tool` class out of the editor:

```gd++
@tool
class_name Spawner
extends Node3D

on process(delta: float) {
  rotate_y(delta);          // Spins in the editor too.
}

@game_only
func spawn() -> void {
  ...                       // Only spawns in the game.
}

@game_only
var wave: int
```

- On a function: the function gets the same check, and so do its helpers: its enum wrapper, default value functions and RPC helper, and for `@virtual`, `@deferred` and `@onthread`, the functions that GD++ adds for them.
- On a variable: its getter and setter get the check. In the editor, they only read and write the variable.
  - Its initial value is still assigned in the editor.
  - C++ code that uses the variable directly isn't checked.
  - It can't have an export annotation, since the editor would read and save the default value.
- In a `@game_only` class, every function and variable is already `@game_only`.

# @editor_only

`@editor_only` is the opposite of `@game_only`: the code only runs in the editor, never in the game. E.g. for gizmos and previews of a `@tool` class.

```gd++
@tool("editor_only")
class_name Gizmo
extends Node3D
```

- Only for `@tool` classes. `@tool("editor_only")` is the same as `@editor_only @tool`.
- Every function that GD++ generates for the class starts with a check. In the game:
  - the function returns right away, with a default value,
  - getters and setters only read and write their variable,
  - an `@onthread` function returns an empty `Async`, without starting a task.
- The check covers the same functions as `@game_only`'s, and comes at the same place in the constructor.
- Unlike `@game_only`'s, it's in release builds too, since the game runs them.
- Your own `decl` and `impl` code isn't checked.
- Not with `@game_only`, neither on the class nor on its functions and variables.
- Not inherited.

It also works on single functions and variables of a `@tool` class:

```gd++
@tool
class_name Spawner
extends Node3D

@editor_only
on process {
  preview();                // Only previews in the editor.
}

@editor_only
var preview_count: int = 3
```

- On a function: the function and its helpers get the check, like with `@game_only`.
- On a variable: its getter and setter get the check. In the game, they only read and write the variable.
  - Its initial value is still assigned in the game.
  - C++ code that uses the variable directly isn't checked.
  - Unlike with `@game_only`, it can have an export annotation, since the editor runs its getter and setter.
- In an `@editor_only` class, every function and variable is already `@editor_only`.

# Guarded classes

Godot doesn't let a runtime class extend a class of the package that isn't one: a `@tool` class, an `@abstract` class, or a C++ class with `tool` or `abstract`. So GD++ guards such subclasses instead, like `@game_only` classes:

```gd++
@tool
class_name Gizmo
extends Node3D

class Handle {
  extends Gizmo             // Guarded.
  @export var size: float = 1.0
}
```

- Guarded classes are the subclasses without `@tool` of those classes, at any depth, and `@abstract` classes without `@tool`.
- They are registered as regular classes, not runtime classes, so the editor creates real objects of them, not placeholders.
- Their generated functions start with the check of `@game_only` classes, so their code doesn't run in the editor either.
- Initial values of variables still set up their objects in the editor, so the inspector shows them.
- In the editor, their getters and setters only read and write the variable. A variable with `get` and `set` blocks gets a hidden field for that.
- Release builds have neither the checks nor the hidden fields, since the editor only loads debug builds. Only the variables you declare take up memory there.
- C++ classes can't be guarded: one that extends such a class needs `tool = true` or `abstract = true`, or the build fails. See `gd++ man cpp-classes`.

# @icon

```gd++
@icon("res://icons/player.svg")
class_name Player
extends CharacterBody3D
```

- Sets the class's icon in the editor, e.g. in the scene tree and the "Create New Node" dialog.
- Takes one argument: a string with the icon's path, usually an SVG file.
- The path starts with `res://`, relative to the project, or `pkg://`, relative to the package.
- GD++ writes the icons into the package's `.gdextension` file.
- `gd++ ls` shows a missing icon file in red.

```gd++
@icon("pkg://icons/bullet.svg")
class Bullet {
  extends Area3D
}
```

# @scene

A node's children, e.g. its meshes and collision shapes, usually live in a scene. With `@scene`, `create` instantiates the class's scene:

```gd++
@scene("pkg://bullet.tscn")
class_name Bullet
extends Area3D
```

```gd++
Gd<Bullet> bullet = create Bullet;   // the root of bullet.tscn, with its children
add_child(bullet);
```

The path:

- starts with `res://`, relative to the project, or `pkg://`, relative to the package.

`create`:

- The first `create` loads the scene, and keeps it. Later ones only instantiate it. See "Loading the scene" below.
- The scene's root must be a `Bullet`. If it isn't, or the scene fails to load, `create` prints an error and returns null.
- Thread-safe: worker threads may create scenes too, though only the main thread may add them to the tree.
- Only `create` uses the scene. `memnew(Bullet)`, `Bullet.new()` in GDScript, and scenes that hold a `Bullet` give the node alone.
- Classes without `@scene` pay nothing for it: `create` decides at compile time.

Loading the scene:

- The scene stays kept until the library is unloaded, or until `scene_evict()`, below.
- `@factory_scene` gives the class two static methods to manage it:
- `scene_cache()` loads and keeps it ahead of time, e.g. when a level loads, so the first `create` doesn't pay for it. It does nothing if the scene is kept already.
- `scene_evict()` drops it, e.g. when the level is unloaded. The next `create` or `scene_cache()` loads it again. Bullets created from it stay as they are.
- Both are thread-safe.

```gd++
@scene("res://bullet.tscn")
@factory_scene
class_name Bullet
extends Area3D
```

```gdscript
func _ready():
    Bullet.scene_cache()    # loads bullet.tscn now

func _exit_tree():
    Bullet.scene_evict()    # drops it
```

- GD++ code calls them the same way: `Bullet::scene_cache();`.
- Other names: `@factory_scene` takes up to two strings, for `scene_cache` and `scene_evict`, e.g. `@factory_scene("preload_bullet")`. An empty string `""`, or a missing name at the end, leaves that method out.

Other facts:

- `@scene` works on classes that extend `Node`, since a scene's root is a node.
- A class that extends a `@scene` class doesn't use its scene, unless it has a `@scene` of its own.
- With `@pool`, the pool instantiates the scene for each new object, and reuses objects without it.
- With `@factory`, scripts call `Bullet.create()`, which does the same. It returns the root of a new instance of the scene, or `null`, so check it. See "In scripts" above.

# Editor plugins

A class that extends `EditorPlugin` is an editor plugin, which adds to the editor, e.g. docks, gizmos and importers:

```gd++
@tool
class_name TerrainPlugin
extends EditorPlugin

on enter_tree {
  add_control_to_bottom_panel(create Label, "Terrain");
}
```

- GD++ adds it to the editor when the editor loads the package. It needs no `plugin.cfg`, and the project settings don't list it, so it can't be turned off there.
- It needs `@tool`, since it runs in the editor.
- An `@abstract` one isn't added: only its subclasses are.
- Godot only has the editor's classes, e.g. `EditorPlugin` or `EditorInspectorPlugin`, in the editor. So GD++ registers the classes that extend them later than the others, once the editor is there. Exported games don't have them at all.

# @singleton

A singleton is the one object of its class, which every part of the game reaches by its class's name, like Godot's `Input` or `Engine`. E.g. for a game's state or services:

```gd++
@singleton
class_name Game
extends Object

var score: int

func add(points: int) -> void {
  score += points;
}
```

```gd++
Game::get_singleton()->add(10);
```

```gdscript
Game.add(10)
```

- The package creates the object when Godot loads it, and deletes it when Godot unloads it.
- Godot knows it by the class's name, like its own singletons. So scripts write `Game.add(10)`, and `Engine.get_singleton("Game")` returns it.
- GD++ code gets it with the static function `get_singleton()`. Its name is taken: a member can't be named `get_singleton`.
- Without `@tool`, the object exists in the editor too, so that scripts that use it parse, but its code doesn't run there: it's guarded like a `@game_only` class. See "@game_only" above.
- It can be a node. Then it's an orphan node, outside the scene tree:
  - It gets no `on ready`, no `on process` and no other notifications of the tree, and `get_tree()` returns null. It can have children, which are orphans too.
  - Code can add it to the tree, e.g. `get_tree()->get_root()->add_child(Game::get_singleton())`. The package deletes it when it's unloaded, wherever it is.
  - Don't free it yourself, e.g. with `queue_free()`: Godot would keep the deleted object as its singleton.
  - Godot's report of orphan nodes, `Node.print_orphan_nodes()`, lists it.
- It can be refcounted, e.g. extend `RefCounted` or `Resource`. Then the package holds a reference to it, which keeps it alive until the package is unloaded. Other references may keep it alive longer.
- Not with `@abstract`, `@pool`, `@scene`, `@factory`, `@factory_pool` or `@factory_scene`, since the package creates its one object.
- `gd++ ls` shows it with the tag `@singleton`.

A node that every scene reaches and that processes every frame, e.g. a game manager, is simpler as an autoload, which Godot adds to the tree. GDExtensions can't register autoloads, but a scene can be one:

1. Make a scene whose root is the node, e.g. `game_manager.tscn` with a `GameManager` root.
2. In Godot's project settings, under Globals > Autoload, add the scene, e.g. as `GameManager`.
3. Scripts then write `GameManager.method()`. GD++ code gets it with `get_node<GameManager>("/root/GameManager")`.

# @trace and @profile

```gd++
@trace("loot")
@profile
class_name Chest
extends Node3D
```

For debugging:

- `@trace` on a class traces all its functions, variables and signals, and prints each creation and destruction of its objects.
  - Except `on process` and `on physics_process`, which run every frame. They have their own groups, `process` and `physics_process`.
- `@profile` times all its functions, and the getters and setters of its properties.
- They only generate code in builds that turn on one of their groups. Here:
  - `@trace`: `--trace loot`, `--trace Chest` or `--trace all`,
  - `@profile`: `--profile Chest` or `--profile all`.
- Not inherited.

See `gd++ man debugging`.

# Annotations and doc comments

Before `class_name` or `class`, a class can have, in any order:

- `@tool`, `@tool("editor_only")`, `@editor_only @tool` or `@game_only`,
- `@abstract`, `@icon`, `@pool`, `@scene`, `@singleton`, `@trace` and `@profile`,
- a doc comment.

```gd++
/// The player's character.
///
/// It runs, jumps and collects coins.
@tool
@icon("res://icons/player.svg")
class_name Player
extends CharacterBody3D
```

The doc comment's first paragraph is the brief description. The rest is the full description. See `gd++ man docs`.

# Members

A class body holds members, in any order:

```
func       functions                      gd++ man functions
shader     functions in GLSL, on the GPU  gd++ man shaders
var        variables and properties       gd++ man variables
signal     signals                        gd++ man signals
enum       enums and integer constants    gd++ man enums
ctor       the constructor                gd++ man lifecycle
dtor       the destructor                 gd++ man lifecycle
on         notification handlers          gd++ man notifications
decl, impl plain C++                      gd++ man code
shader { } GLSL that shaders share        gd++ man shaders
import     force an include               gd++ man includes
noimport   prevent an include             gd++ man includes
```

Functions, shaders, variables, signals and constants share one namespace, since they all become C++ members of one class:

- `var x` also declares its getter `get_x` and its setter `set_x`.
- `signal s` also declares a C++ method `s`, which emits it.
- `@virtual func _f` also declares `f`, which scripts call. See `gd++ man functions`.
- A trait's default function, which the class doesn't define, is a member too. See `gd++ man traits`.
- `@factory`, `@factory_pool`, `@factory_scene` and `@factory_shader` declare their methods, e.g. `create`. See "In scripts" above, and `gd++ man shaders`.
- Names that start with `_gdpp_` are reserved for generated code.

So `var x` and `func get_x()` can't be in the same class:

```out
[×] res://player.gd++:8:1: The name "get_x" is already used by another member.
     8 | func get_x() -> int {
       | ^^^^
    Hint: Members share one namespace. A var x also declares get_x and set_x, a signal declares its emit function, a @virtual func _x declares x, and @factory declares methods, e.g. create.
```

# This

In a class's C++ code, `This` is the class's name, like `Self` in Rust:

```gd++
func clone() -> Player {
  Gd<This> copy = create This;
  copy->speed = speed;
  return copy;
}
```

It's a macro that GD++ defines around the class's code. See `gd++ man code`.

# What GD++ generates

For a class `Player`, GD++ generates `Player.h` and `Player.cpp`, in namespace `godot`:

```cpp
class Player : public CharacterBody3D {
  GDCLASS(Player, CharacterBody3D)
  ...
protected:
  static void _bind_methods();
};
```

- The class has all the members, and `_bind_methods`, which binds them to Godot.
- The build registers the class when Godot loads the library, after its base class if that's a class of the package too.

See `gd++ man generated`.

# Examples

A resource type, for data files edited in the inspector:

```gd++
/// An item that the player can pick up.
@icon("res://icons/item.svg")
class_name Item
extends Resource

@export var title: String
@export var price: int
@export var icon: Texture2D
```

A node with a helper class:

```gd++
class_name Spawner
extends Node3D

@export var scene: PackedScene

func spawn() -> Node3D {
  Gd<Node3D> node = scene->instantiate() as Gd<Node3D>;
  add_child(node);
  return node;
}

class SpawnInfo {
  var count: int
  var position: Vector3
}
```
