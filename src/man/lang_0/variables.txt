Variables: var, node paths and properties

A variable is a property of its class that Godot knows.

- GDScript can read and write it, e.g. `player.speed = 3.0`.
- With an export annotation, the inspector shows it and scenes save it.
- Two kinds: simple variables, which GD++ stores for you, and properties, with your own getter and setter. Under the hood, they're the same.

# Simple variables

```gd++
var health: int
var speed: float = 5.0
var target: Node3D
var anything
```

- `var name: Type`, with an optional initial value after `=`.
- Without a type, the variable is a `Variant`. See `gd++ man types`.

For each simple variable, GD++ generates:

- a public field of the C++ class, with the variable's name and C++ type, e.g. `int64_t health{};`. Your C++ code reads and writes it directly.
- a getter, `int64_t get_health() const;`, and a setter, `void set_health(int64_t p_value);`. Public methods, which Godot calls.
- the binding of both in `_bind_methods`, and the property that uses them.

Facts:

- Without an initial value, a field starts as its type's default: `0`, `0.0`, `false`, an empty `String`, a zero vector, `nullptr`, a null reference, and so on.
- In GDScript, `player.health = 50` calls `set_health`, and `player.health` calls `get_health`.

```gd++
func heal() -> void {
  health = 100;           // C++ code uses the field directly.
}
```

# Initial values

The initial value is C++:

- an expression to the end of the line, which continues on the next lines while a bracket is open,
- or a block of C++ that returns the value,
- or, for a variable of a GD++ enum type, one of the enum's values, e.g. `var trump: Suit = HEARTS`, or for a bitfield, several combined, e.g. `var mask: Layer = WORLD | PLAYER`. See `gd++ man enums`.

```gd++
var count: int = 3
var spawn_point: Vector3 = Vector3(0, 2, 0)
var total: int = compute(1,
  2)

var weights: PackedFloat32Array = {
  PackedFloat32Array w;
  w.push_back(0.5);
  w.push_back(1.5);
  return w;
}
```

When they're assigned:

- In the constructor, in the order of the declarations, before the body of your `ctor`.
- A block becomes a lambda that is called right away. So it can use the object (`this`) and its other fields.

See `gd++ man lifecycle`.

# @onready

```gd++
@onready
var camera: Camera3D = $Camera

@onready
var marker: Node3D = {
  Node3D *res = create Node3D;
  add_child(res);
  return res;
}
```

- Assigns the initial value right before the `on ready` block, instead of in the constructor, like in GDScript.
- Then the node's children exist, so it can get them, e.g. with the node path `$Camera`.
- GD++ assigns it in the class's `_notification`, at `NOTIFICATION_POST_ENTER_TREE`. So it's set before any `_ready` runs, even a script's.
- Without an initial value, it does nothing.
- Only for classes that extend `Node`, since only nodes get `_ready`.

See `gd++ man lifecycle`.

# Node paths

Like in GDScript, the initial value of an `@onready` variable can be a node path:

- `$` and the path of a node,
- `%` and the name of a unique node.

GD++ turns it into a call of `get_node`, with the variable's type:

```gd++
@onready var camera: Camera3D = $Rig/Camera     // get_node<Camera3D>("Rig/Camera")
@onready var bar: ProgressBar = %HealthBar      // get_node<ProgressBar>("%HealthBar")
```

The rules are GDScript's:

- After `$` or `%` come node names, joined by `/`.
- A name is an identifier, e.g. `Camera`, or a string, e.g. `$Hud/"Health Bar"`, for names with spaces or other signs.
  - A string's text goes into the path as it is, so `$"../Sibling"` works too.
  - An identifier can be any name or GDScript keyword, e.g. `$if`, except `true`, `false` and `null`.
  - An identifier can't start with a digit: write `$"2D"`.
- Strings are GDScript strings: `"..."`, `'...'`, `"""..."""` and `'''...'''`, with GDScript's escapes, e.g. `\n` and `é`, or raw strings, e.g. `r"..."`, without them.
- `%` starts the name of a unique node, at the start or after a `/`, e.g. `%HealthBar`, `$%HealthBar` or `$Hud/%HealthBar`.
- `$/` starts an absolute path, e.g. `$/root/Main`.
- Spaces between the parts don't count: `$Hud / Score` is `$Hud/Score`.
- `//` starts a comment, like everywhere in GD++. So `$Hud//Score` is `$Hud`.

Limits:

- A node path must be the whole initial value. For more, write C++, e.g. `get_node<Node>("Hud")->get_child(0)` instead of `$Hud.get_child(0)`.
- It needs `@onready`: in the constructor, the node has no children yet.
- The variable needs a node type: `Node`, or a class that extends it.
- `get_node` casts the node to that type. If the node has another type, the variable is `nullptr`.
- If there's no node at the path, it's `nullptr` too, and Godot prints an error.

# Properties

A property has its own getter and setter, e.g. to check values, or to compute them:

```gd++
var ammo: int {
  decl {
    int64_t ammo_ = 0;
  }
  get {
    return ammo_;
  }
  set(value) {
    ammo_ = value < 0 ? 0 : value;
  }
}
```

The braces after the type hold three kinds of blocks, in any order:

decl { ... }
  C++ declarations for the private section of the class, typically the field that stores the value.
  - A property has no field of its own. Without a `decl` block, it stores nothing.
  - Any number of `decl` blocks are allowed.

get { ... }
  The body of the getter, `int64_t get_ammo() const`, which returns the value.
  - Required: Godot doesn't support properties that can only be set.
  - A const method: it can't change fields, except mutable ones.

set(NAME) { ... }
  The body of the setter, `void set_ammo(int64_t value)`, whose parameter is called NAME.
  - Optional. Without it, the property is read-only, and Godot can't set it.
  - The parameter's type can be left out: it's the property's type. If written, it must be the same type.

Facts:

- A property can't have an initial value. Initialize its storage in its `decl` block, or in the `ctor`.
- Inside the class, C++ code calls the getter and the setter like any method, e.g. `set_ammo(10)`, or uses the storage directly.

A read-only, computed property:

```gd++
var is_dead: bool {
  get {
    return health <= 0;
  }
}
```

The `set` block takes `@deferred` or `@thread_safe`, like a function:

```gd++
var target: Vector3 {
  decl { Vector3 target_; }
  get { return target_; }
  @deferred set(value) {
    target_ = value;
    rebuild_path();
  }
}
```

- `@deferred`: every call of the setter goes through `call_deferred`, from C++, from scripts, and from the inspector or a scene file. The block runs at the end of the frame. Until then, the getter returns the old value.
- `@thread_safe`: the same, with `call_thread_safe`. A call from another thread runs later on the main thread. A call from the main thread runs right away. Only for classes that extend `Node`.
- GD++ puts the block in a second method, `_gdpp_body_set_NAME`, which the call runs by name.

See "@deferred and @thread_safe" in `gd++ man functions`.

# Names

A variable `x` declares three names in its class: `x`, `get_x` and `set_x`, even if it's a read-only property. They must not clash with other members:

```gd++
var speed: float
func get_speed() -> float { ... }     // error: get_speed is taken
```

# Visibility in Godot

- Every variable is a property in Godot, so GDScript can get and set it by name.
- Only exported variables show up in the inspector, and are saved in scenes and resources.

```gd++
@export var health: int           // in the inspector, saved
@export_storage var rng_seed: int // saved, but not in the inspector
var cache: int                    // neither: only for code
```

See `gd++ man exports`.

# Annotations

Variables take:

- `@onready`,
- one export annotation, see `gd++ man exports`,
- the section annotations `@export_category`, `@export_group` and `@export_subgroup`,
- `@game_only`, which keeps their getter and setter from running in the editor. Not with an export annotation. See `gd++ man classes`.
- `@trace` and `@profile`, for debugging.

A doc comment before a variable becomes its description in the editor's help. See `gd++ man docs` and `gd++ man annotations`.

```gd++
@trace
var health: int = 100

@profile
var path_length: float {
  get { return compute_path_length(); }
}
```

- `@trace`: in builds with `--trace Player` (the class's name) or `--trace all`, prints every change of `health`, and which function of the class made it, e.g. `Player "Hero".health: 100 → 70  (in take_damage)`. The quickest way to find out what changes a value.
- `@profile`: in builds with `--profile Player`, times the getter and the setter, here `get_path_length`.
- In other builds, they generate nothing.

See `gd++ man debugging`.

# Examples

```gd++
class_name Character
extends CharacterBody3D

/// Hit points, from 0 to max_health.
@export_range(0, 1000, 1)
var health: int = 100

@export
var max_health: int = 100

@onready
var sprite: Sprite3D = $Sprite

/// Health as a fraction of max_health, from 0 to 1.
var health_ratio: float {
  get {
    return max_health > 0 ? double(health) / max_health : 0.0;
  }
}

/// The character's name, never empty.
@export
var title: String {
  decl {
    String title_ = "Nameless";
  }
  get {
    return title_;
  }
  set(value) {
    title_ = value.is_empty() ? String("Nameless") : value;
  }
}
```
