Signals: declaring and emitting signals

A signal is a message that an object sends, and that other objects can connect to, like a button's `pressed` signal.

- GD++ declares signals like GDScript.
- It sends them with a rewrite, `emit`.

# Declaring signals

```gd++
signal died
signal health_changed(health: int)
signal hit(by: Node3D, damage: int, info)
```

- `signal name`, then optionally the parameters in parentheses, like a function's: `name: Type`, or just `name` for a `Variant`. See `gd++ man types`.
- Without parameters, the parentheses are optional.
- Parameters can't have default values.
- Signals take a doc comment.
- The only annotation they take is `@trace`. See "Tracing signals" below.

# Sending signals

```gd++
func take_damage(amount: int) -> void {
  health -= amount;
  emit health_changed(health);
  if (health <= 0) {
    emit died();
  }
}
```

- `emit NAME(ARGS);` sends the signal, like `NAME.emit(ARGS)` in GDScript.
- Every connected function is called with the arguments.
- The parentheses are needed, even without arguments: `emit died();`.
- `emit` makes sending a signal look different from calling a function, on purpose: they do different things.
- It also works on other objects of GD++ classes, and on externs:

```gd++
emit player->died();
emit terrain->changed();
```

# How it works

For each signal, GD++ generates a public C++ method with the signal's name and parameters. It emits the signal with `emit_signal`:

```cpp
gdpp::Emitted health_changed(int64_t health);
```

- It returns `Emitted`, a struct marked `[[nodiscard]]`, which holds the `Error` that `emit_signal` returned.
- So a plain call, `health_changed(5);`, makes the compiler warn that the result is unused.
- In C++ code, GD++ replaces `emit` with `(void)`, which uses the result:

```gd++
emit health_changed(5);      // becomes:  (void) health_changed(5);
```

- To check whether sending worked, use the result instead of `emit`:

```cpp
Error err = health_changed(5).error;
```

- GD++ registers each signal in `_bind_methods`, with its parameter names and types. So the editor's Node dock lists it, and GDScript can connect to it.
- GD++ replaces every `emit` identifier in C++ code. So don't use `emit` as a name in your C++ code, e.g. for a variable, and don't call methods named `emit`, e.g. `Signal::emit`. Comments and strings are safe.

# Names

A signal declares a C++ method. So its name shares its class's namespace with functions, variables and their getters and setters: a signal and a function can't have the same name.

# Connecting to signals

An `on` block runs when an object emits a signal: `on`, a variable of the class, a dot, and the signal's name.

```gd++
class_name Menu
extends Control

@onready var start: Button = $Start
@export var player: Player

on start.pressed {
  get_tree()->change_scene_to_file("res://level.tscn");
}

on player.health_changed(health) {
  gd::print("Health: ", health);
}

on this.resized {
  gd::print("The menu's size changed.");
}
```

- `on VARIABLE.SIGNAL` runs when the object in the variable emits the signal. `on this.SIGNAL` runs when the object itself does.
- The variable's type says which signals it has: those of its class and its bases, e.g. `Button`'s `pressed`, or a GD++ class's or extern's own. A misspelled signal is an error.
- The parameters are the signal's, in order. Their names are yours to choose. Their types can be left out, since GD++ knows them, and so can the parameters at the end, which the block doesn't need: `on player.health_changed(health)`, `on player.health_changed(health: int)` and `on player.health_changed` all work.
- The block is a method of the class, which scripts can't call.

The block follows its variable: it's always connected to the object that the variable holds.

- GD++ connects it right after each assignment of the variable: its initial value in the constructor, its `@onready` value, its `@recycle` value, and every call of its setter, e.g. from scripts, the inspector, scenes and C++'s `set_player(p)`.
- When the variable gets another object, GD++ disconnects the block from the old one, if it's still there.
- C++ code that assigns the field itself, e.g. `player = p;`, skips the setter. Then the block stays connected to the old object. Call the setter instead: `set_player(p);`.
- A null variable connects nothing, without an error.
- The variable must be a simple variable, or a property with a `set` block that isn't `@deferred` or `@thread_safe`.
- `on this.SIGNAL` connects once, in the constructor.

Facts:

- When the object or the class's object is freed, Godot drops the connection.
- `on` blocks of signals take `@trace`, `@profile`, `@game_only`, `@editor_only` and `@async`, like other `on` blocks.
- With `@async`, the block is a coroutine, which can `await`: each emission starts one, and nothing waits for it, like an `@async("detached")` function. Its parameters are copies, so they stay valid across its awaits. If the class's object is freed while it waits, it stops there. See `gd++ man async`.
- A signal can have only one `on` block per variable in a class.
- In the editor's Node dock, connections that GD++ makes don't show. They're made by the code, like `connect` in a script's `_ready`.

Connecting in the scene, in the editor's Node dock, works too: functions declared with `func` are bound, so the editor lists them.

To connect in C++ code, e.g. to an object in a local variable, call `connect` with `callable`:

```gd++
func spawn() -> void {
  Gd<Coin> coin = create Coin;
  coin->connect(string_name "collected", callable on_collected);
  coin->connect(string_name "lost", callable [this] { lives--; });
  add_child(coin);
}
```

- `callable NAME` makes a `Callable` of a function of the class, and `callable [...] { ... }` of a lambda. See "Callables" in `gd++ man rewrites`.
- In GDScript, connect as usual: `player.died.connect(_on_player_died)`.

# Awaiting signals

An `@async` function waits for a signal with `await`, like GDScript:

```gd++
@async
func hide_hit() -> void {
  await anim->animation_finished;   // a signal of another object
  await died;                       // a signal of this class
  set_visible(false);
}
```

`await` gives the signal's arguments, with their types: e.g. `Gd<Node2D> body = await area->body_entered;`. See "Awaiting signals" in `gd++ man async`.

# Enums in signals

- A signal parameter can be a GD++ enum.
- Godot sees it as an `int`, marked with the enum.
- `emit` converts it for you.

```gd++
enum State { IDLE, RUNNING, JUMPING }
signal state_changed(state: State)

func jump() -> void {
  emit state_changed(State::JUMPING);
}
```

# Tracing signals

For debugging, a signal can have `@trace`:

```gd++
@trace
signal health_changed(health: int)
```

- In builds with `--trace Player` (the class's name) or `--trace all`, each `emit` prints a line with its arguments, before the handlers run, e.g. `⚡ Player "Hero" emits health_changed(health: 70)`.
- The line comes from the signal's emit function. So emissions by name with `emit_signal`, and from GDScript, don't show.
- In other builds, `@trace` generates nothing.

See `gd++ man debugging`.

# Example

```gd++
/// A button that counts its presses.
class_name CountingButton
extends Button

/// Sent every tenth press.
signal tenth_press(total: int)

var presses: int

@override
func _pressed() -> void {
  presses++;
  if (presses % 10 == 0) {
    emit tenth_press(presses);
  }
}
```
