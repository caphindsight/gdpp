Pools: @pool, @recycle, create and destroy

A game that creates and deletes many nodes of the same class, e.g. bullets, spends a lot of time allocating memory and setting up new objects. A pool avoids this: instead of deleting an object, it keeps it, and reuses it later. This page explains how pools work.

# @pool

```gd++
@pool(100)
class_name Bullet
extends Area3D

var speed: float = 20.0

ctor {
  gd::print("A bullet was created.");
}

dtor {
  gd::print("A bullet was deleted.");
}

@recycle ctor {
  speed = 20.0;
}

@recycle dtor {
  gd::print("A bullet was kept for later.");
}
```

```gd++
func fire() -> void {
  Bullet *bullet = create Bullet;
  if (bullet) {
    add_child(bullet);
  }
}

func _on_hit(bullet: Bullet) -> void {
  destroy bullet;
}
```

`destroy` returns the bullet to the pool: it runs the `@recycle dtor`, removes the node from its parent, and keeps it in the pool. `create` takes a bullet from the pool if there is one, and runs its `@recycle ctor`. Otherwise, it creates a new bullet. A reused node also gets ready again: the next time it enters the tree, its `@onready` values are set and `_ready` runs, just like for a new node.

# Two kinds of ctor and dtor

A `@pool` class can have two kinds of constructors and destructors, at most one of each:

- `ctor` and `dtor` run only when an object is actually created or deleted, like in any other class. Variables get their initial values only then, together with `ctor`.
- `@recycle ctor` runs when the pool reuses an object instead of creating a new one, and `@recycle dtor` runs when the pool keeps an object instead of deleting it.

So a bullet that's created, returned to the pool, reused and finally deleted runs `ctor`, `@recycle dtor`, `@recycle ctor` and `dtor`, in that order. Put expensive setup that a reused object can keep in `ctor`, and reset everything that a reused object must not keep in `@recycle ctor`, e.g. variables like `speed` above. Only `@pool` classes can have `@recycle` blocks.

# Out of the tree

`@pool` only works on classes that extend `Node`, since the pool removes its objects from the scene tree. A node that's out of the tree gets no callbacks: no `_process`, `_physics_process`, input or physics, and its timers and tweens are paused. Signals and deferred calls still reach it, though, so disconnect any that must not.

# The size

The size is optional:

- `@pool` has no limit.
- `@pool(100)` can hold up to 100 objects, counting both those in use and those waiting in the pool. Once all of them are in use, `create` returns `nullptr`.
- `@pool(100, "strict")` also logs an error when `create` finds the pool full. Use it for pools that should never run out.

Warning: if a pool has a fixed size, `create` returns `nullptr` once all of its objects are in use, even without `"strict"`. Always check the result before using the object, as `fire` does above: using a null pointer crashes the game. Only a pool without a size never returns `nullptr`.

# Which objects belong to the pool

Only objects made by `create` belong to the pool. Objects created in other ways, e.g. by a scene, by `Bullet.new()` in GDScript, or by `memnew`, don't count toward its size, and `destroy` deletes them for good. If an object from the pool is deleted for good, e.g. with `queue_free()`, it leaves the pool, which frees up room for a new one. `destroy` also deletes an object for good when it's called through a pointer to a base class, e.g. `Node *`, or on an object of a class that extends a `@pool` class, unless that class has its own `@pool`.

# Pools of scenes

With `@scene`, the pool instantiates the class's scene for each new object. A reused object keeps its children, so reusing it doesn't touch the scene. See `gd++ man classes`.

# Threads and speed

`create` and `destroy` are thread-safe, and take constant time: the pool stores its objects in a list of fixed-size chunks, so it never has to move them. Godot only lets the main thread change the scene tree, so when another thread destroys a node that's in the tree, `destroy` leaves it to the main thread, which destroys it at the end of the frame. Until then, the node stays in the tree and keeps running. A node that's out of the tree is destroyed right away, on any thread.

# Unloading

When the library is unloaded, e.g. when the game quits, the pool deletes the objects it's holding, which runs their `dtor`.
