Functions: func, parameters, default values, engine functions, and @override, @virtual, @const, @static

A function is a method of its class that Godot knows: GDScript can call it, e.g. `player.jump()`, and so can `call()`, signals and the editor. Its signature is GD++, and its body is C++.

# Syntax

```gd++
func greet(name: String, times: int = 1) -> void {
  for (int64_t i = 0; i < times; i++) {
    gd::print("Hello, ", name, "!");
  }
}
```

- `func`, then the name, then the parameters in parentheses, separated by commas. A trailing comma is allowed.
- Each parameter is `name: Type`, or just `name` for a `Variant`, with an optional default value after `=`.
- Then, optionally, `->` and the return type. Without it, the function returns a `Variant`.
- Then the body: C++ code in braces. The body is optional.

In the body, parameters have their C++ types: here, `name` is a `const String &` and `times` an `int64_t`. See `gd++ man types`.

```gd++
func area(width: float, height: float) -> float {
  return width * height;
}

func describe(value) -> String {        // value is a Variant
  return String("Got: ") + String(value);
}

func random_thing() {                   // returns a Variant
  return Variant(42);
}
```

# Functions without a body

```gd++
func not_done_yet() -> int
```

A function without a body gets a generated one, which returns the type's default value: `0`, `false`, an empty `String`, `nullptr`, and so on, or nothing for `void`. This is handy for `@virtual` functions, and to sketch a class's API.

# What GD++ does with a function

- It declares the function as a public method of the C++ class, and defines it in the class's source file, with your body.
- It binds the function in `_bind_methods` with `ClassDB::bind_method`, with its parameter names and default values, so Godot can call it. `@static` functions are bound with `ClassDB::bind_static_method`, `@virtual` ones with `GDVIRTUAL_BIND`, next to a function that calls them, and `@override` ones not at all, since the engine binds them.
- With `@game_only`, or in a `@game_only` class, the body starts with a check that returns right away in the editor, in debug builds. See `gd++ man classes`.

Functions are plain C++ methods, so C++ code calls them directly, e.g. `jump();` or `player->jump();`, at full speed.

Function names must be unique in their class, including the getters and setters of variables and the emit functions of signals: there is no overloading.

# Default values

```gd++
func spawn(count: int = 1, at: Vector3 = Vector3(0, 1, 0), kind: Kind = Kind::BIG) -> void { ... }
```

A default value is a C++ expression, up to the `,` or `)` that ends it, or a block of C++ that returns the value:

```gd++
func shout(text: String = {
  return String("HEY").repeat(3);
}) -> void { ... }
```

For a parameter of a GD++ enum type, the default value can also be one of the enum's values, e.g. `suit: Suit = HEARTS`, or for a bitfield, several of them combined, e.g. `mask: Layer = WORLD | PLAYER`. See `gd++ man enums`.

Parameters with default values must come last:

```out
[×] res://a.gd++:4:20: Parameter b needs a default value, since a parameter before it has one.
     4 | func f(a: int = 1, b: int) -> void {}
       |                    ^
    Hint: Parameters with default values must come last.
```

GD++ puts each default value into a static method of the class. Godot calls it once, when it registers the class, and uses the result whenever GDScript leaves the parameter out. C++ callers get the default values too, since the C++ declaration has them. Since the default is computed in a static method, it can't use the object (`this`) or the other parameters.

If a default value is an expression rather than a block, the editor's help shows it as written.

# @override

```gd++
@override
func _unhandled_input(event: InputEvent) -> void {
  if (event->is_action_pressed(string_name "jump")) {
    jump();
  }
}

@const @override
func _get_configuration_warnings() -> PackedStringArray {
  return {};
}
```

`@override` overrides a virtual function of the engine, i.e. of the base class, e.g. `_input`, `_unhandled_input`, `_gui_input` or `_get_configuration_warnings`. The engine calls it, like in GDScript. `@override` also overrides a `@virtual` function of a GD++ base class: see "@virtual" below.

The signature must match the engine's exactly, in C++ terms, including the return type: without `-> void`, the function returns a `Variant`, and the C++ compiler reports that it doesn't override anything. Use `gd++ doc Node._input` to see a signature. A const engine function, e.g. `_get_configuration_warnings`, needs `@const` too: `@const @override`. Note that the engine's `float` parameters are `double`, like GD++'s `float`.

Overrides are not bound, since the base class binds them already. Overriding `_process` or `_physics_process` turns processing on in the constructor, with `set_process(true)` or `set_physics_process(true)`, since godot-cpp doesn't do so on its own.

A script that extends the class and defines a function of the same name replaces the override: the engine calls the script's version, and never the GD++ one. A script can't call the GD++ version with `super`, e.g. `super._unhandled_input(event)`, since Godot doesn't allow `super` calls of the engine's virtual functions. For `_ready`, `_process` and the like, leave `@override` out: see "Engine functions" below. For the others, use `@override("super")`.

# @override("super")

```gd++
@override("super")
func _unhandled_input(event: InputEvent) -> void {
  gd::print(event);
}
```

With `"super"`, GD++ also binds the body as a function of its own, which a script calls in place of `super`: `_super_NAME`. Here, a script calls `_super_unhandled_input(event)`:

```gdscript
extends Player

func _unhandled_input(event):
    _super_unhandled_input(event)
    print("and more")
```

It works on every `@override` function, of the engine or of a GD++ `@virtual` function, and on `@virtual` functions too: see "@virtual(\"super\")" below. The name of the function that it binds, e.g. `_super_unhandled_input`, must be free.

# Engine functions

```gd++
func _ready() -> void {
  gd::print("Ready.");
}

func _process(delta: float) -> void {
  rotate_y(delta);
}
```

The engine functions are the engine's virtual functions that have a notification: `_ready`, `_enter_tree`, `_exit_tree`, `_process` and `_physics_process` in classes that extend `Node`, and `_draw` in classes that extend `CanvasItem`. Written without `@override`, their bodies run in the class's `_notification`, not in an override, so a script that extends the class and defines a function of the same name doesn't replace them: both run. `@override` on them is an error, since a plain override is rarely what you want: drop it. Only if you're sure you need one, which a script replaces, write `@override("engine")`:

```out
[×] res://a.gd++:4:1: The engine function _ready doesn't need @override.
     4 | @override
       | ^^^^^^^^^
    Hint: Drop @override: GD++ runs it from _notification, so scripts can't replace it. Only if you're sure you need a plain override, use @override("engine").
```

Their signatures are `func NAME() -> void`, and `func _process(delta: float) -> void` and `func _physics_process(delta: float) -> void`, whose parameter can have any name. They take only `@trace`, `@profile` and `@game_only`. They aren't functions of the class: C++ code and scripts can't call them. In other classes, e.g. a `_ready` in a class that extends `RefCounted`, or a `_draw` in one that extends `Node` but not `CanvasItem`, they're ordinary functions.

Each one runs at its notification, e.g. `NOTIFICATION_PROCESS`, with the delta from `get_process_delta_time()` or `get_physics_process_delta_time()`. `_ready` runs at `NOTIFICATION_POST_ENTER_TREE`, the last notification before `NOTIFICATION_READY`, after the `@onready` initial values, so it runs before a script's `_ready`, once the node's children are ready. `_process` and `_physics_process` turn processing on in the constructor, like their overrides. Within the class's `_notification`, they run together with `notif` blocks, in the order of their declarations: see `gd++ man lifecycle`.

# @virtual

```gd++
@virtual
func _can_pick(item: Item) -> bool {
  return true;
}

@virtual
func _on_hit(damage: int) -> void
```

`@virtual` declares a function that scripts can override, like the engine's own virtual functions. Like theirs, its name must start with `_`. A GDScript that extends the class overrides it by defining a function of the same name:

```gdscript
extends Player

func _can_pick(item):
    return item.price < 10
```

When C++ code calls the function, the script's version runs if a script overrides it. Otherwise the body runs, as a fallback, or without a body, the type's default value is returned.

Scripts call it without the underscore: GD++ also binds `can_pick`, which calls `_can_pick`, so the script's version or the body runs, like from C++:

```gdscript
if player.can_pick(item):
    print("Picked.")
```

Godot doesn't bind virtual functions, so calling `_can_pick` by name only works on objects whose script overrides it. `can_pick` is a function of the class like any other, so its name must be free. To leave it out, use `@virtual("private")`.

`@virtual` generates a `GDVIRTUAL` declaration and binds it with `GDVIRTUAL_BIND`, and the editor's help marks the function "virtual". In C++, it's a virtual method.

A GD++ subclass overrides the function with `@override`, and a script can then override it again:

```gd++
class_name Hero
extends Player

@override
func _can_pick(item: Item) -> bool {
  return item->is_light();
}
```

When C++ code calls `_can_pick`, through a `Player` or a `Hero`, a script's version runs first, if a script overrides it. Otherwise, `Hero`'s body runs. So does a script's call of `can_pick`. The override doesn't redeclare the function for scripts: `Player`'s `GDVIRTUAL` and `can_pick` do that.

# @virtual("private")

```gd++
@virtual("private")
func _on_hit(damage: int) -> void
```

With `"private"`, GD++ doesn't bind `on_hit`: scripts can override `_on_hit`, but only C++ code calls it. Use it for hooks that the class calls itself.

# @virtual("super")

```gd++
@virtual("super")
func _can_pick(item: Item) -> bool {
  return item->get_weight() < 10;
}
```

With `"super"`, GD++ also binds the body as `_super_can_pick`, which a script's override calls in place of `super`, like with `@override("super")`:

```gdscript
extends Player

func _can_pick(item):
    return item.price < 10 and _super_can_pick(item)
```

The override must not call `can_pick` instead: that calls the override again, forever. `"super"` combines with `"private"`: `@virtual("private", "super")`.

# @override("final")

```gd++
@override("final")
func _can_pick(item: Item) -> bool {
  return true;
}
```

`"final"` on an `@override` of a GD++ `@virtual` function makes it the last version: subclasses can't override it (in C++, it's `override final`), and C++ calls never run a script's version. A script can still define a function of that name, but only calls of it by name, e.g. `player._can_pick(item)` from GDScript, reach it: `can_pick` runs the final version.

`"final"` only works there: the engine runs scripts' overrides of its own virtual functions, e.g. `_input`, so GD++ can't stop that. It combines with `"super"`: `@override("final", "super")`.

# @const

```gd++
@const
func is_alive() -> bool {
  return health > 0;
}
```

`@const` makes the function a const method in C++: it can't change the object's fields, and can be called through const pointers and references. The editor's help marks it "const". Combine it with `@virtual` for a const virtual function.

# @static

```gd++
@static
func lerp_angle(from: float, to: float, weight: float) -> float {
  return Math::lerp_angle(from, to, weight);
}
```

`@static` makes the function static: it belongs to the class, not to an object, so it has no `this`, and can't use the object's fields. GDScript calls it on the class: `Player.lerp_angle(0, 1, 0.5)`.

# @rpc

`@rpc` makes the function callable over the network. See `gd++ man rpc`.

# @deferred and @thread_safe

```gd++
@deferred
func respawn(at: Vector3) -> void {
  set_position(at);
}
```

With `@deferred`, every call of the function goes through `call_deferred`: from C++, from scripts, and over the network. The body runs later, at the end of the frame. `@thread_safe` is the same with `call_thread_safe`: a call from another thread runs later on the main thread, and a call from the main thread runs right away. Only classes that extend `Node` can use `@thread_safe`.

Since the body runs later, the function must return `void`. GD++ puts the body in a second method, `_gdpp_body_NAME`, which the call runs by name. See `gd++ man generated`.

# @onthread

```gd++
@onthread
func find_path(from: Vector2, to: Vector2) -> PackedVector2Array {
  ...
}
```

With `@onthread`, every call of the function, from C++ or from scripts, runs its body on Godot's `WorkerThreadPool`, and returns right away, with an `Async` of the function's return type: here, an `Async[PackedVector2Array]`. The caller tests whether the task is done with `is_done`, takes the result with `claim`, and can ask the task to stop with `cancel`, which the body notices with `is_cancelled`. GD++ puts the body in a second method, `_gdpp_body_NAME`, which the task calls. See `gd++ man async`.

# @game_only

```gd++
@tool
class_name Turntable
extends Node3D

func _process(delta: float) -> void {
  rotate_y(delta);          // Spins in the editor too.
}

@game_only
func launch() -> void {
  gd::print("Launched!");   // Only in the game.
}
```

With `@game_only`, the function only runs in the game, never in the editor, e.g. to keep a few functions of a `@tool` class out of the editor. In debug builds, which the editor loads, its body starts with a check: in the editor, the function returns right away, with a default value, and an `@onthread` function returns an empty `Async`. Engine functions, e.g. `_process`, take it too. In a `@game_only` class, every function already has it. See `gd++ man classes`.

# @trace and @profile

```gd++
@trace
func take_damage(amount: int) -> bool {
  health -= amount;
  return health <= 0;
}

@profile("ai")
func find_path(to: Vector3) -> PackedVector3Array {
  ...
}
```

These are for debugging. In builds with `--trace Player` (the class's name) or `--trace all`, `@trace` prints each call of `take_damage` when it starts, with its arguments, and when it returns, with its result and how long it took. In builds with `--profile ai`, `@profile` times each call of `find_path`, for the editor's monitors and a table of timings. In other builds, they generate nothing. Their arguments name groups, which the options choose. They work on every kind of function, including static, `@virtual`, `@override`, `@deferred` and `@onthread` ones. But calls by name of a `@virtual` function that a script overrides, e.g. `player._can_pick(item)` from GDScript, go straight to the script, and aren't traced or timed. Calls from C++ are, and so are calls of `can_pick`, which go through C++. See `gd++ man debugging`.

# Combining annotations

Annotations can be combined where it makes sense, e.g. `@virtual @const`. These combinations are errors:

```
@static with @virtual, @override, @const, @rpc, @deferred or @thread_safe
@virtual with @override, @rpc, @deferred, @thread_safe or @onthread
@override("final") without a GD++ @virtual function to override
@virtual on a function whose name doesn't start with _
An engine function with an annotation other than @trace, @profile and @game_only
@override with @rpc, @deferred, @thread_safe or @onthread
@rpc with @onthread
@deferred with @thread_safe or @onthread
@thread_safe with @onthread
```

`@trace`, `@profile` and `@game_only` combine with all of them. Each annotation can be used once per function. They take no arguments, except `@override`, `@virtual`, `@rpc`, `@trace` and `@profile`.

# Enums in signatures

A function whose parameters or return type use a GD++ enum is bound through a generated wrapper, named `_gdpp_` followed by the function's name, which converts between the enum and the class's own copy of it, which Godot sees. Your function keeps the plain enum type. See `gd++ man enums`.

# Doc comments

```gd++
/// Deals [param damage] to the player.
/// Returns [code]true[/code] if the player died.
func hurt(damage: int) -> bool { ... }
```

A doc comment before a function becomes its description in the editor's help. Annotations and the doc comment can come in any order. See `gd++ man docs`.

# Examples

```gd++
class_name Inventory
extends Node

var items: Array[Item]

/// Adds an item, unless the inventory is full.
func add(item: Item, max_size: int = 20) -> bool {
  if (items.size() >= max_size) {
    return false;
  }
  items.push_back(item);
  return true;
}

@const
func total_price() -> int {
  int64_t total = 0;
  for (int64_t i = 0; i < items.size(); i++) {
    Ref<Item> item = items[i];
    total += item->get_price();
  }
  return total;
}

@static
func max_items() -> int {
  return 20;
}

@virtual
func _accepts(item: Item) -> bool {
  return true;
}
```
