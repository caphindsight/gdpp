Rewrites: GD++'s additions to C++ code

C++ code in a GD++ file is plain C++, with a handful of exceptions: rewrites. GD++ adds them to C++, and turns them into plain C++ before the compiler sees the code. This page lists them, why they exist, and where they apply.

# The rewrites

```
emit NAME(ARGS)                (void) NAME(ARGS)                  send a signal, see `gd++ man signals`
rpc NAME(ARGS)                 _gdpp_rpc_NAME(0, ARGS)            call an RPC on every peer, see `gd++ man rpc`
rpc(PEER) NAME(ARGS)           _gdpp_rpc_NAME(PEER, ARGS)         call an RPC on one peer
is_cancelled                   gdpp::is_cancelled()               test whether a task should stop, see `gd++ man async`
string_name "NAME"             GDPP_STRING_NAME("NAME")           a StringName created once, see `gd++ man runtime`
is_done TASK                   TASK.is_done()                     test whether an Async holds a task that's done
claim TASK                     TASK.claim()                       take an Async's result
cancel TASK                    TASK.cancel()                      ask an Async's task to stop
await VALUE                    co_await VALUE                     wait for a task or a value, in an @async function, see `gd++ man async`
await OBJECT->NAME             co_await gdpp::signal<"NAME">(     wait for a signal, in an @async function, and get its
                                 OBJECT)                          arguments with their types
await NAME                     the same, on this                  wait for a signal of this class
return                         co_return                          in an @async function, but not in its lambdas
create T                       gdpp::create<T>()                  create an object, see `gd++ man classes`
destroy OBJECT                 gdpp::destroy(OBJECT)              delete an object, or give it back to its pool
queue_destroy NODE             gdpp::queue_destroy(NODE)          destroy a node at the end of the frame
VALUE as T                     gdpp::cast<T>(VALUE)               convert a value to the type T, see `gd++ man cast`
callable NAME                  gdpp::callable_method(this,        a Callable of a function of this class, see "Callables" below
                                 &This::NAME)
callable T::NAME               gdpp::callable_method(this,        a Callable of a static function, or a method of a base T
                                 &T::NAME)
callable OBJECT->NAME          gdpp::callable_member(OBJECT, ...) a Callable of a method of another object
callable "NAME"                gdpp::callable_name(this,          a Callable that calls a method by name, e.g. a script's
                                 GDPP_STRING_NAME("NAME"))
callable OBJECT->"NAME"        gdpp::callable_name(OBJECT, ...)   the same, on another object
callable LAMBDA                gdpp::callable(this, LAMBDA)       a Callable of a lambda, owned by this
callable(OWNER) LAMBDA         gdpp::callable(OWNER, LAMBDA)      a Callable of a lambda, owned by OWNER
assert COND;                   GDPP_ASSERT("COND", COND);         check what must be true, see below
assert_void COND;              GDPP_ASSERT_VOID("COND", COND);    the fallbacks of assert, see below
assert_val COND;               GDPP_ASSERT_VALUE("COND", COND);
```

# Why

- They are rare on purpose, and mostly trivial: most just call a method.
- What they add is the look. These places stand out when you read the code:
  - Sending a signal, calling a remote function, and polling, stopping or awaiting a task look different from a plain function call.
  - `is_cancelled` reads like a flag.
  - `string_name "NAME"` reads like a typed literal.
  - A conversion reads like GDScript's.
  - Creating and deleting an object read alike for every class, pools included.
  - A `Callable` of anything, a function, a method, a name or a lambda, reads alike.
- `assert` does more: it returns from a function whose check fails, but only in debug builds. Plain C++ can only do that with `#ifdef`.
- The method calls work too, e.g. `task.is_done()`, if you prefer them.

# Where they apply

Rewrites only happen in C++ code, never in comments or strings. Each applies in its own places:

- `emit`: everywhere. So it's reserved: don't use `emit` as a name in your C++ code, and don't call methods named `emit`, e.g. `Signal::emit`.
- `is_cancelled`: everywhere except as a member, e.g. `state.is_cancelled`, a name in a scope, e.g. `gdpp::is_cancelled`, or a call, e.g. `is_cancelled()`. So it's reserved too: a variable or field named `is_cancelled` doesn't compile.
- `rpc`: only when a call follows it, or a peer in parentheses and then a call. Elsewhere it's left alone, e.g. in Godot's own `rpc("ping")`.
- `string_name`: only when a string literal follows it, e.g. `string_name "update"`, and after `await`, when `(` follows it, e.g. `await string_name(name)`. Elsewhere it's left alone, e.g. a variable named `string_name`.
- `await`: where a name or `(` follows it, and it isn't a member. Elsewhere it's left alone, e.g. in `x.await` or `await = 1`. It's for `@async` functions: elsewhere, GD++ reports it. "Awaiting signals" in `gd++ man async` lists its forms.
- `return`: in the body of an `@async` function, outside of lambdas.
- `is_done`, `claim` and `cancel`: only when a name follows them. Elsewhere they're left alone, e.g. a variable named `claim`, or the call `task.is_done()`.
- `create`, `destroy` and `queue_destroy`: only when a name follows them, and they aren't members. Elsewhere they're left alone, e.g. in `Image::create(...)`, or a call of your own function `create(5)`.
- `as`: only when a value comes before it and a type after it.
- `callable`: only when a name, a string, `[` or `(` follows it, and it isn't a member. In `callable(...)`, only when a name or `[` follows the `)`. And not when the name is called, e.g. `callable f(1)`. Elsewhere it's left alone, e.g. in `Callable callable = f;` or `callable.call()`.
- `assert`, `assert_void` and `assert_val`: only where they start a statement, followed by a condition and a `;`. The condition must start with a name, a literal, `(`, `!`, `*` or `&`. Elsewhere they're left alone, e.g. in `s.assert(x);` or `assert = 1;`.

Avoid the names of all rewrites as names in your C++ code.

Shaders and shader blocks are GLSL, not C++, so none of these rewrites apply in them. Their copy for the CPU has rewrites of its own, which turn GLSL into C++, e.g. of swizzles such as `v.xy`. See "Without a GPU" in `gd++ man shaders`.

Their operands:

- NAME may have objects before it, joined by `->` or `.`, e.g. `rpc other->take_damage(5)`. The objects must be named by variables, not by function calls.
- TASK is a name, followed by any member accesses, scopes, calls and subscripts, e.g. `pending`, `this->tasks[i]` or `find_path(a, b)`.
  - Like C++'s own prefix operators, the rewrite applies to all of it: `claim find(a).size()` claims the result of `find(a).size()`. Write `(claim find(a)).size()` to call `size` on the result.
  - TASK must start with a name: `claim (a ? x : y)` isn't rewritten. Write `(a ? x : y).claim()` then.
- T is a class name, maybe in a scope, e.g. `Bullet`, `This` or `godot::Mesh`.
- OBJECT and NODE are like TASK, e.g. `bullet` or `this->bullets[i]`.
- VALUE is like TASK, but may also be in parentheses, e.g. `body`, `get_node("Mesh")` or `(a + b)`.
  - `as` binds it like a C++ postfix operator: `a + b as float` converts `b` only.
  - T is a type, e.g. `int`, `Gd<Node3D>` or `Node3D *`.
  - `as` is only rewritten where both are clear. In `x as int * y` or `(int) x as float`, it stays, and the code doesn't compile. Parentheses fix it, e.g. `(x as int) * y`. See `gd++ man cast`.

- In `callable`, OBJECT is a chain of names joined by `->` or `.`, like the objects of `rpc`, e.g. `hud->score`. LAMBDA is a C++ lambda, e.g. `[this](int x) { ... }`. After `callable(OWNER)`, it can also be a name, e.g. a variable that holds a lambda.
  - `callable` applies to the whole name, like the prefix rewrites above: `(callable on_hit).bind(5)` binds an argument.

Other facts:

- Rewrites also apply to the C++ that macros generate. GD++ expands macros first. See `gd++ man macros`.
- A rewrite keeps the code's line breaks. So line numbers in errors still match the GD++ file.
- In an `@async` function, `string_name "NAME"` becomes `gdpp::string_name<"NAME">()` instead, which does the same without a lambda, since a coroutine's frame can't hold one.
- `gd++ cat` and the code in this manual highlight the rewrites as keywords: `is_done`, `claim`, `cancel`, `create`, `destroy`, `queue_destroy` and `as` only where a name follows them, `string_name` only where a string follows it, or `(` in an await, and `callable` only where a name, a string, `[` or `(` follows it.

# Callables

`callable` makes a `Callable` of anything that can be called, e.g. to connect a signal, or for a tween or a timer:

```gd++
on ready {
  button->connect(string_name "pressed", callable start);            // a function of this class
  hud->connect(string_name "closed", callable hud->queue_free);      // a method of another object
  timer->connect(string_name "timeout", callable "_on_timeout");     // a method by name, e.g. a script's
  tween->tween_callback(callable [this] { set_visible(false); });     // a lambda
}

func adder(n: int) -> Callable {
  return callable [n](int x) -> int { return x + n; };
}
```

A function or a method:

- `callable NAME`: a function of this class or its bases, e.g. `callable start` or `callable queue_free`. In a `@static` function, only a `@static` function.
- `callable T::NAME`: a static function of the class T, e.g. `callable Bullet::spawn`, or a method of T, a base of this class.
- `callable OBJECT->NAME`: a method of another object, held by a `Gd`, a pointer, a `Ref` or a `Weak`. On an extern or a trait, it calls the method by name, since its class isn't known to C++.
- Unlike godot-cpp's `callable_mp`, it doesn't need the class's name, and it works for every kind of function.

A method by name, which C++ doesn't know, e.g. a script's:

- `callable "NAME"`: of this object.
- `callable OBJECT->"NAME"`: of another object.
- The name is a `StringName` created once, like `string_name "NAME"`.

A lambda:

- `callable [CAPTURES](PARAMS) { ... }`: a `Callable` that runs the lambda. Its parameters get the call's arguments, converted to their types, and its result is the call's.
- The lambda belongs to this object: once the object is freed, Godot drops the lambda's signal connections, and calls of it do nothing.
- `callable(OWNER) LAMBDA` makes it belong to OWNER instead, e.g. `callable(enemy) [] { ... }`, or to nothing with `callable(nullptr) LAMBDA`. In a `@static` function, it belongs to nothing.
- The lambda's parameters need types: `auto` doesn't work, since the `Callable` converts the arguments to them.
- Captures are C++'s. Capture `this` to use the object's members, and values by copy, e.g. `[this, n]`: the lambda runs later, once local variables are gone.

`callable` takes no arguments to bind. Call `bind` on the result, in parentheses: `(callable on_hit).bind(5)`.

# Assertions

An assertion checks something that must always be true:

```gd++
func fire() -> void {
  assert target != nullptr;
  look_at(target->get_global_position());
}
```

In debug builds, if the condition is false:

- The assertion prints an error, and returns from the function.
- A function that returns a value returns the type's default, e.g. `0`, `nullptr` or an empty `String`.
- The error shows the condition. Below it, Godot shows where the assertion is in the GD++ file:

```
Failed GD++ assertion: `target != nullptr`.
```

- With `gd++ build --trace`, the error is also a trace line, with the place, among the calls that led to it. See "Failed assertions" in `gd++ man debugging`.

A failed assertion is always undefined behavior, in debug builds too:

- GD++ tries hard to keep the game from crashing, and to let it go on sensibly, so you can find the bug and fix it.
- But the code around the assertion was written for a true condition. The function stops halfway, and its caller gets a default value it may not expect.
- So nothing that happens after a failed assertion is promised.
- To check a condition in a well-defined way, e.g. whether a file exists, use a plain `if`. An assertion's advantage over an `if` is that it costs nothing in release builds.

In release builds:

- Assertions are gone. The condition isn't evaluated, and the code goes on as if it were true.
- So the condition must not do anything that the code needs, e.g. call a function for its effect.
- It must still compile.

In a test, a failed assertion also fails the test, even in code that the test calls. See `gd++ man tests`.

C++'s own `assert(x);` is an assertion too: GD++ rewrites it like `assert x;`. So GD++ code never uses the `assert` macro of `<cassert>`.

How an assertion returns:

- GD++ turns an assertion into a call of one of the runtime's macros, which gets the condition's text too, e.g. `GDPP_ASSERT_VOID("target != nullptr", target != nullptr);`.
- The macro depends on what the surrounding code returns, since its `return` must match: `return;` in a `void` function, a value in one that returns a value.
- GD++ works this out, so that `assert` just works:
  - In functions, getters, setters and other code that GD++ wraps in a function, GD++ knows what the code returns.
  - In a lambda, GD++ reads the lambda's return type, e.g. `-> int`, `-> int &` or `-> void`. A lambda without one returns `void`.
  - In a constructor or destructor, in `decl` and `impl` blocks, or in a class within a function, GD++ knows that it returns nothing.
  - In other functions in `decl` and `impl` blocks, or in a class within a function, the runtime's `GDPP_ASSERT` finds out from the function's signature at compile time.

# Where C++ gets in the way

A few cases can't be handled, because of how C++ works:

- A lambda or function without a return type, e.g. `[](int x) { return x * 2; }` or `auto twice(int x) { ... }`, gets its type from its `return` statements.
  - An assertion's `return` would need a value of that type, and the code can't name it.
  - So an assertion there doesn't compile. The error says to write the return type, e.g. `[](int x) -> int { ... }`.
  - Only a problem if it returns a value. A lambda without a return type that returns nothing is fine.
- GD++ reads C++ code before the preprocessor does. It can't see a lambda that a macro writes, e.g. `CALLBACK(int x) { ... }` with `#define CALLBACK(...) [&](__VA_ARGS__)`. An assertion there returns like the code around the lambda, which may not compile.
- `GDPP_ASSERT` needs a compiler that tells it the function's signature: GCC, Clang or MSVC. With another one, an assertion where `GDPP_ASSERT` is used doesn't compile, and the error says what to do.

The fallbacks, a last resort for the last two cases:

- `assert_void COND;` and `assert_val COND;` are like `assert COND;`, but always return as from a function that returns `void` or a value.
- Use them only where `assert` doesn't work:

```gd++
#define CALLBACK(...) [&](__VA_ARGS__)
auto print = CALLBACK(int x) { assert_void x != 0; };
```

# Trailing commas

- In C++ code, a call's arguments may end with a comma, like in GDScript: `f(a, b,)` becomes `f(a, b)`.
- This helps when each argument is on its own line.
- GD++ drops any `,` right before `)`. So avoid macro calls with an empty last argument, e.g. `M(a,)`.

# Seeing them

`gd++ trans FILE` prints the generated C++, with every rewrite done. This function:

```gd++
func poll() -> void {
  assert score >= 0;
  if (is_done pending && !is_cancelled) {
    emit found(claim pending, score as int32_t);
  }
  rpc(1) report(score);
  call(string_name "refresh");
}
```

becomes, apart from the `#line` directives:

```cpp
void Pathfinder::poll() {
  GDPP_ASSERT_VOID("score >= 0", score >= 0);
  if (pending.is_done() && !gdpp::is_cancelled()) {
    (void) found(pending.claim(), gdpp::cast<int32_t>(score));
  }
  _gdpp_rpc_report(1, score);
  call(GDPP_STRING_NAME("refresh"));
}
```

# Other names

`This` and `gd` aren't rewrites. Both are plain C++:

- `This`: a macro for the current class's name.
- `gd`: an alias of `UtilityFunctions`.

See `gd++ man code`.
