Rewrites: emit, rpc, is_cancelled, string_name, is_done, claim, cancel, as and assert, GD++'s additions to C++ code

C++ code in a GD++ file is plain C++, with a handful of exceptions: rewrites, which GD++ adds to C++, and turns into plain C++ before the compiler sees the code. This page lists them, says why they exist, and where they apply.

# The rewrites

GD++ extends C++ with a few rewrites, which it turns into plain C++:

```
emit NAME(ARGS)                (void) NAME(ARGS)                  send a signal, see `gd++ man signals`
rpc NAME(ARGS)                 _gdpp_rpc_NAME(0, ARGS)            call an RPC on every peer, see `gd++ man rpc`
rpc(PEER) NAME(ARGS)           _gdpp_rpc_NAME(PEER, ARGS)         call an RPC on one peer
is_cancelled                   gdpp::is_cancelled()               test whether a task should stop, see `gd++ man async`
string_name "NAME"             GDPP_STRING_NAME("NAME")           a StringName created once, see `gd++ man runtime`
is_done TASK                   TASK.is_done()                     test whether an Async holds a task that's done
claim TASK                     TASK.claim()                       take an Async's result
cancel TASK                    TASK.cancel()                      ask an Async's task to stop
VALUE as T                     gdpp::cast<T>(VALUE)               convert a value to the type T, see `gd++ man cast`
assert COND;                   GDPP_ASSERT("COND", COND);         check what must be true, see below
```

# Why

They are rare on purpose, and mostly trivial: most just call a method. What they add is the look. Sending a signal, calling a remote function, and polling or stopping a task look different from a plain function call, `is_cancelled` reads like a flag, `string_name "NAME"` reads like a typed literal, and a conversion reads like GDScript's. So these places stand out when you read the code. `assert` does more: it returns from a function whose check fails, but only in debug builds, which plain C++ can only do with `#ifdef`. The method calls work too, e.g. `task.is_done()`, if you prefer them.

# Where they apply

Rewrites only happen in C++ code, never in comments or strings. Each rewrite applies in its own places:

- `emit` is rewritten wherever it stands as a word, so it's reserved: don't use `emit` as a name in your C++ code, and don't call methods named `emit`, e.g. `Signal::emit`.
- `is_cancelled` is rewritten wherever it isn't a member, e.g. `state.is_cancelled`, a name in a scope, e.g. `gdpp::is_cancelled`, or a call, e.g. `is_cancelled()`. So it's reserved too: a variable or field named `is_cancelled` doesn't compile.
- `rpc` is only rewritten when a call follows it, or a peer in parentheses and then a call. Elsewhere it's left alone, e.g. in Godot's own `rpc("ping")`.
- `string_name` is only rewritten when a string literal follows it, e.g. `string_name "update"`. Elsewhere it's left alone, e.g. a variable named `string_name`.
- `is_done`, `claim` and `cancel` are only rewritten when a name follows them. Elsewhere they're left alone, e.g. a variable named `claim`, or the call `task.is_done()`.
- `as` is only rewritten when a value comes before it and a type after it.
- `assert` is only rewritten where it starts a statement, and a condition and then a `;` follow it. The condition must start with a name, a literal, `(`, `!`, `*` or `&`. Elsewhere it's left alone, e.g. in `s.assert(x);` or `assert = 1;`.

Avoid the names of all rewrites as names in your C++ code. Their operands:

- NAME may be written with objects before it, joined by `->` or `.`, e.g. `rpc other->take_damage(5)`. The objects must be named by variables, not by function calls.
- TASK is a name, followed by any member accesses, scopes, calls and subscripts, e.g. `pending`, `this->tasks[i]` or `find_path(a, b)`. Like C++'s own prefix operators, the rewrite applies to all of it: `claim find(a).size()` claims the result of `find(a).size()`, so write `(claim find(a)).size()` to call `size` on the result. TASK must start with a name: `claim (a ? x : y)` isn't rewritten, so write `(a ? x : y).claim()` then.
- VALUE is like TASK, but may also be in parentheses, e.g. `body`, `get_node("Mesh")` or `(a + b)`. `as` binds it like a C++ postfix operator, so `a + b as float` converts `b` only. T is a type, e.g. `int`, `Node3D *` or `Ref<Mesh>`. `as` is only rewritten where both are clear: in `x as int * y` or `(int) x as float`, it stays, so the code doesn't compile, and parentheses fix it, e.g. `(x as int) * y`. See `gd++ man cast`.

A rewrite keeps the code's line breaks, so the line numbers in errors still match the GD++ file.

`gd++ cat` and the code in this manual highlight the rewrites as keywords: `is_done`, `claim`, `cancel` and `as` only where a name follows them, and `string_name` only where a string follows it.

# Assertions

An assertion checks something that must always be true:

```gd++
func fire() -> void {
  assert target != nullptr;
  look_at(target->get_global_position());
}
```

In debug builds, if the condition is false, the assertion prints an error and returns from the function. A function that returns a value returns the type's default, e.g. `0`, `nullptr` or an empty `String`. The error shows the condition and where the assertion is in the GD++ file, and a second line says what a failed assertion means:

```
Failed GD++ assertion: `target != nullptr`, at player.gd++:2.
Failed GD++ assertions are undefined behavior and must be fixed.
```

A failed assertion is always undefined behavior, in debug builds too. GD++ tries hard to keep the game from crashing and to let it go on sensibly, so you can find the bug and fix it. But the code around the assertion was written for a true condition: the function stops halfway, and its caller gets a default value it may not expect. So nothing that happens after a failed assertion is promised.

To check a condition in a well-defined way, e.g. whether a file exists, use a plain `if`. What an assertion has over an `if` is that it costs nothing in release builds.

In release builds, assertions are gone: the condition isn't evaluated, and the code goes on as if it were true. So the condition must not do anything that the code needs, e.g. call a function for its effect. It must still compile, though.

C++'s own `assert(x);` is an assertion too: GD++ rewrites it like `assert x;`. So GD++ code never uses the `assert` macro of `<cassert>`.

GD++ turns an assertion into a call of one of the runtime's macros, which gets the condition's text too. In functions, getters, setters and other code that GD++ wraps in a function, GD++ knows what the code returns, and picks `GDPP_ASSERT_VOID` or `GDPP_ASSERT_VALUE`, e.g. `GDPP_ASSERT_VOID("target != nullptr", target != nullptr);`. In `decl` and `impl` blocks, it doesn't, so it uses `GDPP_ASSERT`, which finds out from the function's signature at compile time. There, an assertion doesn't compile in a constructor or destructor, or in a lambda that returns a value. With a compiler other than GCC, Clang or MSVC, `GDPP_ASSERT` only prints the error, and doesn't return.

# Trailing commas

In C++ code, a call's arguments may end with a comma, like in GDScript: `f(a, b,)` becomes `f(a, b)`. This helps when each argument is on its own line. GD++ drops any `,` right before `)`, so avoid macro calls with an empty last argument, e.g. `M(a,)`.

# Seeing them

`gd++ trans FILE` prints the generated C++, with every rewrite done. E.g. this function:

```gd++
func poll() -> void {
  assert score >= 0;
  if (is_done pending && !is_cancelled) {
    emit found(claim pending, score as int32_t);
  }
  rpc(1) report(score);
  call(string_name "refresh");
}
```

becomes, apart from the `#line` directives:

```cpp
void Pathfinder::poll() {
  GDPP_ASSERT_VOID("score >= 0", score >= 0);
  if (pending.is_done() && !gdpp::is_cancelled()) {
    (void) found(pending.claim(), gdpp::cast<int32_t>(score));
  }
  _gdpp_rpc_report(1, score);
  call(GDPP_STRING_NAME("refresh"));
}
```

# Other names

`This` and `gd` aren't rewrites: `This` is a macro for the current class's name, and `gd` an alias of `UtilityFunctions`, both plain C++. See `gd++ man code`.
