Includes: automatic #include lines

In GD++, you don't write `#include` lines.

- GD++ knows which header declares each name of godot-cpp and of your package.
- It finds the names your code uses, and includes their headers.
- To use a class, just use it.

This page covers how that works, and the rare cases where it doesn't.

# Where the names come from

Before transpiling a package, GD++ scans every header of the package's godot-cpp, hand-written and generated from the API spec. It lists every name declared directly in namespace `godot`, with its header: classes, structs, enums, aliases, templates, functions and variables. E.g.:

```
Node3D           <godot_cpp/classes/node3d.hpp>
TypedArray       <godot_cpp/variant/typed_array.hpp>
UtilityFunctions <godot_cpp/variant/utility_functions.hpp>
memnew           <godot_cpp/core/memory.hpp>
```

- It adds the classes, externs and enums of the package's GD++ files, each with its generated header, e.g. `"Player.h"`.
- The list is cached in the package's build cache.
- `gd++ doc NAME` shows a name's header.

See `gd++ man doc` and `gd++ man build-cache`.

# Which names are included

GD++ reads every identifier in a class, and includes the header of each one it knows:

- In the class's header:
  - the base class,
  - the types in the class's API: variables, function parameters and return values, signal parameters,
  - imported names,
  - every identifier in `decl` and `@global decl` blocks, and in the `decl` blocks of properties.
- In the class's source file, unless the header includes it already:
  - every identifier in function bodies, default values, initial values, `get` and `set` blocks, `ctor`, `dtor` and `on` blocks, and `impl` and `@global impl` blocks.

Facts:

- Using a class anywhere, even only in code, e.g. `node as MeshInstance3D *` or `memnew(Timer)`, includes it.
- The match is by name only. A variable of yours named like a Godot class includes that class too, which is harmless.
- Every generated file also includes the GD++ runtime header. It includes godot-cpp's core headers and a few basic classes, e.g. `Object`, `Node`, `RefCounted`, `Resource` and `Engine`. See `gd++ man runtime`.

# GD++ classes and cycles

GD++ files can use each other freely, even in cycles: `Player` can have a `var` of type `Enemy`, and `Enemy` one of type `Player`.

- In headers, GD++ declares other GD++ classes, externs and enums ahead (`class Enemy;` or `enum class Suit : int64_t;`), and includes their headers at the end. That breaks the cycle.
- A name is included at the top when the header needs its definition: the base class, the types of `@virtual` functions, and names in `decl` blocks.
- So fields of GD++ class types in `decl` blocks can create include cycles that don't compile. Prefer pointers, and variables declared with `var`.

# import

```gd++
import MeshInstance3D
```

- Forces the header of a name into the class's header, even if the class doesn't seem to use it.
- Goes in a class body, like a member.
- Needed when code uses a class without ever writing its name, which only happens through `auto`, templates or macros:

```gd++
import Material

func tint(mesh: MeshInstance3D) -> void {
  auto material = mesh->get_active_material(0);                    // Ref<Material>
  auto standard = material as Ref<StandardMaterial3D>;
  ...
}
```

- Here, `StandardMaterial3D` is written, so it's included anyway. `Material` is only used through `auto`. Without `import Material`, the compiler may complain about an incomplete type.
- For an enum, `import` also makes the class expose the enum to Godot. See `gd++ man enums`.
- Only classes, externs, enums and godot-cpp's other names can be imported. Built-in types, e.g. `int` or `Vector3`, can't, since their headers are always included:

```out
[×] res://a.gd++:3:8: Built-in type Vector3 can't be imported.
     3 | import Vector3
       |        ^^^^^^^
    Hint: Only classes, externs and enums have includes.
```

# noimport

```gd++
noimport MeshInstance2D
```

- Stops the class from including the header of a name, in its header and its source file, even if the class uses it.
- This almost always breaks compilation. It's allowed, e.g. to include another version of a header yourself, or to work around a conflict.
- For an enum, it stops the class from exposing the enum to Godot. It's an error if the class uses the enum in its API. See `gd++ man enums`.

# Including other headers

For headers that GD++ doesn't know, e.g. the C++ standard library, other libraries, or the package's plain C++ headers:

- Write `#include` in a `@global decl` block.
- Or in a `@global impl` block, if only the source file needs it.
- Paths in quotes are relative to the package root. Paths in angle brackets are relative to the project root. Both also find the generated code.

```gd++
@global decl {
  #include <vector>
  #include "src/pathfinding.h"
}
```

See `gd++ man code` and `gd++ man packages`.

# Outside of packages

`gd++ trans` outside of a package knows only the names you declare with its options, e.g. `--object Node3D`, or the classes of a spec, with `--spec`. See `gd++ man trans`.
