Async: @onthread, @async, await and Async tasks

Some work is too slow for one frame: finding a path, generating terrain, loading and parsing a file. Other work waits for things to happen: an animation to end, a timer, a player to enter an area.

- `@onthread` runs a function on another thread.
- `@async` makes a function a coroutine, which can `await` signals and other tasks, like GDScript's `await`.
- Both kinds of call return right away, with an `Async`: a task that tells when the work is done, and holds its result.

# A first example

```gd++
class_name Pathfinder
extends Node2D

var target: Vector2
var pending: Async[PackedVector2Array]

@onthread
func find_path(from: Vector2, to: Vector2) -> PackedVector2Array {
  PackedVector2Array path;
  // ... a long search, on a worker thread ...
  return path;
}

on ready {
  pending = find_path(get_position(), target);
}

on process(delta: float) {
  if (is_done pending) {
    follow(claim pending);
    pending = find_path(get_position(), target);
  }
}

func follow(path: PackedVector2Array) -> void { ... }
```

- `on ready` starts the first search.
- Each frame, `on process` checks whether `pending` holds a search that's done.
- Then `claim` takes the path out of `pending`, and `on process` starts the next search, which runs while the game goes on.
- No frame waits for a search.

Scripts call the function the same way, and get a task object. Its `done` property and `claim()` method work like `is_done` and `claim`:

```gdscript
var task = $Pathfinder.find_path(position, goal)
# ... later, e.g. in _process:
if task.done:
    follow(task.claim())
```

# @onthread

- Every call of the function, from C++ or from scripts, runs its body on Godot's `WorkerThreadPool`.
- The task is named after the class and the function, e.g. "Pathfinder.find_path".
- The call only starts the task, and returns an `Async` of the function's type:

```
The function is declared as          Callers get
@onthread func f() -> int            Async[int]
@onthread func f() -> Node           Async[Node]
@onthread func f() -> void           Async[void], a task without a result
@onthread func f()                   Async, whose result is a Variant
```

- The body is written for the plain type: it returns an `int`, a `Node`, nothing, or a `Variant`.
- GD++ adds the `Async`. Writing it yourself is an error:

```out
[×] res://pathfinder.gd++:4:13: The @onthread function f already returns an Async: write -> int.
     4 | func f() -> Async[int] {}
       |             ^^^^^
    Hint: Its callers get an Async of the type its body returns.
```

Shaders take `@async` too: the call then returns an `Async` of the shader's result, done once the GPU is done, with no thread waiting for it. See "Not waiting at all: @async" in `gd++ man shaders`.

An `@onthread` function:

- can be `@static` or `@const`, and have default values,
- can use `@trace` and `@profile`, which follow its body, on its thread,
- can't be `@virtual` or `@override`, since the engine or a script would replace the function that starts the task,
- can't be `@rpc`, `@deferred` or `@thread_safe`,
- exists only in classes. An extern declares that a function returns an `Async` instead. See "Across packages" below.

For work whose result nobody waits for, see `@onthread("detached")` below. For work that waits for signals, see `@async` below.

# @onthread("detached")

Some work has no result that anyone waits for: saving a game, writing a log, sending a report. `@onthread("detached")` runs it on a worker thread too, but its calls return nothing. There's no task to keep, test or claim.

```gd++
@onthread("detached")
func save_game(slot: int, data: Dictionary) -> void {
  // ... write the file, on a worker thread ...
}

func _on_save_pressed() -> void {
  save_game(1, collect_data());   // Returns right away.
}
```

- The function must return `void`, and so does each call, from C++ or from scripts.
- Once the body is done, the task schedules a deferred call, on the main thread, that does the wait that Godot requires for each `WorkerThreadPool` task. Since that wait comes after the body, it doesn't block.
- In all else, it's an `@onthread` function:
  - The same annotations combine with it.
  - The body has the same limits. See "Writing the body" below.
  - A refcounted object it's called on stays alive until the body has run.
- Its body can check `is_cancelled`, which only becomes `true` when the game quits, since nothing can cancel it without an `Async`.
- When the game quits, it gets the same grace period as other tasks.
- A non-void return type is an error:

```out
[×] res://saver.gd++:2:1: The @onthread("detached") function save_game must return void.
     2 | func save_game(slot: int) -> bool {
       | ^^^^
    Hint: Nothing waits for its task, so its calls can't return a value.
```

# @async and await

An `@async` function is a coroutine: its body can wait for a signal, or for another task, with `await`, like in GDScript. Waiting doesn't block: the function returns to its caller, and goes on where it stopped once the signal comes.

```gd++
class_name Door
extends Node3D

var anim: AnimationPlayer

@async
func open() -> void {
  anim->play("open");
  await anim->animation_finished;
  await get_tree()->create_timer(2.0)->timeout;
  anim->play("close");
}

on ready {
  open();   // returns at the first await
}
```

- A call runs the body right away, on the caller's thread, until the first `await` that waits. Then it returns an `Async`, like an `@onthread` function.
- The body goes on when the signal comes, on the thread that emits it, which is the main thread for most signals.
- The `Async` is done once the body returns, and holds what it returned.
- Like with `@onthread`, the body is written for the plain type, and GD++ adds the `Async`. `-> Async[int]` is an error: write `-> int`.
- A coroutine needs C++20. With an older C++ standard, `@async` and `await` are errors. See `gd++ man packages`.
- `await` in a function without `@async` is an error: "Function f awaits, so it needs @async."

An `on` block can be `@async` too, e.g. `@async on ready { ... }`. Nothing waits for it. Don't make the per-frame blocks, e.g. `on process`, `@async`: each frame would start another coroutine. See "Awaiting in on blocks" in `gd++ man notifications`.

An `@async` function:

- can be `@static`, `@const`, `@virtual`, `@trace`, `@game_only` and `@editor_only`. `@trace` prints the call when it starts, marked "(coroutine)". It prints no end, and no changes of the class's `@trace` variables, since the coroutine outlives the call.
- can't be `@onthread`, `@deferred`, `@thread_safe`, `@rpc` or `@profile`, whose time would span its awaits.
- can `@override` an `@async` `@virtual` function of a GD++ class, but no function of the engine, which doesn't take an `Async`. For a notification, write an `@async` `on` block instead, e.g. `@async on ready`. Else call an `@async` function from the override.
- uses `return` like any function. GD++ makes it `co_return`, but not in lambdas.

`@async("detached")`, for a function that returns `void`: calls return nothing, like `@onthread("detached")`. `Async` is `[[nodiscard]]`, so this is the way to start a coroutine without keeping its task:

```gd++
@async("detached")
func flash() -> void {
  set_visible(false);
  await get_tree()->create_timer(0.1)->timeout;
  set_visible(true);
}
```

Without `"detached"`, a call whose `Async` isn't kept makes the compiler warn. Dropping the `Async` doesn't stop the coroutine, though: it goes on without it. See "Coroutines' lifetimes" below.

# Awaiting signals

`await` waits for a signal, and gives its arguments, like GDScript's `await`:

```
await OBJECT->NAME;                         signal NAME of OBJECT, e.g. await anim->animation_finished
await NAME;                                 signal NAME of this class
await OBJECT->string_name "NAME";           signal NAME of OBJECT, named by a string
await string_name "NAME";                   signal NAME of this object, named by a string
await OBJECT->string_name(EXPR);            the signal of OBJECT whose name EXPR gives, a String or StringName
await string_name(EXPR);                    the signal of this object whose name EXPR gives
await SIGNAL;                               a Signal value, e.g. Signal(button, "pressed")
```

- OBJECT is a pointer, a `Ref` or a `Gd`, e.g. `anim`, `get_tree()->create_timer(1.0)` or `this`.
- A signal without arguments gives nothing. One with one argument gives it, and one with more gives an `Array` of them. The type is `Variant`:

```gd++
Variant body = await area->body_entered;
Array names = await anim->animation_changed;   // its old name and its new one
```

- `string_name` names signals that the first form can't, e.g. a signal of a base class that GD++ doesn't know, or one whose name is computed at runtime, e.g. `await enemy->string_name("died_" + kind)`.
- A missing object, or an object without the signal, prints an error, and `await` gives `null` right away.
- The object's class must be complete in C++. GD++ includes the classes that the code names, but not those it only reaches through calls, e.g. `Tween` in `await create_tween()->finished`. Then add `import Tween`. See `gd++ man includes`. `SceneTreeTimer`, for `await get_tree()->create_timer(1.0)->timeout`, is always included.

How GD++ tells a signal from a task:

- `await X->NAME`, where a name follows the last `->` and nothing follows the name, awaits a signal.
- `await NAME` awaits a signal if the class declares one named NAME, else the value of NAME, e.g. a task in a variable.
- Everything else awaits a value: a task, a `Signal`, a `Variant`, e.g. `await task`, `await find(a)` or `await state.task`.
- So to await a task in a field through `->`, write `await task` or `await (this->task)`.

# Awaiting tasks and values

`await` on an `Async` waits until its task is done, and gives its result, which it keeps, like `TASK.result()`:

```gd++
@async
func load_level() -> int {
  PackedVector2Array path = await find_path(start, goal);   // an @onthread function's task
  int coins = await count_coins();                          // another @async function's task
  return coins;
}
```

- A task that's done already gives its result right away.
- Else, the coroutine goes on at the end of the frame in which the task got done, on the main thread.
- An empty or claimed `Async` prints an error, and gives the type's default value.

`await` on a `Variant` works like GDScript's `await`:

- a task, of any package: until it's done, and gives its result,
- a `Signal`: until it's emitted, and gives its arguments,
- the state of a GDScript function that awaits: until the function returns, and gives what it returned,
- anything else: right away, and gives the value.

So GD++ code can await script functions that await, or not:

```gd++
Variant level = await loader->call("load_level", "forest");
```

# @async in scripts

Scripts get a task object from `@async` functions, like from `@onthread` ones. To wait for it, await `until_done()`:

```gdscript
var coins = await $Level.count_coins().until_done()
```

- `until_done()` returns a signal that's emitted once the task is done, with its result. It works whenever the script calls it, also after the task is done.
- `await task` alone doesn't wait. GDScript only waits for signals and its own functions, so it gives the task object right away.
- The task object also has a `finished` signal, emitted once, at the end of the frame in which the task got done. To await a task that may be done already, use `until_done()`.
- Await from the main thread, where the signals come.

`@virtual @async` functions can be overridden by scripts, with or without `await`:

```gd++
@virtual @async
func _open() -> bool {
  await anim->animation_finished;
  return true;
}
```

```gdscript
func _open():
    await $Lock.unlocked
    return true
```

- The function returns an `Async[bool]` in GD++ code, whichever runs.
- Scripts see its return type as `Variant`, since a script function that awaits returns its state, not its result. The override's own type, e.g. `-> bool`, is fine.
- The task gets done when the script's function returns, with what it returned.

# Coroutines' lifetimes

A coroutine that waits belongs to the signal it waits for, not to its `Async`:

- Dropping the `Async` doesn't stop it, and doesn't wait for it. A coroutine whose `Async` nobody holds goes on, and its result is dropped.
- If the object the function was called on is refcounted, the coroutine keeps it alive.
- If the object the function was called on is freed while it waits, e.g. a node, the coroutine stops: its locals are destroyed, and the rest of its body never runs.
- The same happens if the object that would send the signal is freed first, e.g. an enemy whose `died` the coroutine awaits.
- A stopped coroutine's task is abandoned: it gets Claimed, and is never done. What awaits it stops too: other coroutines, and scripts' awaits, like with a freed object's signal in GDScript.
- When the package's library is unloaded, e.g. by a hot reload, its waiting coroutines stop the same way, since their code goes away.

`cancel` works on coroutines' tasks too: `is_cancelled` is `true` in the body from then on. Like with `@onthread`, it only asks: the body checks it, e.g. after each `await`.

# Async types

- `Async[T]`: a task whose result has type T.
- `Async[void]`: no result.
- A plain `Async`: a `Variant` result.
- A type like any other: variables, parameters, return values and signals can have it.
- It can be passed around and stored, like any refcounted object. Copies share the task.
- In C++: an `Async<T>`, e.g. `Async<int64_t>` for `Async[int]`.
- In Godot: an object of the package's class of tasks, e.g. `FooAsync` for a package whose prefix is `Foo`. See "The class of tasks" below.

```gd++
var pending: Async[PackedVector2Array]
signal started(task: Async[int])

func track(task: Async[int]) -> void { ... }
```

These uses are errors:

```
@export var task: Async[int]           Async variables can't be exported.
var tasks: Array[Async[int]]           Typed collections can't hold Async values. Use a plain Array.
var task: Async[Async[int]]            An Async can't have an Async result.
var task: Async[int, String]           Type Async takes one type argument, the type of its result.
```

# The three states

An `Async` goes through three states, in order, and never goes back:

1. Running: the body runs on a worker thread, or, for `@async`, it runs or awaits.
2. Done: the body has returned, and the task holds its result.
3. Claimed: the result was taken. A new `Async`, which never had a task, is Claimed too.

GD++ code uses a few rewrites and methods. Scripts get a task object, whose members do exactly the same:

```
GD++ code           Scripts             What it does
if (TASK)           task.valid          tells whether the task is Running or Done
is_done TASK        task.done           tells whether the task is Done
claim TASK          task.claim()        returns the result, and claims it
TASK.result()       task.result         returns the result, and keeps it
TASK.wait()         task.wait()         waits until the task is Done, then returns the result, and keeps it
cancel TASK         task.cancel()       asks the body to stop
await TASK          await task.until_done()   waits until the task is Done, without blocking, then returns the result, and keeps it
```

What each does in each state, in GD++ code and in scripts alike:

```
                              Running                    Done                             Claimed
if (TASK), task.valid         true                       true                             false
is_done TASK, task.done       false                      true                             false
claim TASK, task.claim()      error                      returns the result, and claims   error
TASK.result(), task.result    error                      returns the result               error
TASK.wait(), task.wait()      blocks, then returns it    returns the result               error
await                         waits, then returns it     returns the result               error
cancel TASK, task.cancel()    asks the body to stop      does nothing                     does nothing
```

Facts:

- Only `claim` makes the task Claimed. `result` and `wait` keep the result, so they return it as often as you like.
- To wait for the result and take it, call `wait`, then `claim`.
- `if (TASK)` and `task.valid`: the task has a result, or will have one.
- `is_done` and `task.done`: the task has a result right now.
- So the task is Running when it's valid, but not done.
- In scripts, test `task.valid`, not the task itself. `if task:` only tells that the variable holds a task object. A Claimed task object is still an object, so `if task:` is true for it, while `task.valid` is `false`.
- Errors:
  - In debug builds, an error prints a message, and returns the type's default value in GD++ code, e.g. `0` or an empty array, and `null` in scripts. The `Async` stays as it is.
  - Release builds don't check: an error is undefined behavior. Test the `Async` first.
- The result has the function's type in GD++ code, e.g. `PackedVector2Array` for an `Async[PackedVector2Array]`. In scripts, it's a `Variant`, and an enum result is an `int`.
- `wait` on the Running task of an `@async` function is an error: the coroutine may need the waiting thread, so it would never get Done. Await it instead.
- To act once a task is Done: await it, in an `@async` function or a script, or test `is_done`, e.g. once a frame.
- For `cancel`, see "Stopping tasks" below.

# In GD++ code

`if (TASK)`:

- Tests the `Async` like a pointer.
- Works in `if`, `while`, `!`, `&&` and `||`.
- To keep it in a variable, write `bool valid = bool(TASK);`.

`is_done`, `claim` and `cancel`:

- Rewrites, like `emit` and `rpc`.
- `is_done TASK`, `claim TASK` and `cancel TASK` become `TASK.is_done()`, `TASK.claim()` and `TASK.cancel()`.
- They make the places that poll, take and stop a task stand out. The method calls work too.
- TASK is a name, followed by any member accesses, scopes, calls and subscripts, e.g. `pending` or `this->tasks[i]`.
- The rewrite applies to all of TASK, like C++'s own prefix operators: `claim find(a).size()` claims the result of `find(a).size()`.
- See `gd++ man rewrites`.

`TASK.result()`:

- Reads the result of a done task, and keeps it. So it can be read again, e.g. by several functions that each look at it.
- No rewrite, since it doesn't change the `Async`.

Waiting:

- Godot requires waiting once for each `WorkerThreadPool` task. `claim` does it for you. Since the task is done, that doesn't block.
- `TASK.wait()` waits for real, and keeps the result. So `TASK.wait(); auto path = claim TASK;` waits for the result, then takes it.
- On the main thread, the game stops while it waits. Prefer `await` in an `@async` function, or testing `is_done` each frame.

A loop that keeps one search running, and follows each path it finds:

```gd++
on process(delta: float) {
  if (!pending) {
    pending = find_path(get_position(), target);
  } else if (is_done pending) {
    follow(claim pending);
  }
}
```

Once claimed, `pending` is `false`, so the next frame starts another search.

# In scripts

Scripts see an `Async` as an object of the class of tasks, e.g. `FooAsync`:

```
FooAsync, extends RefCounted
  valid: bool                          read-only, true while Running or Done, like `if (TASK)` in GD++ code
  done: bool                           read-only, true while Done, like `is_done TASK`
  result: Variant                      read-only, the result while Done, which it keeps, like `TASK.result()`
  claim() -> Variant                   take the result, while Done, like `claim TASK`
  wait() -> Variant                    wait until Done, then return the result, which it keeps
  cancel() -> void                     ask the body to stop, while Running
  until_done() -> Signal               a signal emitted once Done, with the result: `await task.until_done()`
  signal finished(result)              emitted once, at the end of the frame in which the task got Done
```

- Test `valid`, not the task object: `if task:` is true for any task object, even a Claimed one.
- To wait without blocking, await `until_done()`. See "@async in scripts" above.
- The property getters, `is_valid()`, `is_done()` and `get_result()`, can be called too.
- When you inspect a task while the game runs, e.g. from the debugger's Stack Variables or its remote scene tree, the inspector shows `valid` and `done`, but not `result`. It would read `result` again and again, also before the task is done.

A character that follows a path that a worker thread finds, and starts the next search when it has one:

```gdscript
var search = null

func _process(_delta):
    if search == null:
        search = $Pathfinder.find_path(position, target)
    elif search.done:
        follow(search.claim())
        search = null
```

A level that loads in the background, with a spinner while it does, and a button that cancels it, after which the body may return null:

```gdscript
@onready var loading = $Levels.load_level("forest")

func _process(_delta):
    $Spinner.visible = loading.valid and not loading.done
    if loading.done:
        var level = loading.claim()
        if level:
            add_child(level)

func _on_cancel_pressed():
    loading.cancel()
```

- `valid` tells a Running task from a Claimed one, since neither is done. Here, the spinner hides once the level is claimed.
- A script lets go of a task by dropping its reference, e.g. with `search = null`.
- An object of the class of tasks that runs no task, e.g. `FooAsync.new()`, is Claimed: `valid` and `done` are `false`, like an empty `Async` in GD++ code.

# The task's lifetime

Sharing:

- Copies of an `Async` share its task, like references to the task object in scripts. What one copy does, all of them see.
- So claiming through one copy, or through a script that holds the task, makes the task Claimed for every copy and every script.
- An `Async` is thread-safe to test and `claim` from any thread. Like any variable, though, one `Async` shouldn't be changed by two threads at once.

Dropping:

- When the last reference to an `@onthread` function's task is gone, from C++ or from a script, it waits for the task to finish, unless that already happened.
- An `@async` function's coroutine doesn't wait: it goes on without its task. See "Coroutines' lifetimes" above.
- So dropping an `Async` whose task still runs blocks until the task is done. Dropping a claimed or finished one doesn't.
- Keep the `Async` until `is_done` is `true`, like `pending` in the first example.
- `Async` is `[[nodiscard]]`. The compiler warns about a call whose `Async` isn't kept, e.g. `find_path(a, b);`, which would wait for the task right away.
- For work whose result nobody wants, use `@onthread("detached")`.
- A result doesn't have to be claimed. A task whose result nobody wants, e.g. a void one, can simply be dropped once it's done.

# Stopping tasks

No thread can be killed safely, so a running task can't be stopped from outside. Instead, a body stops itself when it sees that it should:

```gd++
@onthread
func generate(size: int) -> Terrain {
  Gd<Terrain> terrain;
  for (int64_t row = 0; row < size; row++) {
    if (is_cancelled) {
      return {};
    }
    ...
  }
  return terrain;
}
```

`is_cancelled`:

- `true` in a body once its task should stop: after its `Async`'s `cancel()`, or once the game is quitting.
- A rewrite, like `is_done`: it becomes `gdpp::is_cancelled()`. See `gd++ man rewrites`.
- Cheap to check, so long bodies can check it in every loop.
- What the body returns then is up to it, e.g. an empty result. It's the task's result, as usual.
- Outside of tasks, it's `true` while the game quits.

`cancel TASK` in C++, or `task.cancel()` in a script:

- Asks a task to stop.
- A rewrite, like `is_done` and `claim`: it becomes `TASK.cancel()`, and makes the place that stops another task stand out.
- It only sets the flag. The body goes on until it checks `is_cancelled`.
- The `Async` stays as it is, so its result is still claimed, or dropped, as usual.
- Always safe: cancelling a done task, or an empty `Async`, does nothing.

# When the game quits

Running tasks would hold the game up when it quits, e.g. when its window is closed: Godot waits for them. So:

- When quitting starts, `is_cancelled` becomes `true` in every task.
- The package's tasks get a grace period, 1 second by default, to finish.
- If some still run when it's over, the game exits right away, and prints how many tasks were still running.
- Such an exit skips the rest of Godot's cleanup. A body that ignores `is_cancelled` can end the game abruptly. Check `is_cancelled` in long bodies.
- The grace period is the package's `quit_timeout` setting, in seconds. Set it with `gd++ init PATH --update --quit-timeout SECONDS`. See `gd++ man packages`.
- Only quitting can end the game this way. A task cancelled with `cancel()` is only asked to stop, and the game waits for it normally.
- In the editor, e.g. for the tasks of `@tool` classes, quitting waits for tasks as long as they take.

# Writing the body

The body runs on a worker thread, with the limits of any code on threads:

- The call copies the arguments. Arrays and dictionaries still share their contents with the caller: don't change them while the body runs.
- The body can use the object's fields, but other threads, e.g. the main thread, may use them too. Keep what the body needs in its arguments, or protect the fields, e.g. with a `Mutex`.
- If the object is refcounted, the call keeps it alive until the body has run. Other objects, e.g. nodes, must not be freed while the body runs.
- Most of the scene tree isn't thread-safe. To change it, the body can defer the change to the main thread, e.g. with `call_deferred` or a `@thread_safe` function. Or it returns what it computed, and the main thread uses the result.
- In a `@game_only` class, calls in the editor start no task, and return an empty `Async`, which is `false`. See `gd++ man classes`.
- In an `@editor_only` class, the same goes for calls in the game.

# The class of tasks

Godot sees every `Async` as an object of one class of the package: the class of tasks.

- Its name is the package's prefix followed by `Async`.
- GD++ provides it: you don't write it.
- A package gets one when its GD++ classes use `Async`: an `@onthread` or `@async` function, or an `Async` type in a variable, a signal, or a function's parameters or return type. Other packages don't register it.
- The prefix is set in `.gd++pkg`. It defaults to the package's id in PascalCase, e.g. `MyGame` for `my_game`, giving `MyGameAsync`.
- Set it with `gd++ init PATH --update --prefix NAME`. See `gd++ man packages`.

```toml
prefix = "Foo"                         # FooAsync
```

Facts:

- Each package that uses `Async` registers its own class of tasks, so packages built separately never clash.
- The GD++ runtime defines it. The package's generated registration code registers it.
- Its name must differ from the package's other classes. Otherwise the build fails, and asks for another prefix.
- Changing the prefix renames the class. Scripts that name it, e.g. in a type hint, must change too.
- "In scripts" above lists its members.
- It's `RefCounted`: a task lives while a GD++ `Async` or a script holds it.
- Its members are thread-safe.
- A script can't start a task with it: `FooAsync.new()` makes an object that runs no task.
- The editor's help shows `Async` types as this class, e.g. `FooAsync`, and documents the class itself in builds with documentation. See `gd++ man docs`.
- Like Godot's own classes, the help lists `valid`, `done` and `result` as properties, not their getters.
- `gd++ trans --runtime` shows its implementation: the runtime header defines it, as `GDPP_ASYNC_CLASS`, with `Async<T>`. "How it works" below gives an overview.
- `gd++ trans` on a file outside any package names the class `GdppAsync`.

# Across packages

C++ code works with the tasks of any package:

- An `Async<T>` calls the methods of the package's own tasks directly, and those of other packages' tasks by name.
- So an extern can declare that a function of another package returns an `Async`, e.g. an `@onthread` function.
- Calling `planner->plan(10)` returns an `Async<Array>` of the other package's task. See `gd++ man externs`.

```gd++
extern Planner {
  extends Node
  func plan(steps: int) -> Async[Array]
}
```

Godot knows an `Async` parameter as the package's own class, e.g. `FooAsync`. So a script's type checks may refuse another package's task there. To take the tasks of any package, declare the parameter as a `Variant`, and convert it in C++, e.g. `task as Async<int64_t>`. See `gd++ man cast`.

# How it works

For an `@onthread` function `f`, GD++ generates:

- `f` itself, which returns an `Async` of the function's type. It calls `gdpp::run_task`, which creates an object of the package's class of tasks, and starts the task with `WorkerThreadPool::add_task`.
- `_gdpp_body_f`, a method with the body, which the task calls. It isn't bound, so scripts can't call it.

With `@onthread("detached")`:

- `f` returns `void`, and calls `gdpp::run_detached`, which starts the task like `gdpp::run_task`, but returns nothing.
- Once the body is done, the task schedules the wait with `call_deferred`. So it doesn't matter who drops the last reference to it.

For an `@async` function `f`, GD++ generates:

- `f` itself, which returns an `Async` of the function's type. It calls `gdpp::run_coroutine`, which creates an object of the package's class of tasks, and starts the coroutine. `@async("detached")` calls `gdpp::run_detached_coroutine` instead, which returns nothing.
- `_gdpp_body_f`, the body: a C++20 coroutine, which returns a `gdpp::Coroutine` of the function's type. Its parameters are values, not references, since references would dangle once it awaits. It isn't bound.
- In the body, `await` becomes `co_await`, and `return` becomes `co_return`. `await X->NAME` becomes `co_await gdpp::signal(X, gdpp::string_name<"NAME">())`.
- In the body, `string_name "NAME"` becomes `gdpp::string_name<"NAME">()`, not `GDPP_STRING_NAME("NAME")`: that macro's lambda would outlive an `await` in the coroutine's frame, which GCC rejects.
- Each `await` that waits connects the signal, once, to a `gdpp::SignalWait`: a `Callable` that owns the coroutine, and resumes it. Its target is the object the function was called on, so Godot drops it when either object is freed, which destroys the coroutine.
- Awaiting a task connects to its `until_done()` signal.

The task object:

- Stores the body's result as a `Variant`. The `Async` converts it back to the function's type.
- Godot requires waiting once for each `WorkerThreadPool` task, with `wait_for_task_completion`. The object does so in `wait`, which `claim` calls, or else when it's freed.
- A task can't wait for itself. If it frees the last reference to itself, e.g. by freeing the object that held it, the main thread waits for it instead, right after.
- Once done, it emits `finished` with `call_deferred`, which holds a reference to it until then.

Quitting:

- From the package's first task on, the runtime watches the root window. The window leaves the scene tree when the game starts quitting, before any node is freed.
- From then on, `is_cancelled` is `true`, and waiting for a task ends the game when the grace period is over.
- When the package's library is unloaded, it also waits for the package's running tasks, within the same grace period, since their code must not be unloaded while they run. It disconnects the awaits of waiting coroutines, which destroys them.

`gd++ trans FILE` shows the code. `gd++ trans --runtime` shows the class of tasks and `Async<T>`. See also `gd++ man generated` and `gd++ man runtime`.
