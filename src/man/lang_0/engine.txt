Engine blocks: ready, process and the like

This page explains engine blocks, which run code when a node enters the scene tree, gets ready, processes a frame, draws, or exits the tree: `enter_tree`, `ready`, `process`, `physics_process`, `draw` and `exit_tree`.

# Syntax

```gd++
ready {
  gd::print("Ready.");
}

process(delta) {
  rotate_y(delta);
}
```

An engine block is its word, then its body, C++ in braces. `process` and `physics_process` take the delta time, the seconds since the last frame, as a `float`: name it in parentheses, without a type, e.g. `process(delta)` or `process(dt)`. The others take nothing, and have no parentheses: `ready { ... }`. Engine blocks have no return type.

These are the blocks, with the engine's virtual function that each one stands for, and the classes they work in:

```
BLOCK                    FUNCTION            CLASSES
enter_tree { }           _enter_tree         Node
ready { }                _ready              Node
process(delta) { }       _process            Node
physics_process(delta)   _physics_process    Node
exit_tree { }            _exit_tree          Node
draw { }                 _draw               CanvasItem
```

In other classes, they're an error. A class has at most one block of each kind. Their words are still free to use as names elsewhere, e.g. `var ready: bool`.

# How they work

Engine blocks are `notif` blocks with syntax sugar: `process(delta) { ... }` is a `notif PROCESS { ... }` block whose `delta` is set, from `get_process_delta_time()`. Their bodies run in the class's `_notification`, not in an override of the engine's function, so neither a subclass nor a script that extends the class and defines a function of the same name replaces them: both run, the base's first. They aren't functions of the class: C++ code and scripts can't call them.

Each one runs at its notification, e.g. `NOTIFICATION_PROCESS`. `ready` runs at `NOTIFICATION_POST_ENTER_TREE`, the last notification before `NOTIFICATION_READY`, once the node's children are ready, right after the `@onready` initial values. So it runs before a script's `_ready`. `process` and `physics_process` turn processing on in the constructor, with `set_process(true)` or `set_physics_process(true)`. Within the class's `_notification`, they run together with `notif` blocks, in the order of their declarations: see `gd++ man lifecycle`.

# Annotations

Engine blocks take only `@trace`, `@profile`, `@notrace`, `@noprofile` and `@game_only`, and `ready` in a `@pool` class also `@recycle`:

```gd++
@trace
physics_process(delta) {
  move_and_slide();
}
```

The groups `process` and `physics_process` turn on the tracing and profiling of all `process` and `physics_process` blocks, even without annotations. See `gd++ man debugging`.

In a `@pool` class, `ready` only runs the first time an object gets ready, unless it has `@recycle`. See "Getting ready again" in `gd++ man pools`.

# Overrides

A function named like the engine's virtual functions, e.g. `func _ready() -> void`, is an override, so it needs `@override`, like any other override:

```out
[×] res://a.gd++:4:1: Function _ready overrides a virtual function of Node, so it needs @override.
     4 | func _ready() -> void {}
       | ^^^^
    Hint: To run code at its notification, write a ready block instead: "ready { ... }". Only for a plain override, which a script replaces, add @override.
```

A plain override is rarely what you want, since a script that defines a function of the same name replaces it. Only if you're sure you need one, write `@override func _ready() -> void`. It runs at `NOTIFICATION_READY`, unless a script replaces it. See "@override" in `gd++ man functions`.
