Generated code: the C++ that GD++ writes

GD++ turns each GD++ file into ordinary C++, which you can read, debug and include. This page describes that C++: the files, what's in them, and the names of the helpers GD++ adds.

- `gd++ trans FILE` shows the C++ of a file. See `gd++ man trans`.
- In a build, it's in the package's build cache, in `.gd++build/gdpp`. See `gd++ man build-cache`.

# Files

Each declaration of a GD++ file gets its own files, named after it:

- a class NAME: `NAME.h`, its definition, and `NAME.cpp`, its methods and bindings,
- an extern NAME: `NAME.h`, its wrapper class,
- a trait NAME: `NAME.h`, its interface,
- an enum NAME: `NAME.h`, its enum class.

Plus, for the whole package:

- `gd++/syntax_0.hpp`, the runtime header. See `gd++ man runtime`.
- `gd++/syntax_0_gpu.hpp`, the runtime header of shaders and GPU arrays, which only the files that use them include. See `gd++ man shaders`.
- `doc_classes/NAME.xml` per class, its documentation, in debug builds, and one for each class that GD++ adds, e.g. the class of tasks. See `gd++ man docs`.

Facts:

- Every generated file starts with "// Generated by GD++ from FILE, do not edit.".
- Headers use `#pragma once`.
- Everything is in namespace `godot`, except `@global` blocks.
- With `gd++ build --trace`, the header of a class with assertions defines `GDPP_TRACING` before its includes. So they print a trace line when they fail.

# An example

`counter.gd++`:

```gd++
class_name Counter
extends Node

signal changed(value: int)

var count: int = 1

func add(amount: int = 1) -> void {
  count += amount;
  emit changed(count);
}
```

`Counter.h`:

```cpp
// Generated by GD++ from counter.gd++, do not edit.

#pragma once

#include <gd++/syntax_0.hpp>
#include <godot_cpp/classes/node.hpp>

namespace godot {

#define This Counter
class Counter : public Node {
  GDCLASS(Counter, Node)

public:
  int64_t count{};

public:
  Counter();
  void add(int64_t amount = _gdpp_default_add_amount());
  int64_t get_count() const;
  void set_count(int64_t p_value);
  gdpp::Emitted changed(int64_t value);

protected:
  static void _bind_methods();

private:
  static int64_t _gdpp_default_add_amount();
};
#undef This

} // namespace godot
```

`Counter.cpp`:


# The class header

In order:

1. The `#include` lines: the runtime header, then the headers of the names the header uses, sorted. See `gd++ man includes`.
2. `@global decl` blocks.
3. In namespace `godot`: forward declarations of the package's GD++ classes, externs, traits and enums that the header uses, e.g. `class Enemy;` or `enum class Suit : int64_t;`.
4. The enum stand-ins of the class, one per enum it exposes: `enum _gdpp_Counter_Suit : int64_t {};` and `GDPP_ENUM_TAG`, or `GDPP_BITFIELD_TAG` for a bitfield. See `gd++ man enums`.
5. The class, between `#define This NAME` and `#undef This`:
   - `class NAME : public BASE`, followed by `public TRAIT` for each trait it implements itself,
   - `GDCLASS(NAME, BASE)`,
   - each `decl` block, after `private:`,
   - `public:` the fields of simple variables, value-initialized with `{}`,
   - `private:` the `decl` blocks of properties,
   - `public:` integer constants as `static constexpr int64_t`, the constructor and destructor if any, the hooks of traits if it implements any, `GDVIRTUAL` declarations of `@virtual` functions, the functions except `@private` ones, RPC helpers, getters and setters, and the emit functions of signals,
   - `protected:` `static void _bind_methods()`, and `void _notification(int WHAT)` if the class has `on` blocks or `@onready` variables,
   - `private:` the `@private` functions, and the generated helpers: enum wrappers, and default value functions.
6. The `#include` lines of the GD++ names that were only forward-declared, at the end, after namespace `godot`.

# The class source

In order:

1. `#define GDPP_DEBUGGING`, if a `@trace` or `@profile` annotation of the file's classes is on, then `#include "NAME.h"`, then the headers of names that only the source uses.
2. `@global impl` blocks.
3. In namespace `godot`, between `#define This NAME` and `#undef This`, the parts below, in order.

`_bind_methods` binds:

- each function, with its default values, except `@private` functions, and the bodies of `@onthread` and `@async` functions, which their tasks call directly,
- each variable's getter and setter, and its property, after the inspector sections it starts,
- each signal and each integer constant,
- each value of each exposed enum, as a bitfield flag for a bitfield.

The constructor, if needed, in order (see `gd++ man lifecycle`):

- in a `@pool` class, `const bool _gdpp_reserved = std::exchange(gdpp::reserving(), false);`, which tells whether `pool_reserve` makes the object,
- the creation line of a class whose `@trace` is on,
- RPC configurations,
- `set_process(true)` and the like, for overrides and `on` blocks,
- the initial values of variables, those of `@recycle` variables as `if (!_gdpp_reserved) { ... }`,
- the `ctor` block,
- the `@recycle ctor` block without `"only"`, as `if (!_gdpp_reserved) { ... }`.

The destructor, if the class has a `dtor` block, a `@trace` that's on, or `@pool`:

- the `@recycle dtor` block without `"only"`, as `if (!_gdpp_pool_slot.given) { ... }`, so that an object resting in its pool skips it,
- the `dtor` block.

`_notification`, if the class has `on` blocks or `@onready` variables, in order (see `gd++ man callbacks`):

- the `@onready` initial values, as `if (WHAT == NOTIFICATION_POST_ENTER_TREE && !is_node_ready()) { ... }`,
- the call of the `on ready` block,
- the call of each other `on` block, in order, as `if (WHAT == NOTIFICATION_PROCESS) { _gdpp_body__process(get_process_delta_time()); }`, or for the nameless one, `_gdpp_body__notification(WHAT);`.
- In a `@pool` class, the `@onready` values and `on ready` without `@recycle` are also guarded by `!_gdpp_pool_slot.readied`. `_notification` sets it at `NOTIFICATION_READY`, last. An `@override func _ready()` without `@recycle` checks it first.
- An `on` block is a method `_gdpp_body__NAME`, e.g. `_gdpp_body__process`, since godot-cpp would make a method named `_process` an override.

Each function:

- the `GDVIRTUAL_CALL` of a `@virtual` function, or of an `@override` of one without `"final"`,
- then the body, or instead:
  - for `"super"`, the call of `_super_NAME`, which has the body,
  - for the function that GD++ binds for a `@virtual` function, e.g. `think` for `_think`, the call of the `@virtual` function,
  - for `@deferred` and `@thread_safe`, the call that runs `_gdpp_body_NAME` later,
  - for `@onthread`, `gdpp::run_task`, which starts a task that runs it on the `WorkerThreadPool`. See `gd++ man async`.
  - for `@async`, `gdpp::run_coroutine`, which starts the coroutine `_gdpp_body_NAME`. See `gd++ man async`.
- then its enum wrapper, default value functions and RPC helper.

Then:

- each variable's getter and setter, and their enum wrappers. For a `@deferred` or `@thread_safe` `set` block, the setter makes the call that runs `_gdpp_body_set_NAME` later.
- each signal's emit function,
- the `impl` blocks.

Editor checks:

- In a `@game_only` class, each of these functions except `_bind_methods` starts with an editor check, in debug builds.
- Outside one, the functions of a `@game_only` function or variable do.
- `@editor_only` works the same way, with the opposite check, in all builds.
- See `gd++ man classes`.

When `@trace` or `@profile` annotations are on, the functions they apply to start with their code, after the editor check:

- `gdpp::ProfileStats` and `gdpp::Profile` for `@profile`,
- `gdpp::Trace` for `@trace`,
- `gdpp::Watch` in each function that checks the class's `@trace` variables.
- A traced function that returns a value runs its body in a lambda, `return _gdpp_trace.ret([&]() -> T { ... }());`, so the trace sees every result.
- The constructor and destructor of a traced class call `gdpp::trace_lifetime`.
- The emit function of a traced signal calls `gdpp::trace_emit`.
- See `gd++ man debugging`, and `gd++ trans FILE --trace all --profile all` for your own files.

# Generated names

GD++ names its helpers with the prefix `_gdpp_`, which is reserved: don't use it for your own names.

```
get_NAME, set_NAME           a variable's getter and setter
NAME (of a signal)           a signal's emit function, returning gdpp::Emitted
create                       @factory's static method, which calls create
destroy                      @factory's method, which calls destroy
queue_destroy                @factory's method, which calls queue_destroy
pool_reserve                 @factory_pool's static method, which fills the pool
pool_clear                   @factory_pool's static method, which empties the pool
scene_cache                  @factory_scene's static method, which loads the scene
scene_evict                  @factory_scene's static method, which drops the scene
compile_shader               @factory_shader's static method, which compiles a shader, and its _async and _detached forms
compile_shaders              @factory_shader's static method, which compiles all shaders, and its _async and _detached forms
_gdpp_default_FUNC_PARAM     a static function that returns a parameter's default value
_gdpp_rpc_FUNC               an @rpc function's helper, which rpc calls
_gdpp_body_FUNC              the body of a @deferred, @thread_safe, @onthread or @async function, or set block, which its deferred call or task runs
_gdpp_FUNC                   the wrapper that binds a function with enums in its signature
_gdpp_get_NAME, _gdpp_set_NAME   the wrappers that bind a variable of an enum type
_gdpp_CLASS_ENUM             a class's stand-in type for an enum
_gdpp_ret                    a local variable in @virtual functions
_gdpp_base                   an extern wrapper's object
_gdpp_traits                 a static function that records the traits of a class, which casts look up
_gdpp_destroy                what destroy calls through a trait: destroy of the class
_gdpp_queue_destroy          what queue_destroy calls through a trait: queue_destroy of the class
_gdpp_pool                   a @pool class's pool, a static gdpp::Pool<T>
_gdpp_pool_slot              where an object of a @pool class is in its pool
_gdpp_recycle_ctor, _gdpp_recycle_dtor   what a @pool class runs when its pool reuses and keeps an object
_gdpp_scene                  a @scene class's scene path, a static constexpr gdpp::Scene<T>
_gdpp_abstract               an @abstract class's mark, a static constexpr gdpp::Abstract<T>, which makes create fail to compile
_gdpp_editor_NAME            the field that a guarded variable's getter and setter use in the editor, if it has get and set blocks
_gdpp_gpu_CLASS              the namespace, at global scope, of a class's shaders' code: its shader blocks, and a struct per shader
_gdpp_shader_SHADER          a shader's struct: its GLSL, and its body as C++, for the CPU
_gdpp_kernel, _gdpp_call     a shader's compiled code, and the call that runs it
_gdpp_body, _gdpp_result     in a shader's GLSL: its body, and what main stores the body's results in
```

- `This` is a macro, defined around each class's code.
- `GENERATION` is a local constant of an `on` block, `@recycle ctor`, `@recycle dtor` or `@override` `@recycle _ready` that uses it.
- The setter's parameter is `p_value`, unless a property's `set` block names it.

# #line directives

Every piece of your code, e.g. a function body or an initial value, is wrapped in `#line` directives:

- one before it, with its line in the GD++ file,
- one after it, which switches back to the generated file.

Facts:

- So compiler errors, warnings and debuggers point to the right line in the right file.
- In builds, the GD++ file is named by its copy in the build cache, relative to the build cache, e.g. `package/src/player.gd++`.
- Your code is copied with its line breaks. So a body's text starts on the line of its `{`.
- C++ code from a template keeps its lines in the template, so `#line` names those, also in another file. See `gd++ man templates`.
- C++ code from a macro has no lines of its own, so `#line` names the invocation's line. See `gd++ man macros`.

# Extern headers

An extern NAME gets a header with a wrapper class NAME, in namespace `godot`:

```cpp
class Terrain {
public:
  using Base = Node3D;
  static constexpr const char *gdpp_name = "Terrain";
  explicit Terrain(Base *p_object);
  double height_at(double x, double z) const;
  int64_t get_seed() const;
  void set_seed(int64_t p_value) const;
  gdpp::Emitted changed() const;
protected:
  Base *_gdpp_base;
};
```

- Its methods are defined inline, after the classes they may use.
- They call `_gdpp_base->call`, `call_deferred`, `get`, `set` or `emit_signal` with the member's name. See `gd++ man externs`.
- The wrapper of an extern that extends another extern derives from that one's wrapper, e.g. `class Car : public Vehicle`, and shares its `Base` and `_gdpp_base`.
- An extern with `@factory` also has e.g. `static constexpr gdpp::ExtFactory<Bullet> _gdpp_factory{ "create", "destroy", "queue_destroy" };`, which names the methods that `create`, `destroy` and `queue_destroy` call, with `nullptr` for the defaults. An extern that extends it doesn't use it, since its type names `Bullet`.

If a `@trace` or `@profile` annotation of the extern is on, the header starts with `#define GDPP_DEBUGGING`. The methods start with the same lines as a class's functions, with `gdpp::via_extern` and "extern" names:

```cpp
inline double Terrain::height_at(double x, double z) const {
  static gdpp::ProfileStats _gdpp_stats("extern Terrain.height_at");
  gdpp::Profile _gdpp_profile(_gdpp_stats);
  gdpp::Trace _gdpp_trace(gdpp::via_extern, _gdpp_base, "height_at", "x", x, "z", z);
  return _gdpp_trace.ret(gdpp::cast<double>(_gdpp_base->call(GDPP_STRING_NAME("height_at"), x, z)));
}
```

See `gd++ man debugging`.

# Trait headers

A trait NAME gets a header with an interface NAME, in namespace `godot`:

```cpp
class Damageable {
public:
  using Base = Node3D;
  virtual ~Damageable() = default;
  virtual void take_damage(int64_t amount) = 0;
  virtual bool is_dead() = 0;
  virtual void _gdpp_destroy() = 0;
  virtual void _gdpp_queue_destroy() = 0;
};
```

- Each function is pure virtual, defaults too: the classes that implement the trait get a copy of each default.
- `_gdpp_destroy` is left out for a refcounted base, and `_gdpp_queue_destroy` for a base that isn't a `Node`.
- A class that implements the trait derives from the interface, after its base class.
- Its functions are declared with `override`, and so are its hooks, defined like `void Crate::_gdpp_destroy() { gdpp::destroy(this); }`.
- Its `static void _gdpp_traits(gdpp::TraitsOf<Crate>)` calls `gdpp::implement<Damageable, Crate>()` for each trait it implements, those of its bases included.
- A trait's `@group` adds `add_to_group(GDPP_STRING_NAME("NAME"));` to the constructors of its classes.

See `gd++ man traits`.

# Enum headers

An enum NAME gets a header with an enum class:

```cpp
enum class Suit : int64_t {
  DIAMONDS = 0,
  CLUBS = 1,
  SPADES = 2,
  HEARTS = 3,
};
```

A bitfield's enum class is followed by `GDPP_BITFIELD(Name)`, which gives it the bitwise operators, and lets `&` test as a `bool`.

# Registration

The build also generates `__register_types__.cpp`, in the build cache, outside `gdpp/`.

- It includes every class's header.
- It registers each class when the library loads, bases first:
  - with `GDREGISTER_VIRTUAL_CLASS` for abstract classes, i.e. GD++ classes with `@abstract` and C++ classes with `abstract = true`,
  - with `GDREGISTER_RUNTIME_CLASS` for runtime classes, i.e. classes without tool or abstract that don't extend such a class of the package,
  - with `GDREGISTER_CLASS` for the others.
- Its entry point is `gdpp_library_init`. See `gd++ man cpp-classes`.

In a package with GD++ classes, `__register_types__.cpp` also:

- includes the GD++ runtime,
- calls `gdpp::uninitialize()` when the library is unloaded. It waits for the package's running tasks, and removes the engine's hooks into the package's code, e.g. signal connections. So the editor doesn't call the old code after a hot reload.
- registers the class of tasks first, e.g. `FooAsync`, if the package's GD++ classes use `Async`. The GD++ runtime defines it.
- registers the class of GPU arrays, e.g. `FooGpuArray`, and the internal class of the textures that shaders return, e.g. `FooGpuTexture`, if the package's GD++ classes have shaders or GPU arrays. The runtime header of shaders defines them.
- records the traits of each class right after registering it, with `gdpp::register_traits`, which calls its `_gdpp_traits`. `gdpp::uninitialize()` forgets them.

`SConstruct` defines, for all the package's C++:

- `GDPP_ASYNC_CLASS` as the class of tasks' name,
- `GDPP_QUIT_TIMEOUT_USEC` as the package's `quit_timeout`,
- `GDPP_GPU_ARRAY_CLASS` and `GDPP_GPU_TEXTURE_CLASS` as the names of the class of GPU arrays and the class of textures,
- `GDPP_GPU_FORCE_CPU`, with `gd++ build --nogpu`, which runs shaders on the CPU.

See `gd++ man async`.

# Using generated classes from C++

- Plain C++ files of the package can include a GD++ class's header, e.g. `#include "Counter.h"`, and use the class.
- Its functions, getters and setters are public methods.
- The fields of simple variables are public too.
