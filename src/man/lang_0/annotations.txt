Annotations: the complete list

Annotations attach information to a declaration, like in GDScript: `@export` on a variable, `@override` on a function, `@tool` on a class. This page lists all of them. The page of each topic explains them in full.

Your own annotations start with `@@`, e.g. `@@save`, and are declared with `annotation save`. Only macros read them. See "User annotations" below.

# Syntax

```gd++
@name
@name(ARG, ARG, ...)
```

- `@` and a name, with arguments in parentheses if it takes any.
- Arguments are numbers (negative ones too), strings in double quotes, or names.
- A trailing comma is fine.
- Annotations go right before their declaration, on the same line or on the lines before, in any order.
- A doc comment can come before the annotations or between them. A declaration has at most one doc comment. See `gd++ man docs`.

```gd++
@export var speed: float

@export_range(0, 100, 1, "or_greater")
var health: int

@virtual @const
func _score() -> int
```

# Classes

@abstract
  Make the class only a base for other classes, like in GDScript: the editor doesn't offer it, and `create` doesn't work on it. Not with `@pool` or `@scene`. See `gd++ man classes`.

@tool and @tool("editor_only")
  Run the class's code in the editor too. With `"editor_only"`, the same as `@editor_only @tool`. See `gd++ man classes`.

@game_only
  Run the class's code only in the game, never in the editor, not even when other code calls it. Not with `@tool`. See `gd++ man classes`.

@editor_only
  Run the class's code only in the editor, never in the game. Only with `@tool`. See `gd++ man classes`.

@factory and @factory(CREATE, DESTROY, QUEUE_DESTROY)
  Declare the class's methods that do what `create`, `destroy` and `queue_destroy` do, for scripts. See `gd++ man classes`.
  - Without arguments, they're named `create()`, `destroy()` and `queue_destroy()`.
  - With arguments: up to three names, as strings, e.g. `@factory("spawn", "despawn", "queue_despawn")`. An empty string `""`, or a missing name at the end, leaves that method out: `@factory("spawn")` declares only `spawn()`.
  - Only the methods that apply: no `create()` for `@abstract` classes, no `destroy()` for refcounted classes, and no `queue_destroy()` for classes that don't extend `Node`.
  - Without `@factory`, the class has none of them.
  - On an extern, it makes `create`, `destroy` and `queue_destroy` call these methods of its class. See "Factory methods" in `gd++ man externs`.

@factory_pool and @factory_pool(RESERVE, CLEAR)
  Declare the class's static methods that fill and empty its pool: `pool_reserve()` and `pool_clear()` by default. Only with `@pool`. See `gd++ man pools`.
  - With arguments: up to two names, as strings, e.g. `@factory_pool("prewarm")`. An empty string `""`, or a missing name at the end, leaves that method out.

@factory_scene and @factory_scene(CACHE, EVICT)
  Declare the class's static methods that load and drop its scene: `scene_cache()` and `scene_evict()` by default. Only with `@scene`. See `gd++ man classes`.
  - With arguments: up to two names, as strings, e.g. `@factory_scene("preload_scene")`. An empty string `""`, or a missing name at the end, leaves that method out.

@factory_shader and @factory_shader(SHADER, SHADER_ASYNC, SHADER_DETACHED, SHADERS, SHADERS_ASYNC, SHADERS_DETACHED)
  Declare the class's static methods that compile its shaders ahead of time: `compile_shader(shader)`, `compile_shader_async(shader)`, `compile_shader_detached(shader)`, `compile_shaders()`, `compile_shaders_async()` and `compile_shaders_detached()` by default. Only for classes with a shader. See `gd++ man shaders`.
  - With arguments: up to six names, as strings, e.g. `@factory_shader("", "", "", "warm_up")`. An empty string `""`, or a missing name at the end, leaves that method out.

@icon(PATH)
  The class's icon in the editor: a string with a `res://` or `pkg://` path. See `gd++ man classes`.

@pool, @pool(SIZE), @pool(SIZE, "fixed") and @pool(SIZE, "grow")
  `destroy` keeps objects in a pool instead of deleting them, and `create` reuses them. Only for classes that extend `Node`. See `gd++ man pools`.
  - Scripts use the class's `@factory` methods for the same.
  - `@factory_pool` declares methods that make objects ahead of time, and drop them all.
  - With SIZE, a positive integer: the pool holds up to SIZE objects. `create` returns null once all of them are in use, so code must check its result. `"fixed"` is the same.
  - With `"grow"`: the pool makes more objects then. In debug builds, it logs an error when it grows past SIZE objects, and again past each double of that.

@scene(PATH)
  Make `create` instantiate the class's scene: a string with a `res://` or `pkg://` path. Only for classes that extend `Node`. See `gd++ man classes`.
  - The scene is loaded once.
  - Its root must be an object of the class.
  - Scripts use the class's `@factory` methods for the same.
  - `@factory_scene` declares methods that load the scene ahead of time, and drop it.

@trace(GROUPS...)
  Trace all its functions, variables and signals, and print the creation and destruction of its objects. Except `on process`, `on physics_process` and overrides of `_process` and `_physics_process`. See "@trace and @profile" below.

@profile(GROUPS...)
  Time all its functions, and the getters and setters of its properties with `get` and `set` blocks. See "@trace and @profile" below.

# ctor and dtor blocks

@recycle
  Only in a `@pool` class. See `gd++ man pools`.
  - `@recycle ctor` runs when the pool reuses an object, and when an object is actually created, after `ctor`.
  - `@recycle dtor` runs when the pool keeps an object, and when an object is actually deleted, before `dtor`.
  - So they run once per use of an object.
  - With `@recycle("only")`, they run only when the pool reuses or keeps an object.
  - The plain `ctor` and `dtor` run only when an object is actually created or deleted.
  - For `@recycle` on variables, see "Variables of classes" below.

# Functions of classes

@override
  Override a virtual function of the engine, e.g. `_input`, or a `@virtual` function of a GD++ base class. See `gd++ man functions`.
  - A function named like one needs it.
  - A script's function of the same name replaces it.
  - To add code that runs at a notification, e.g. at `_ready`, use an `on` block instead, e.g. `on ready { ... }`. It adds to the base's, and scripts can't replace it.
  - Optional arguments, in double quotes:
  - `"final"`: on an override of a GD++ `@virtual` function, subclasses and scripts can't override it any further.
  - `"super"`: also bind the body as `_super_NAME`, which scripts call in place of `super`.

@virtual
  Let subclasses and scripts override the function. See `gd++ man functions`.
  - Its name must start with `_`, e.g. `_think`.
  - Scripts call it as `think`, which GD++ binds too.
  - Optional arguments, in double quotes:
  - `"private"`: don't bind `think`.
  - `"super"`: also bind the body as `_super_think`, which scripts' overrides call in place of `super`.

@const
  Make the function a const method. See `gd++ man functions`.

@static
  Make the function static. See `gd++ man functions`.

@private
  Make the function a private C++ method, which GD++ doesn't bind. Only C++ code of the class calls it. See `gd++ man functions`.

@rpc(ARGS...)
  Make the function callable over the network. Only in classes that extend `Node`. See `gd++ man rpc`. Arguments:
  - `"authority"` or `"any_peer"`,
  - `"call_remote"` or `"call_local"`,
  - `"unreliable"`, `"unreliable_ordered"` or `"reliable"`,
  - a channel number, last.

@deferred
  Every call, from C++ or from Godot, goes through `call_deferred` and runs later. The function must return `void`. See `gd++ man functions`.

@thread_safe
  Like `@deferred`, with `call_thread_safe`: calls from other threads run later, on the main thread. Only in classes that extend `Node`. See `gd++ man functions`.

@onthread
  Every call, from C++ or from Godot, runs the body on the `WorkerThreadPool`, and returns an `Async` of the function's type. The caller waits for the body and gets its result through it. See `gd++ man async`.
  - Argument `"detached"`, for a function that returns `void`: calls return nothing, and nothing waits for the task.

@async
  The function is a coroutine: its body can `await` signals and tasks. Every call runs the body until an `await` that waits, and returns an `Async` of the function's type, done once the body returns. See `gd++ man async`.
  - Argument `"detached"`, for a function that returns `void`: calls return nothing.

@trace(GROUPS...)
  Print each call when it starts, with its arguments, and when it returns, with its result and time. See "@trace and @profile" below.

@profile(GROUPS...)
  Time each call, for the editor's monitors and the profile table. See "@trace and @profile" below.

@notrace and @noprofile
  Leave the function out of its class's `@trace` or `@profile`, and out of the groups `process` and `physics_process`. Its own `@trace` or `@profile` still applies. See "@trace and @profile" below.

@game_only
  Run the function only in the game, never in the editor, e.g. in a `@tool` class. See `gd++ man classes`.

@editor_only
  Run the function only in the editor, never in the game. Only in a `@tool` class. See `gd++ man classes`.

@recycle
  Only on an `on ready` block, or an `@override func _ready()`, in a `@pool` class: run it each time an object gets ready, not only the first time. See "Getting ready again" in `gd++ man pools`.

Rules:

- `@static` doesn't combine with `@virtual`, `@override`, `@const`, `@rpc`, `@deferred` or `@thread_safe`.
- `@virtual` doesn't combine with `@override`, `@rpc`, `@deferred`, `@thread_safe` or `@onthread`.
- `@override` doesn't combine with `@rpc`, `@deferred`, `@thread_safe` or `@onthread`.
- `@rpc` doesn't combine with `@onthread`.
- `@private` doesn't combine with `@virtual`, `@override` or `@rpc`.
- `@deferred` doesn't combine with `@thread_safe` or `@onthread`.
- `@thread_safe` doesn't combine with `@onthread`.
- `@game_only` doesn't combine with `@editor_only`.
- `on` blocks only take `@trace`, `@profile`, `@notrace`, `@noprofile`, `@game_only` and `@editor_only`. `on ready` also takes `@recycle`.
- `@override("final")` only works on an override of a GD++ `@virtual` function.
- A `@virtual` function's name must start with `_`.
- A function named like a virtual function of the base class needs `@override`.

# Externs

@pool
  The extern's class has `@pool`: `create`, `destroy` and `queue_destroy` use its pool, through its methods for scripts. No arguments: the class configures its pool. Only for externs that extend `Node`. See "Pools and scenes" in `gd++ man externs`.

@scene
  The extern's class has `@scene`: `create` instantiates its scene, through its method for scripts. No arguments: the class names its scene. Only for externs that extend `Node`. See "Pools and scenes" in `gd++ man externs`.

Externs also take `@trace` and `@profile`, which work like a class's on their functions, variables and signals. See "@trace and @profile" below.

# Functions of externs

@const
  The function is a const method of the class.

@deferred
  Call the function with `call_deferred`. It must return `void`.

@thread_safe
  Call the function with `call_thread_safe`. It must return `void`. Only in externs that extend `Node`.

@rpc
  The function can be called over the network, with `rpc`. No arguments in externs. Only in externs that extend `Node`.

@trace(GROUPS...)
  Print each call through the extern, like `@trace` on a class's function, marked "extern". See "@trace and @profile" below.

@profile(GROUPS...)
  Time each call through the extern, for the editor's monitors and the profile table, as `extern CLASS.NAME`. Not on `@deferred` and `@thread_safe` functions. See "@trace and @profile" below.

@notrace and @noprofile
  Leave the function out of its extern's `@trace` or `@profile`. See "@trace and @profile" below.

See `gd++ man externs`.

# Shaders

A shader takes `@onthread`, `@trace`, `@profile`, `@notrace`, `@noprofile`, `@game_only` and `@editor_only`, which work like on a function, and:

@async
  Calls return right away, while the GPU works. Without it, they wait until the GPU is done with the shader. Only on shaders that return a `GpuArray`, a `Texture2D` or `void`: other results come back from the GPU, so their calls must wait. Combines with `@onthread`, whose task then doesn't wait for the GPU. See "Not waiting for the GPU: @async" in `gd++ man shaders`.

@grid(NAME, SIZES...)
  Both parts are optional, e.g. `@grid(size)`, `@grid(16, 16)` or `@grid(size, 16, 16)`.
  - NAME, a parameter's name, maybe in double quotes: that parameter is the shader's grid, instead of the first one. See "The grid" in `gd++ man shaders`.
  - SIZES: the size of the shader's workgroups, one positive integer for each dimension of its grid. At most 1024 cells in all. See "Workgroups" in `gd++ man shaders`.

A shader is always static, so `@static` is an error. Shader blocks take no annotations.

# Traits

@group(NAME)
  Every class that implements the trait adds its objects to the group NAME, a string, when they're created. Without NAME, the group is named like the trait. Only for traits that extend `Node`. See "@group" in `gd++ man traits`.

Functions of traits only take `@const`. The functions of a class that implement them can't have `@static`, `@virtual`, `@override`, `@deferred`, `@thread_safe`, `@onthread` or `@private`. See `gd++ man traits`.

# Variables of classes

@onready
  Assign the initial value right before the `on ready` block, instead of in the constructor. Only in classes that extend `Node`. In a `@pool` class, only the first time an object gets ready, unless it also has `@recycle`. See `gd++ man lifecycle`.

@recycle
  Only in a `@pool` class. See "Resetting variables" and "Getting ready again" in `gd++ man pools`.
  - Reset the variable to its initial value, or to its type's default without one, each time the pool reuses an object.
  - With `@onready`: assign the initial value each time an object gets ready, not only the first time.

@export
  Show the variable in the inspector, and save it.

@export_range(MIN, MAX[, STEP][, EXTRAS...])
  An `int` or `float` in a range.

@export_enum(NAMES...)
  An `int` or `String` chosen from a list.

@export_flags(NAMES...)
  An `int` of bit flags.

@export_file([FILTERS...])
  A `String` with a file path.

@export_dir
  A `String` with a directory path.

@export_multiline
  A `String` with many lines.

@export_placeholder(TEXT)
  A `String` with a placeholder text.

@export_storage
  Save the variable, but don't show it in the inspector.

@export_category(NAME)
  Start a category of the inspector at this variable.

@export_group(NAME[, PREFIX])
  Start a group of the inspector at this variable.

@export_subgroup(NAME[, PREFIX])
  Start a subgroup of the inspector at this variable.

@trace(GROUPS...)
  Print each change of its value, with the class's function that made it. See "@trace and @profile" below.

@profile(GROUPS...)
  Time its getter and setter. See "@trace and @profile" below.

@notrace and @noprofile
  Leave the variable out of its class's `@trace` or `@profile`: its changes aren't printed, or its getter and setter aren't timed. See "@trace and @profile" below.

@game_only
  Run its getter and setter only in the game, never in the editor, e.g. in a `@tool` class. Not with an export annotation. See `gd++ man classes`.

@editor_only
  Run its getter and setter only in the editor, never in the game. Only in a `@tool` class. See `gd++ man classes`.

Rules:

- At most one export annotation per variable, and any section annotations.
- Export and section annotations only work in classes that extend `Node` or `Resource`. See `gd++ man exports`.

# Set blocks of properties

@deferred
  Every call of the setter goes through `call_deferred`, and runs the `set` block later. See "Properties" in `gd++ man variables`.

@thread_safe
  Like `@deferred`, with `call_thread_safe`: calls from other threads run later, on the main thread. Only in classes that extend `Node`. See "Properties" in `gd++ man variables`.

They don't combine.

# Variables of externs

@profile(GROUPS...)
  Time the calls of their getter and setter through the extern.

@noprofile
  Leave them out of the extern's `@profile`.

# Signals

@trace(GROUPS...)
  Print each emission with `emit`, with its arguments. See "@trace and @profile" below.

@notrace
  Leave the signal out of its class's `@trace`: its emissions aren't printed. See "@trace and @profile" below.

Signals of externs can have `@trace` too, which prints each emission through the extern, marked "extern", and `@notrace`.

# Enums

@bitfield
  Make an enum type a bitfield, whose values without `=` are flags: 1, 2, 4, and so on. See `gd++ man enums`.

# Code blocks

@global
  Put a `decl` or `impl` block outside the class and outside namespace `godot`. See `gd++ man code`.

# @trace and @profile

For debugging. They generate code only in builds that turn them on, so they can stay in your code:

```gd++
@trace("combat")
var health: int = 100

@trace("combat", "ai")
@profile
func take_damage(amount: int) -> bool {
  health -= amount;
  return health <= 0;
}
```

```sh
gd++ build --trace combat              # traces health and take_damage
gd++ build --profile Player            # profiles take_damage
gd++ build                             # neither: the annotations generate nothing
```

Groups:

- The arguments are group names, in double quotes: `@trace("combat")` is in the group `combat`.
- Every annotation is also in the group named after its class, e.g. `Player`, without an argument.
- The groups `process` and `physics_process` turn on all `on process` and `on physics_process` blocks, and overrides of `_process` and `_physics_process`, even without annotations.
- `gd++ build --trace GROUP...` turns on the `@trace` annotations in those groups. `--profile GROUP...` the `@profile` ones. `all` turns on all of them.
- A member is on if its own annotation is on, or its class's, unless it has `@notrace` or `@noprofile`.

`@notrace` and `@noprofile`:

- On a function or a variable, and `@notrace` on a signal: leave it out of its class's `@trace` or `@profile`, including the groups `process` and `physics_process` for a function.
- A member's own `@trace` or `@profile` still applies.
- They need a `@trace` or `@profile` on the class or extern. Without one, they're an error. See "Leaving members out" in `gd++ man debugging`.

Other facts:

- They combine with every other annotation, and with each other.
- Externs can have them too. See "Externs" in `gd++ man debugging`.
- `gd++ man debugging` covers what they print, how to read it, and how to use them well.

# No annotations

- Enum values, integer constants, `ctor`, `dtor`, `import` and `noimport` take no annotations.
- Externs themselves only take `@pool`, `@scene`, `@trace` and `@profile`. See "Externs" above.
- Traits themselves only take `@group`. See "Traits" above.

# Errors

- An unknown annotation, with a suggestion if it looks like a typo: "Unknown annotation @exprot." with "Did you mean \"@export\"?".
- An annotation in the wrong place, e.g. "Annotation @tool can't be used on a func.".
- An annotation used twice on one declaration: "Annotation @export is used twice.". User annotations too: "Annotation @@save is used twice.".
- An undeclared user annotation: "Unknown annotation @@sav." with "Did you mean \"@@save\"?", or a hint to declare it.
- Arguments for an annotation that takes none: "Annotation @const takes no arguments.".
- `@trace` and `@profile` with anything but names in double quotes: "Annotation @trace takes names of groups in double quotes, e.g. @trace("combat").".
- An annotation that needs a base class: "Annotation @onready can only be used in classes that extend Node, which Item doesn't.".
- An annotation not followed by a declaration: "Expected a declaration after the annotation, ...".

# User annotations

`@@name` is your own annotation. GD++ ignores it, but macros see it, and generate code for it:

```gd++
class_name Player
extends Node

annotation save

@@save
@export var health: int = 100

@@save("hp_max") var max_health: int = 100

// A save function with each @@save variable, under its key.
invoke {
  local lines = { "Dictionary d;" }
  for _, m in ipairs(ctx.members) do
    local args = m.kind == "var" and gd.annotation(m, "@@save")
    if args then
      table.insert(lines, "d[" .. gd.quote(args[1] or m.name) .. "] = " .. m.name .. ";")
    end
  end
  table.insert(lines, "return d;")
  gd.func { name = "save", ret = "Dictionary", body = gd.join(lines, "\n") }
}
```

Facts:

- `@@` and a name, with arguments like a built-in annotation's: numbers, strings and names.
- `annotation NAME` declares one, for every file of the package. It goes wherever an inline class can go. See `gd++ man files`.
- Declaring a name more than once is fine, in one file or in several. So each macro's file can declare the annotations it reads.
- A declaration only has a name: no parameters, no doc comment and no annotations. GD++ doesn't check the arguments. The macro does, and reports problems with `gd.error`. See "Lua: errors" in `gd++ man macros`.
- They never clash with built-in annotations, or with other names of the package: `@@export` isn't `@export`.
- They go on any declaration that takes annotations, enum values included. Not on macros, templates and invocations.
- Each name only once per declaration.
- GD++ generates nothing for them: Godot and the C++ code never see them. Without a macro that reads it, a user annotation does nothing.
- Macros see them in `ctx.members` and `ctx.annotations`, with their `@@`, next to built-in ones with their `@`: `{ "@export", "@@save", { "@@key", "hp" } }`. `gd.annotation(m, "@@save")` returns their arguments. See "Lua: annotations" in `gd++ man macros`.
- Emitters take them the same way: `gd.var { ..., annotations = { "@@save" } }`. They must be declared too.

# Not in GD++

Some GDScript annotations have no GD++ version, since GD++ does the same another way, or it doesn't apply to C++:

- `@abstract` on functions, `@static_unload`, `@warning_ignore` and the like: not supported.
- `@export_node_path`, `@export_color_no_alpha`, `@export_exp_easing`, `@export_global_file`, `@export_global_dir` and the like: not supported yet. Use `@export`, or a property of the right type.
- `static`, `const` and `onready` without `@` are not keywords. Write `@static` and `@onready`, and `enum NAME = VALUE` for constants.
