Errors: GD++ and C++ compiler errors

When a GD++ file has a mistake, GD++ stops and explains it: where it is, what's wrong, and usually how to fix it. This page explains how to read these errors, lists the most common ones, and explains how errors of the C++ compiler relate to your GD++ files.

# Reading an error

```out
[×] res://player.gd++:1:21: Expected "{" to start the function body, but found ":".
     1 | func greet() -> void:
       |                     ^
    Hint: GD++ uses braces for function bodies, not a colon as in GDScript: "func foo() -> void { ... }".
```

- The first line has the file, the line and the column, then the message.
- Then the line of the file, with carets under the part that's wrong.
- Then, if GD++ has one, a hint about how to fix it.

GD++ reports one error at a time: the first one it finds. Fix it, and run again.

Errors come from three places, in this order:

1. Brackets and comments: GD++ first checks that every bracket is closed by its match, and that every block comment and raw string ends, in the whole file, C++ code included.
2. Syntax: the declarations must follow GD++'s grammar. See `gd++ man grammar`.
3. Meaning: names, types, annotations and the like must make sense, e.g. a type must exist, and an annotation must fit its declaration.

`gd++ build` checks every GD++ file of the package before compiling anything. `gd++ trans FILE` checks one file. `gd++ ls` marks files with errors.

# Coming from GDScript

GD++ looks like GDScript, so GDScript habits are the most common mistakes. GD++ recognizes them, and says what to write instead:

```
func greet() -> void:          Bodies use braces: func greet() -> void { ... }
func _process(delta):          Engine blocks: process(delta: float) { ... }, see gd++ man engine
var x := 5                     No type inference: var x: int = 5
const X = 5                    No const: enum X = 5
static func f()                Attributes are annotations: @static func f()
onready var x                  Annotations start with @: @onready var x
pass                           An empty body is {}
func f(x int)                  Types after a colon: func f(x: int)
func f() int                   Return types after an arrow: func f() -> int
var x int                      Types after a colon: var x: int
```

# C++ compiler errors

GD++ checks the GD++ parts of a file, but not the C++ code in it: that's the C++ compiler's job, during `gd++ build`. When it fails, the build shows the compiler's output. Thanks to `#line` directives, errors in your C++ code point to the GD++ file and line:

```
package/player.gd++:12:5: error: 'helth' was not declared in this scope
```

The path is relative to the build cache, where the compiler runs: `package/` holds the copies of the package's files that the build compiled, so the line shown is the compiled one, even if you edited the file since. See `gd++ man code`.

Some compiler errors are about the generated code, but caused by the GD++ declarations. The usual ones:

- "marked 'override', but does not override": an `@override` function's signature doesn't match the engine's. Check the return type, e.g. `-> void`, the parameter types, and `@const`. See `gd++ doc CLASS.FUNCTION`.
- "overriding final function": an `@override` function overrides an `@override("final")` one. See `gd++ man functions`.
- "invalid use of incomplete type": a class is used, but its header isn't included, since its name isn't written anywhere. Add `import CLASS`. See `gd++ man includes`.
- "ignoring return value ... declared with attribute 'nodiscard'": a signal's emit function was called without `emit`. Write `emit NAME(...)`.
- "Refcounted objects free themselves when their last reference goes away.": `destroy` or `queue_destroy` on a refcounted object, e.g. a `Ref<Mesh>`. Drop the reference instead, e.g. with `mesh.unref()`. See `gd++ man classes`.
- "queue_destroy only works on nodes.": `queue_destroy` on an object that isn't a node. Use `destroy`.
- "'claim' was not declared in this scope", or the same for `is_done` or `cancel`: the word is followed by something that doesn't start with a name, e.g. `claim (a ? x : y)`, so GD++ didn't rewrite it. Call the method instead: `(a ? x : y).claim()`. See `gd++ man rewrites`.
- "expected unqualified-id before 'gdpp'", or a similar error at a declaration: a variable or field is named `is_cancelled`, which GD++ reserves and rewrites to `gdpp::is_cancelled()`. Rename it. See `gd++ man rewrites`.
- Errors in a file `NAME.h` or `NAME.cpp` of the build cache point to generated code. Open the file, e.g. `res://.gd++pkg/gdpp/Player.cpp`, to see what GD++ generated, and which declaration it came from.
