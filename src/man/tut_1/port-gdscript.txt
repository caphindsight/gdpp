Tutorial: port a GDScript class to GD++

This tutorial turns a GDScript class into a GD++ class, step by step. It ends with a table of GDScript habits and what to write instead. It assumes a project with a package, as set up in `gd++ man tour`.

# The script

A coin that spins, and that the player collects:

```gdscript
class_name Coin
extends Area2D

signal collected(value: int)

@export var value: int = 1
@export_range(0.0, 10.0) var spin_speed: float = 2.0

@onready var sprite: Sprite2D = $Sprite

func _process(delta: float) -> void:
    sprite.rotation += spin_speed * delta

func _on_body_entered(body: Node2D) -> void:
    var player := body as Player
    if player == null:
        return
    player.score += value
    collected.emit(value)
    queue_free()
```

- `Player` is a GD++ class of the same package, with a `var score: int`.
- The coin's `body_entered` signal is connected to `_on_body_entered` in the scene, in the editor's Node dock.

# 1. Copy the declarations

Create `coin.gd++` next to `coin.gd`. The lines outside of function bodies stay almost the same:

```gd++
class_name Coin
extends Area2D

signal collected(value: int)

@export var value: int = 1
@export_range(0.0, 10.0) var spin_speed: float = 2.0

@onready var sprite: Sprite2D = $Sprite
```

Things to check in this part:

- Every variable needs a type: `var x := 5` becomes `var x: int = 5`. A variable without a type is a `Variant`.
- Integer constants become `enum NAME = 5`. See `gd++ man enums`.
- Keywords like `static` become annotations: `@static func`.
- Initial values are C++: `Vector2(1, 2)` works as it is, but `[1, 2]` or `{"a": 1}` don't. Use a block that builds the value. See `gd++ man variables`.

# 2. Rewrite the function bodies in C++

- Signatures stay the same, except for `_process` and the like, which become `on` blocks, e.g. `on process(delta: float) { ... }`.
- Bodies go in braces, and are C++:

```gd++
on process(delta: float) {
  sprite->set_rotation(sprite->get_rotation() + spin_speed * delta);
}

func _on_body_entered(body: Node2D) -> void {
  Gd<Player> player = body as Gd<Player>;
  if (!player) {
    return;
  }
  player->score += value;
  emit collected(value);
  queue_destroy this;
}
```

What changed:

- Objects are `Gd<T>`s, which work like pointers, so members are reached with `->`: `sprite->...`. That goes for every object, nodes and resources alike. See `gd++ man gd`.
- `queue_free()` becomes `queue_destroy this;`. It does the same, and keeps working if the class later gets `@pool`. With `@factory` on the class, scripts call `Coin.create()` and `coin.queue_destroy()` for the same. See `gd++ man classes`.
- Engine properties are getters and setters in C++: `sprite.rotation += x` becomes `sprite->set_rotation(sprite->get_rotation() + x)`. Your own GD++ variables are plain fields, so `player->score += value` works.
- `as` casts like in GDScript, but names a C++ type: `body as Gd<Player>`. A failed downcast gives null. See `gd++ man cast`.
- Signals are sent with `emit NAME(ARGS);`. See `gd++ man signals`.
- `func _process(delta)` becomes `on process(delta: float)`, `func _ready()` becomes `on ready`, and the like. `on` blocks add to the base's, and scripts can't replace them. See `gd++ man callbacks`.
- Other virtual functions of the engine, e.g. `_unhandled_input`, need `@override`. See `gd++ man functions`.

# 3. Look up the API

GDScript and C++ name most things the same, but not all:

- Global functions like `print` or `randi_range` live in `gd`: `gd::print(...)`.
- Singletons like `Input` are reached with `get_singleton()`: `Input::get_singleton()->is_action_pressed(string_name "jump")`.
- `string_name "jump"` is a `StringName` made once, the fast way to name actions, signals and methods. See `gd++ man rewrites`.

When you don't know what a class offers in C++, ask `gd++ doc`:

```sh
gd++ doc Node2D.set_rotation          # one method, with its exact signature
gd++ doc Input                        # the whole class
gd++ doc UtilityFunctions             # everything gd:: has
```

See `gd++ man doc`.

# 4. Check the file

```sh
gd++ trans coin.gd++
```

- It checks the GD++ parts of the file, and prints the C++ it generates.
- GD++ recognizes most GDScript habits, and says what to write instead:

```out
[×] res://coin.gd++:11:36: Expected "{" to start the function body, but found ":".
    11 | func _process(delta: float) -> void:
       |                                    ^
    Hint: GD++ uses braces for function bodies, not a colon as in GDScript: "func foo() -> void { ... }".
```

- The C++ in the bodies is only checked when it's compiled, in the next step. See `gd++ man errors`.

# 5. Swap the script for the class

Godot can't have two classes named `Coin`, so remove the old script first: delete `coin.gd`, or move it out of the project. Then build:

```sh
gd++ build
```

Compiler errors in your bodies point to the lines of `coin.gd++`. Once it builds:

1. Open the editor.
2. In each scene that used the script, select the coin node, remove its script, and change its type to `Coin` with "Change Type".
3. Check that the values in the inspector are still the ones you set.
4. Check that the Node dock still connects `body_entered` to `_on_body_entered`.

# 6. Connect signals in the scene

- Keep connecting signals in the scene, in the editor's Node dock, as with scripts.
- GD++ binds every `func`. So the editor lists the functions of `Coin`, and connects signals to them by name.
- Connections in the scene are visible in the editor, and the code needs none.
- Connect in code only where the scene can't, e.g. for nodes that the code creates.
- For an object in a variable of the class, write an `on` block. It stays connected to whatever the variable holds:

```gd++
var coin: Coin

on coin.collected {
  score++;
}
```

- Elsewhere, use `connect`, with `callable` for a function of the class:

```gd++
Gd<Coin> coin = create Coin;
coin->connect(string_name "collected", callable _on_coin_collected);
add_child(coin);
```

See "Connecting to signals" in `gd++ man signals`.

# 7. Port one class at a time

Ported classes and scripts work together:

- A script can extend `Coin`, connect to its signals and call its functions, since they're all bound.
- The C++ compiler doesn't know scripts. So GD++ code reaches them through an extern, which lists what the code needs of a script's class:

```gd++
extern Hud {
  extends Control
  func add_score(points: int) -> void
  var lives: int
}
```

An extern is a type, which calls the script's members by name:

```gd++
@export var hud: Hud

func _on_body_entered(body: Node2D) -> void {
  hud->add_score(value);
  if (hud->get_lives() == 0) { ... }
}
```

- Calls by name are slower than C++ calls. Keep them out of hot loops.
- Ported classes don't need externs. So start with classes that use no scripts, e.g. leaves of your scene tree, and work up, removing externs as their scripts get ported.

See `gd++ man externs`.

# GDScript habits and what to write

```
GDScript                            GD++
var x := 5                          var x: int = 5
const SPEED = 5                     enum SPEED = 5
static func f()                     @static func f()
func f(): pass                      func f() {}
print(a, b)                         gd::print(a, b)
node.position = p                   node->set_position(p)
$Hud/Score  (in a body)             get_node<Label>("Hud/Score")
body as Player                      body as Gd<Player>
sig.emit(a)                         emit sig(a);
sig.connect(f)                      connect in the scene, or if you can't:
                                    on x.sig { ... }, for a variable x of the class, or
                                    connect(string_name "sig", callable f)
func(x): return x + 1               callable [](int x) { return x + 1; }
Input.is_action_pressed("jump")     Input::get_singleton()->is_action_pressed(string_name "jump")
                                    or Action::jump, see gd++ man project-names
load("res://bullet.tscn")           ResourceLoader::get_singleton()->load("res://bullet.tscn")
scene.instantiate()                 scene->instantiate() as Gd<Bullet>
Bullet.new()                        create Bullet
bullet.queue_free()                 queue_destroy bullet
is_instance_valid(enemy)            Gd<Enemy> e = enemy, with enemy a Weak[Enemy]
preload(PATH).instantiate()         create Bullet, with @scene(PATH) on Bullet
                                    (and with @factory, scripts call Bullet.create())
assert(x > 0)                       assert x > 0;
body.has_method("hit")              body as Gd<Hittable>, with a trait Hittable
```
