Build caches: the .gd++build directory

Every package has a build cache: the directory `.gd++build` at its root. `gd++ build --id ID` builds in `.gd++build/ID` instead.

- Builds happen there.
- It keeps everything builds can reuse, so the next build only compiles what changed.
- You never need to look inside, but it helps when something goes wrong.

# What's inside

```
my_package/.gd++build/
  ID/                       the build cache of gd++ build --id ID, laid out like this one
  build.toml                the package settings of the last sync
  godot-cpp/                a copy of the package's bindings
  extension_api.json        a copy of the package's API spec
  SConstruct                the build script
  __register_types__.cpp    registers the package's classes with Godot, and with gd++ test, the @test classes
  tests.gd                  the script that gd++ test runs, which runs the tests
  godot_names.toml          what godot-cpp declares, for GD++
  package/                  copies of the package's GD++ and C/C++ files
  gdpp/                     the C++ that GD++ generates from the GD++ files
    gd++/syntax_N.hpp       the GD++ runtime header, for syntax N
    Player.h, Player.cpp    a header and a source per class
    test/PlayerTest.cpp     the source of a @test class, which release builds don't compile
    Suit.h                  a header per enum, extern and trait
    doc_classes/Player.xml  a class's documentation, in debug builds
  build/                    what SCons builds: godot-cpp and object files
    godot-cpp/              godot-cpp, compiled, with its generated bindings
    linux.template_debug.dev.x86_64/   object files, one directory per kind of build
```

- All of it is generated. Never edit it: builds overwrite it.
- It's ephemeral: deleting it is always safe, and only makes the next build slow.
- With `vcs = "git"`, GD++ adds it to `.gitignore`.

# Syncing

At the start of every build, and of `gd++ doc` and `gd++ trans` in a package, `gd++` syncs the build cache with the package:

1. It compares the package's id and settings (all of `.gd++pkg` but its classes and hidden directories) with `build.toml`. If they differ, or `build.toml` is missing, it:
   - cleans the package, like `gd++ clean --bin`,
   - copies the bindings and the spec into the cache,
   - writes the new `build.toml`.
2. It writes `SConstruct`, with the list of the package's C and C++ sources.
3. In builds, it copies the package's GD++ files and C/C++ sources and headers into `package/`, and deletes copies of files that are gone.

Facts:

- Changing a package's settings, e.g. its bindings or spec, or moving or renaming its directory, makes the next build start from scratch.
- Builds compile the copies, not your files. So compiler errors and debuggers name the copies, e.g. `package/src/player.gd++`, and show the compiled code, even if you edit a file during the build.
- Only files whose contents differ are copied, for both sources and dependencies.
- Thanks to the copies, builds don't depend on the dependency caches. Many packages can share a dependency, and deleting a dependency doesn't break a build cache.
- `build.toml` is written last, after a successful sync. So the next build redoes an interrupted sync.

# The names cache

To transpile GD++ code, GD++ must know every name that godot-cpp declares, e.g. `Node3D` or `TypedArray`: which header declares it, and whether a class is refcounted. See `gd++ man includes`.

- The first time, `gd++` generates godot-cpp's bindings from the spec. This is the "Compiling bindings" step: it only generates C++, and doesn't compile it.
- It scans all of godot-cpp's headers, and saves the names in `godot_names.toml`.
- Later builds read that file.
- It belongs to the bindings and spec of the last sync. It's deleted with the rest of the cache when they change.
- It has a version: when a new `gd++` scans differently, it scans again.

# The generated C++

Each build transpiles every GD++ file of the package into the `gdpp` directory:

- a header per class, extern, trait and enum,
- a source per class, in `gdpp/test` for `@test` classes,
- the runtime header.

Facts:

- Files whose contents didn't change are left alone, so the C++ compiler doesn't recompile them.
- Files that no GD++ file generates any more, e.g. after you rename a class, are deleted.
- In debug builds, `gdpp/doc_classes` holds each class's documentation, in Godot's XML format, including the classes that GD++ adds, e.g. the class of tasks. Release builds delete it. See `gd++ man docs`.
- The generated C++ is meant to be read. When the compiler reports an error in generated code, open the file it names, e.g. `my_package/.gd++build/gdpp/Player.cpp`.
- `gd++ trans` shows it without building. See `gd++ man generated`.

# Object files

- SCons keeps object files in `build/`, one directory per kind of build, e.g. `linux.template_debug.dev.x86_64` and `windows.template_release.x86_64`.
- So switching between debug and release, or between targets, doesn't recompile everything.
- Object files keep their source's extension, e.g. `package/src/util.cpp.os` on Linux. So `foo.c` and `foo.cpp` don't clash.
- godot-cpp is compiled into `build/godot-cpp`, once per kind of build.

# Parallel builds

Two builds must never share a build cache: SCons and the generated files would clash. `--id` gives a build a cache of its own:

```sh
gd++ build --id agent-1    # builds in .gd++build/agent-1
gd++ test --id agent-2     # builds in .gd++build/agent-2
```

- `.gd++build/ID` is a complete build cache, laid out like `.gd++build` itself: its own copies of the dependencies, its own generated C++ and object files. The first build with a new ID is slow.
- Builds with different IDs can run at the same time, e.g. one per terminal or AI agent, even in one package. A build without an ID runs in `.gd++build` itself, beside them.
- The libraries and the `.gdextension` file still land in the package root, whatever the ID. Parallel builds of one package overwrite each other's: the last one to finish wins.
- A build cleans only its own cache, e.g. when the package settings changed or with `--clean`: the files of `.gd++build`, or `.gd++build/ID`. The other IDs' caches stay.
- `gd++ clean` deletes `.gd++build` with every ID's cache in it.
- `gd++ doc` and `gd++ trans` always use `.gd++build`.
- IDs are made of letters, digits, `_` and `-`, and aren't names the cache uses: `build`, `gdpp`, `godot-cpp`, `package` or `SConstruct`.

# Cleaning

```sh
gd++ clean                 # the build caches of the packages in the current directory
gd++ clean --bin           # also their libraries and .gdextension files
gd++ clean res://...       # every package's build cache
gd++ build --clean         # clean with --bin, then build
```

Clean when:

- a build keeps failing in a way that makes no sense, e.g. after a crash during a build,
- `gd++` says "run `gd++ clean` to fix this".

`gd++ clean --bin` deletes every library and `.gdextension` file in the package root, whatever its name: `lib*.dll`, `lib*.so`, `lib*.dylib`, `*.gdextension` and `*.gdextension.uid`.

- So it also deletes the leftovers of a renamed package.
- Don't keep other files with these names in a package root.

See `gd++ man clean`.
