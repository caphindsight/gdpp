Packages: gd++pkg.toml and source files

A package is a directory in a project with a `gd++pkg.toml` file.

- It builds into one GDExtension library, with all the classes of its GD++ and C++ files.
- A project can have many packages.
- The project root itself can be one.

# Creating a package

```sh
gd++ init my_package --bind 10.0.0-stable --spec 4.7.2-stable
```

This creates the directory `my_package` if needed, and writes `my_package/gd++pkg.toml`. For a small game, put the package at the project root:

```sh
gd++ init . --bind 10.0.0-stable --spec 4.7.2-stable
```

See `gd++ man init` for all options.

# gd++pkg.toml

```toml
bind = "10.0.0-stable"
spec = "4.7.2-stable"
syntax = 1
std = "c++20"
prefix = "Foo"
quit_timeout = 2.5
hot_reload = false
macro_depth = 100

[[class]]
name = "Foo"
include = "pkg://foo.h"
icon = "pkg://foo.svg"
tool = true
```

bind (required)
  The Godot C++ bindings (godot-cpp) to build with, e.g. `"10.0.0-stable"`. They must be in one of the project's dependency caches. `gd++ fetch --missing` downloads them. See `gd++ man dependencies`.

spec (required)
  The Godot API spec to build against, e.g. `"4.7.2-stable"`.
  - It describes the classes of one Godot version, and decides which classes and methods your code can use.
  - The library needs at least that Godot version. The generated `.gdextension` file says so, and older Godot versions refuse to load it.
  - The bindings are generated from the spec. Their version doesn't need to match the spec's exactly, but they must support it.

syntax (optional, default 0)
  The GD++ language version of the package's GD++ files.
  - `gd++ init` writes the latest stable version for a new package.
  - Without the key, a package uses syntax 0, the nightly version.
  - See "Syntax versions" below.

std (optional, default `"c++20"`)
  The C++ standard, e.g. `"c++17"`, `"c++20"` or `"c++23"`.
  - It becomes `-std=...` for GCC and Clang, and `/std:...` for MSVC.
  - It must be at least C++17, which godot-cpp needs.

prefix (optional, default: the package's id in PascalCase)
  The prefix of the classes that GD++ adds to the package, e.g. `"Foo"`.
  - If the package's GD++ classes use `Async`, e.g. in an `@onthread` function, the package registers `FooAsync`, the class of its tasks. See `gd++ man async`.
  - Default examples: `my_game` gives `MyGame`. An id that starts with a digit gets `Pkg` in front: `3d_tools` gives `Pkg3dTools`.
  - Set it when the default clashes with a class name, or reads badly.

quit_timeout (optional, default 1)
  How many seconds the package's tasks may still run after the game starts quitting, before it exits anyway, e.g. `2.5`.
  - `0`: the game exits right away, even if tasks still run.
  - It can't be negative.
  - See "When the game quits" in `gd++ man async`.

hot_reload (optional, default `true`)
  Whether the editor reloads the package's library when a build changes it, without a restart.
  - `false`: the editor loads the library once. Restart the editor to see a new build.
  - Turn it off if hot reload crashes the editor. Due to a Godot bug, it does when the package has a tool class that runs code on the worker thread pool, e.g. an `@onthread` function.
  - See "Debug and release builds" in `gd++ man building`.

macro_depth (optional, default 64)
  How deeply the package's macro and template invocations may nest, e.g. `100`.
  - It must be positive.
  - Raise it only if an invocation really needs to nest that deep. A macro that invokes itself forever hits the limit, which then stops it.
  - `gd++ init --macro-depth 64` removes the key, since 64 is the default.
  - See "The sandbox" in `gd++ man macros`.

[[class]] (optional, any number)
  A plain C++ class that the package registers with Godot. Its keys:
  - `name`: the class name.
  - `include`: the header that declares it.
  - `icon` (optional).
  - `tool = true` if its code runs in the editor too. Without it, the class is a runtime class: its code runs only in the game.
  - `kind = "ptr"` or `kind = "ref"` if GD++ code can use it.
  - GD++ classes are not listed here: GD++ finds them in the GD++ files.
  - See `gd++ man cpp-classes`.

Facts:

- Missing required keys and unknown keys are errors, e.g. "Missing key spec in res://my_package/gd++pkg.toml.".
- Change the file with `gd++ init PATH --update`, or by hand.
- `gd++ fix` reformats it and sorts its classes by name.

# Syntax versions

Each package chooses its GD++ language version with the `syntax` key.

- `gd++ init` gives a new package the latest stable version.
- `gd++ --syntax` lists the versions that your `gd++` supports.
- Stable versions, 1 and up, never change:
  - Code that builds with one keeps building with every later `gd++`.
  - Language changes come in a new syntax version.
  - You choose when to upgrade a package, with `gd++ init PATH --update --syntax N`.
- Syntax 0 is the nightly version, the language as it's being developed:
  - It's not backward compatible: any new `gd++` may break code written for it.
  - Use it to try new features, never in production.
  - `gd++ init` warns when you choose it, and `gd++ ls` marks it.

The language pages describe one syntax version, shown in their titles: in a package, the package's, and elsewhere the latest stable one. `gd++ man --syntax N` or `gd++ man --nightly` shows another, e.g. `gd++ man --nightly signals`.

# The package's id

A package's id is the name of its directory, e.g. `my_package`.

- It names the library, e.g. `libmy_package.linux.debug.x86_64.so`.
- It names the `.gdextension` file, e.g. `my_package.gdextension`.
- For the package at the project root, it's the name of the project directory.
- Renaming or moving the directory changes the id. The next build notices, cleans the package and rebuilds it from scratch.

# Source files

Every file in the package with one of these extensions is part of it. You don't list them.

- GD++ files: `.gd++`, `.gdpp` and `.gg`. All three work the same.
- C and C++ sources: `.c`, `.cc`, `.cpp`, `.cxx` and `.c++`. They are compiled into the library.
- Headers, e.g. `.h` and `.hpp`: not compiled on their own, but sources and GD++ code can include them.

Files can be at any depth in the package directory, except in:

- hidden directories, whose names start with ".",
- nested packages (subdirectories with their own `gd++pkg.toml`), whose files belong to them,
- nested Godot projects (subdirectories with their own `project.godot`),
- `res://_gd++proj`.

Adding, removing or renaming a file needs no command: the next build picks it up.

# Include paths

C++ code in the package includes headers relative to:

- the package root, with quotes, e.g. `#include "src/util.h"` for `pkg://src/util.h`,
- the project root, with angle brackets, e.g. `#include <shared/math.h>` for `res://shared/math.h`,
- the directory of the generated C++, with either, e.g. `#include "Player.h"` for the header of the GD++ class `Player`.

Facts:

- Quotes also find headers next to the including file, and after the package root, the project root.
- With MSVC, angle brackets also find the package root, since MSVC can't tell the two apart.
- GD++ code rarely needs `#include`. See `gd++ man includes`.

# What a package builds into

`gd++ build` writes into the package root:

- One library per target, named `lib<id>.<platform>.<debug|release>.<arch>.<ext>`, e.g. `libmy_package.windows.release.x86_64.dll`.
- `<id>.gdextension`: where the libraries are, for every platform, and which icons the classes have.
- `<id>.gdextension.uid`: the resource UID of the `.gdextension` file, so Godot doesn't make one up.

Godot finds and loads `.gdextension` files anywhere in a project. So once a package is built, its classes show up in the editor. See `gd++ man building`.

# The package's classes

A package registers with Godot:

- every class declared in its GD++ files, see `gd++ man classes`,
- every C++ class listed in its `gd++pkg.toml`, see `gd++ man cpp-classes`.

Class names:

- Must be unique in the package. GD++ fails if two files declare the same name, or if a GD++ class has the name of a class in `gd++pkg.toml`.
- Should be unique in the whole project, and differ from Godot's classes, since Godot has one namespace for all classes.
- `gd++ ls` shows every package's classes, and marks names that are declared twice.

# Packages and each other

- Each package is compiled on its own. It knows only its own code and godot-cpp.
- So a package can't use another package's classes at compile time.
- To use classes of another package, or of any other GDExtension, at runtime, declare them as externs. See `gd++ man externs`.

# Nested packages

- A package can contain another package, e.g. the project root package and a package in a subdirectory.
- Files in the inner package belong to the inner package only.
- Each one builds into its own library.

# Removing a package

```sh
gd++ rm --pkg my_package
```

- Deletes the package's `gd++pkg.toml`, build cache, libraries and `.gdextension` files.
- Keeps its source files.
- `--dir` deletes the whole directory.

See `gd++ man rm`.
