C++ classes: plain C++ in a package

You don't have to write every class in GD++. A package can also have plain C++ classes, written the usual godot-cpp way, with `GDCLASS` and `_bind_methods`. GD++ compiles them into the package's library, and registers them with Godot if you list them. You write by hand what GD++ would write for you, e.g. to port existing godot-cpp code, or if you prefer it. GD++ classes can do anything C++ classes can, since their `decl` and `impl` blocks take any C++ (see `gd++ man code`).

# Writing a C++ class

Put the header and the source anywhere in the package, e.g. `pkg://src/spinner.h`:

```cpp
#pragma once

#include <godot_cpp/classes/node3d.hpp>

namespace godot {

class Spinner : public Node3D {
  GDCLASS(Spinner, Node3D)

public:
  double speed = 1.0;
  void _process(double delta) override;
  void set_speed(double p_speed) { speed = p_speed; }
  double get_speed() const { return speed; }

protected:
  static void _bind_methods();
};

}
```

and `pkg://src/spinner.cpp`:

```cpp
#include "src/spinner.h"

namespace godot {

void Spinner::_bind_methods() {
  ClassDB::bind_method(D_METHOD("set_speed", "speed"), &Spinner::set_speed);
  ClassDB::bind_method(D_METHOD("get_speed"), &Spinner::get_speed);
  ADD_PROPERTY(PropertyInfo(Variant::FLOAT, "speed"), "set_speed", "get_speed");
}

void Spinner::_process(double delta) {
  rotate_y(speed * delta);
}

}
```

Every `.c`, `.cc`, `.cpp`, `.cxx` and `.c++` file in the package is compiled, so there's no build file to edit. Includes in quotes are relative to the package root, and includes in angle brackets to the project root. See `gd++ man packages`.

# Registering it

Godot can only use a class once it's registered. List the class in `gd++pkg.toml` with `gd++ init`:

```sh
gd++ init . --class Spinner --include pkg://src/spinner.h --icon pkg://icons/spinner.svg
```

This adds to `gd++pkg.toml`:

```toml
[[class]]
name = "Spinner"
include = "pkg://src/spinner.h"
icon = "pkg://icons/spinner.svg"
```

name
  The class's name, as in C++. It must be a C++ identifier: letters, digits and underscores, not starting with a digit.

include
  The header that declares the class, as a `pkg://` or `res://` path. The generated registration code includes it: a `pkg://` path as `"src/spinner.h"`, relative to the package root, and a `res://` path as `<shared/spinner.h>`, relative to the project root. `gd++ init` asks for confirmation if the path doesn't end with `.h` or `.hpp`.

icon (optional)
  The class's icon in the editor, as a `pkg://` or `res://` path, usually to an SVG file. It goes into the `.gdextension` file.

tool (optional, default false)
  Whether the class's code runs in the editor too, like `@tool` on a GD++ class. See "Editor and runtime code" below. `gd++ init --tool` sets it, and `gd++ init --notool` removes it.

kind (optional)
  How GD++ code uses the class: `"ptr"`, as a pointer, or `"ref"`, as a `Ref`. Without it, GD++ code can't use the class by name. `gd++ ls` shows it as `[ptr]` or `[ref]`. See "Using a C++ class from GD++" below.

A new class needs `--include`, or `--noinclude` if a header that's already included declares it. See `gd++ man init` for how to change the include, the icon, the tool setting and the kind later, and `gd++ man rm` for how to remove the class. The file lists classes sorted by name.

# Editor and runtime code

Like GD++ classes and GDScript scripts, a C++ class runs its code in the editor only if you ask for it. By default, it's a runtime class: in the editor, Godot creates placeholders for its objects instead. A placeholder keeps the property values you set in the inspector, but runs none of the class's code: no constructor, no `_ready`, no `_process` and no setters. Games run from the editor and exported games run all code.

So `Spinner` above doesn't spin in the editor: the scene you edit stays still, and a bug in `_process` can't break the editor.

A tool class runs its code in the editor too, e.g. to draw gizmos, or to react when you change a property in the inspector. Make `Spinner` a tool class with `--tool`:

```sh
gd++ init . --class Spinner --update --tool
```

This adds `tool = true` to its `[[class]]` table:

```toml
[[class]]
name = "Spinner"
include = "pkg://src/spinner.h"
icon = "pkg://icons/spinner.svg"
tool = true
```

`--notool` makes it a runtime class again. Both take effect on the next build.

In a tool class, `Engine::get_singleton()->is_editor_hint()` tells whether the code runs in the editor, e.g. to spin only in the game:

```cpp
void Spinner::_process(double delta) {
  if (Engine::get_singleton()->is_editor_hint()) {
    return;
  }
  rotate_y(speed * delta);
}
```

Placeholders only stop the code that Godot calls. Code that already runs in the editor, e.g. that of a tool class, can still create an object of a runtime class with `memnew`, or call its static functions, and then the runtime class's code runs. To make sure that a class's code never runs in the editor, check `is_editor_hint()` in its functions, like GD++ classes with `@game_only` do. See `gd++ man classes`.

# How registration works

The build generates `__register_types__.cpp` in the build cache. It includes the headers of all the package's classes, C++ and GD++, and registers the classes when Godot loads the library, at the scene initialization level. A class is registered after its base class, if the base is a class of the same package, since Godot requires that. The generated code has `using namespace godot`, so C++ classes can be declared either in namespace `godot` or at global scope.

Runtime classes, i.e. C++ classes without `tool = true` and GD++ classes without `@tool`, are registered with `GDREGISTER_RUNTIME_CLASS`. The others are registered with `GDREGISTER_CLASS`. Don't register classes yourself: the generated code registers every class once.

If the package's GD++ classes use `Async`, e.g. in an `@onthread` function, the package also gets a class of tasks, named after the package's prefix, e.g. `FooAsync` for the prefix `Foo`. The GD++ runtime defines it, and `__register_types__.cpp` registers it first, with `GDREGISTER_CLASS`. No other class of the package, C++ or GD++, can have its name: the build fails then, and asks for another prefix. `SConstruct` defines `GDPP_ASYNC_CLASS` as its name, for all the package's C++. See `gd++ man async`.

The library's entry symbol is `gdpp_library_init`, which the `.gdextension` file names. Don't define your own entry point.

# Mixing C++ and GD++

C++ classes and GD++ classes live side by side in one package, and are registered together. Their names must differ, or the build fails with "Class Spinner is declared in ... and in ...gd++pkg.toml.". A GD++ class can't be added to `gd++pkg.toml`: it's declared in its GD++ file, and `gd++ init --class` refuses it.

GD++ code knows Godot's classes and the package's GD++ classes. It knows a C++ class only if it's marked `[ptr]` or `[ref]`, see "Using a C++ class from GD++" below. An unmarked C++ class:

- can't be a type in a GD++ class's API, e.g. the type of a `var` or a parameter. Use the C++ class's Godot base class instead, e.g. `Node3D`, and convert in code with `node as Spinner *`. See `gd++ man cast`.
- can be used in the code of a GD++ class if you include its header yourself, with a `@global` block:

```gd++
class_name Game
extends Node

@global decl {
  #include "src/spinner.h"
}

on ready {
  Spinner *spinner = memnew(Spinner);
  add_child(spinner);
}
```

- A C++ class can use a GD++ class: include its generated header, which is named after the class, e.g. `#include "Player.h"`. Mind that the generated classes are in namespace `godot`, and that the fields of simple GD++ variables are public, while their getters and setters are the functions that Godot calls. See `gd++ man generated`.

A C++ class can also extend a GD++ class of the same package, e.g. `class FastPlayer : public Player`. It's registered after its base. A GD++ class can only extend a C++ class that's marked `[ptr]` or `[ref]`.

# Using a C++ class from GD++

GD++ code uses Godot's classes in two ways: refcounted classes through references, e.g. `Ref<Resource>`, and the others through pointers, e.g. `Node3D *`. See "Objects and references" in `gd++ man classes`. GD++ can't tell which way a C++ class takes, so you say it with `gd++ init`:

```sh
gd++ init . --class Spinner --update --ptr
```

`--ptr` is for classes that aren't refcounted, like `Spinner`, which extends `Node3D`, and `--ref` for refcounted ones, e.g. those that extend `Resource`. Either needs the class to have an include. This adds `kind = "ptr"` or `kind = "ref"` to its `[[class]]` table:

```toml
[[class]]
name = "Spinner"
include = "pkg://src/spinner.h"
kind = "ptr"
```

Now GD++ code uses `Spinner` by name, like a Godot class: as the type of a `var` or a parameter, in casts, and as a base class. GD++ includes its header where needed:

```gd++
class_name Game
extends Node

@export var spinner: Spinner

on ready {
  spinner->set_speed(2.0);
}

class FastSpinner {
  extends Spinner

  on ready {
    set_speed(10.0);
  }
}
```

GD++ finds the class's base class in its header, if the header declares the class in namespace `godot`, as above. GD++ then knows that `FastSpinner` is a `Node`, so it can have an `on ready` block. If the class is declared elsewhere, e.g. at global scope, GD++ still knows the class, but not its base.

Mind that GD++ doesn't check the kind: if a refcounted class is marked `[ptr]`, or the other way around, the generated C++ is wrong, e.g. it doesn't compile, or it leaks objects. `gd++ init --nogdpp` removes the mark.

# In gd++ ls

`gd++ ls` lists a package's C++ classes with their headers, and the tags `[ptr]` or `[ref]` for classes that GD++ code can use, `@tool` for tool classes and `@icon` for classes with an icon. A missing header or icon is marked "(missing)", in red.

```
  Classes
    res://src/spinner.h  Spinner                           [ptr] @tool @icon
    res://src/wobbler.h  Wobbler
    pkg://player.gd++    Player   extends CharacterBody3D
```
