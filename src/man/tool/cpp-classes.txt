C++ classes: plain C++ in a package

A package can also have plain C++ classes, written the usual godot-cpp way, with `GDCLASS` and `_bind_methods`.

- GD++ compiles them into the package's library.
- GD++ registers them with Godot if you list them.
- You write by hand what GD++ would write for you. Use them to port existing godot-cpp code, or if you prefer it.
- GD++ classes can do anything C++ classes can: their `decl` and `impl` blocks take any C++. See `gd++ man code`.

# Writing a C++ class

Put the header and the source anywhere in the package, e.g. `pkg://src/spinner.h`:

```cpp
#pragma once

#include <godot_cpp/classes/node3d.hpp>

namespace godot {

class Spinner : public Node3D {
  GDCLASS(Spinner, Node3D)

public:
  double speed = 1.0;
  void _process(double delta) override;
  void set_speed(double p_speed) { speed = p_speed; }
  double get_speed() const { return speed; }

protected:
  static void _bind_methods();
};

}
```

and `pkg://src/spinner.cpp`:

```cpp
#include "src/spinner.h"

namespace godot {

void Spinner::_bind_methods() {
  ClassDB::bind_method(D_METHOD("set_speed", "speed"), &Spinner::set_speed);
  ClassDB::bind_method(D_METHOD("get_speed"), &Spinner::get_speed);
  ADD_PROPERTY(PropertyInfo(Variant::FLOAT, "speed"), "set_speed", "get_speed");
}

void Spinner::_process(double delta) {
  rotate_y(speed * delta);
}

}
```

- Every `.c`, `.cc`, `.cpp`, `.cxx` and `.c++` file in the package is compiled. There's no build file to edit.
- Includes in quotes are relative to the package root. Includes in angle brackets are relative to the project root.

See `gd++ man packages`.

# Registering it

Godot can only use a registered class. List the class in `.gd++pkg` with `gd++ init`:

```sh
gd++ init . --class Spinner --include pkg://src/spinner.h --icon pkg://icons/spinner.svg
```

This adds to `.gd++pkg`:

```toml
[[class]]
name = "Spinner"
include = "pkg://src/spinner.h"
icon = "pkg://icons/spinner.svg"
```

name
  The class's name, as in C++. It must be a C++ identifier: letters, digits and underscores, not starting with a digit.

include
  The header that declares the class, as a `pkg://` or `res://` path. The registration code includes it:
  - a `pkg://` path as `"src/spinner.h"`, relative to the package root,
  - a `res://` path as `<shared/spinner.h>`, relative to the project root.
  - `gd++ init` asks for confirmation if the path doesn't end with `.h` or `.hpp`.

icon (optional)
  The class's icon in the editor, as a `pkg://` or `res://` path, usually to an SVG file. It goes into the `.gdextension` file.

tool (optional, default false)
  Whether the class's code runs in the editor too, like `@tool` on a GD++ class. `gd++ init --tool` sets it, and `gd++ init --notool` removes it. See "Editor and runtime code" below.

abstract (optional, default false)
  Whether the class is only a base for other classes, like `@abstract` on a GD++ class: the editor doesn't offer it. `gd++ init --abstract` sets it, and `gd++ init --noabstract` removes it.

kind (optional)
  How GD++ code uses the class: `"ptr"`, as a pointer, or `"ref"`, as a `Ref`. Without it, GD++ code can't use the class by name. `gd++ ls` shows it as `[ptr]` or `[ref]`. See "Using a C++ class from GD++" below.

Facts:

- A new class needs `--include`, or `--noinclude` if an already included header declares it.
- `gd++ man init` shows how to change the include, the icon, the tool and abstract settings and the kind later.
- `gd++ man rm` shows how to remove the class.
- The file lists classes sorted by name.

# Editor and runtime code

By default, a C++ class is a runtime class, like GD++ classes and GDScript scripts:

- In the editor, Godot creates placeholders for its objects.
- A placeholder keeps the property values you set in the inspector, but runs none of the class's code: no constructor, no `_ready`, no `_process` and no setters.
- Games run from the editor and exported games run all code.
- So `Spinner` above doesn't spin in the editor, and a bug in `_process` can't break the editor.

A tool class runs its code in the editor too, e.g. to draw gizmos, or to react to property changes in the inspector. Make `Spinner` a tool class with `--tool`:

```sh
gd++ init . --class Spinner --update --tool
```

This adds `tool = true` to its `[[class]]` table:

```toml
[[class]]
name = "Spinner"
include = "pkg://src/spinner.h"
icon = "pkg://icons/spinner.svg"
tool = true
```

- `--notool` makes it a runtime class again.
- Both take effect on the next build.
- In a tool class, `Engine::get_singleton()->is_editor_hint()` tells whether the code runs in the editor:

```cpp
void Spinner::_process(double delta) {
  if (Engine::get_singleton()->is_editor_hint()) {
    return;
  }
  rotate_y(speed * delta);
}
```

Placeholders only stop the code that Godot calls.

- Code that already runs in the editor, e.g. a tool class's, can still create an object of a runtime class with `memnew`, or call its static functions. Then the runtime class's code runs.
- To make sure a class's code never runs in the editor, check `is_editor_hint()` in its functions, like GD++ classes with `@game_only` do. See `gd++ man classes`.

Godot doesn't let a runtime class extend a class of the package that isn't one: a tool class, an abstract class, or a GD++ class with `@tool` or `@abstract`.

- A C++ class that extends one needs `tool = true` or `abstract = true` too, or the build fails: "Class Helper extends Actor, which isn't a runtime class, so it needs tool or abstract too: ...".
- An abstract class's code runs in the editor too, so check `is_editor_hint()` in it if needed.
- GD++ classes that extend one are guarded instead. See "Guarded classes" in `gd++ man classes`.

# How registration works

The build generates `__register_types__.cpp` in the build cache.

- It includes the headers of all the package's classes, C++ and GD++.
- It registers them when Godot loads the library, at the scene initialization level.
- A class is registered after its base class, if the base is in the same package, as Godot requires.
- It has `using namespace godot`, so C++ classes can be declared in namespace `godot` or at global scope.
- Abstract classes, i.e. C++ classes with `abstract = true` and GD++ classes with `@abstract`, are registered with `GDREGISTER_VIRTUAL_CLASS`, like GDScript's abstract scripts. Those with a pure virtual function are registered with `GDREGISTER_ABSTRACT_CLASS`, which godot-cpp requires: then not even scripts that extend them can be created.
- Runtime classes, i.e. classes without tool or abstract that don't extend such a class of the package, are registered with `GDREGISTER_RUNTIME_CLASS`. The others with `GDREGISTER_CLASS`.
- Don't register classes yourself: the generated code registers every class once.
- The library's entry symbol is `gdpp_library_init`, which the `.gdextension` file names. Don't define your own entry point.

The class of tasks:

- If the package's GD++ classes use `Async`, e.g. in an `@onthread` function, the package gets a class of tasks.
- It's named after the package's prefix, e.g. `FooAsync` for the prefix `Foo`.
- Likewise, a package whose GD++ classes have shaders or use `GpuArray` gets `FooGpuArray`, the class of its GPU arrays, and `FooGpuTexture`, the internal class of the textures that its shaders return. See `gd++ man shaders`.
- The GD++ runtime defines it. `__register_types__.cpp` registers it first, with `GDREGISTER_CLASS`.
- No other class of the package, C++ or GD++, can have its name. Then the build fails and asks for another prefix.
- `SConstruct` defines `GDPP_ASYNC_CLASS` as its name, for all the package's C++.
- See `gd++ man async`.

# Mixing C++ and GD++

- C++ and GD++ classes live side by side in one package, and are registered together.
- Their names must differ, or the build fails with "Class Spinner is declared in ... and in .../.gd++pkg.".
- A GD++ class can't be added to `.gd++pkg`: it's declared in its GD++ file. `gd++ init --class` refuses it.
- GD++ code knows Godot's classes and the package's GD++ classes. It knows a C++ class only if it's marked `[ptr]` or `[ref]`. See "Using a C++ class from GD++" below.

An unmarked C++ class:

- Can't be a type in a GD++ class's API, e.g. the type of a `var` or a parameter. Use its Godot base class instead, e.g. `Node3D`, and convert in code with `node as Gd<Spinner>`. See `gd++ man cast`.
- Can be used in a GD++ class's code if you include its header yourself, with a `@global` block:

```gd++
class_name Game
extends Node

@global decl {
  #include "src/spinner.h"
}

on ready {
  Gd<Spinner> spinner = memnew(Spinner);
  add_child(spinner);
}
```

A C++ class can use a GD++ class:

- Include its generated header, named after the class, e.g. `#include "Player.h"`.
- Generated classes are in namespace `godot`.
- The fields of simple GD++ variables are public. Their getters and setters are the functions that Godot calls.
- See `gd++ man generated`.

Inheritance:

- A C++ class can extend a GD++ class of the same package, e.g. `class FastPlayer : public Player`. It's registered after its base.
- A GD++ class can only extend a C++ class marked `[ptr]` or `[ref]`.

# Using a C++ class from GD++

GD++ holds every class as a `Gd<T>`, in two ways:

- refcounted classes as a reference, which keeps the object alive, e.g. `Gd<Resource>`,
- the others as a plain pointer, e.g. `Gd<Node3D>`.

See `gd++ man gd`. GD++ can't tell which way a C++ class takes before reading its header, so you say it with `gd++ init`:

```sh
gd++ init . --class Spinner --update --ptr
```

- `--ptr`: for classes that aren't refcounted, like `Spinner`, which extends `Node3D`.
- `--ref`: for refcounted classes, e.g. those that extend `Resource`.
- Either needs the class to have an include.
- `gd++ init --nogdpp` removes the mark.

This adds `kind = "ptr"` or `kind = "ref"` to its `[[class]]` table:

```toml
[[class]]
name = "Spinner"
include = "pkg://src/spinner.h"
kind = "ptr"
```

Now GD++ code uses `Spinner` by name, like a Godot class: as the type of a `var` or a parameter, in casts, and as a base class. GD++ includes its header where needed:

```gd++
class_name Game
extends Node

@export var spinner: Spinner

on ready {
  spinner->set_speed(2.0);
}

class FastSpinner {
  extends Spinner

  on ready {
    set_speed(10.0);
  }
}
```

Facts:

- GD++ finds the class's base class in its header, if the header declares the class in namespace `godot`, as above. So GD++ knows that `FastSpinner` is a `Node`, and can have an `on ready` block.
- If the class is declared elsewhere, e.g. at global scope, GD++ knows the class, but not its base.
- GD++ doesn't check the kind. A refcounted class marked `[ptr]`, or the other way around, gives wrong C++: it doesn't compile, or it leaks objects.

# In gd++ ls

`gd++ ls` lists a package's C++ classes with their headers, and these tags:

- `[ptr]` or `[ref]`: GD++ code can use the class.
- `@tool`: a tool class.
- `@icon`: the class has an icon.
- "(missing)", in red: a missing header or icon.

```
  Classes
    res://src/spinner.h  Spinner                           [ptr] @tool @icon
    res://src/wobbler.h  Wobbler
    pkg://player.gd++    Player   extends CharacterBody3D
```
