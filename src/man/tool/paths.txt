Paths: res://, pkg:// and finding packages

Commands take paths as arguments, e.g. `gd++ build src/player` or `gd++ init . --class Foo --include pkg://foo.h`. This page covers how `gd++` reads paths, and how it shows them.

# Kinds of paths

- Relative, e.g. `src/player` or `../assets`: relative to the current directory.
- Absolute, e.g. `/home/me/game` or `C:\games\game`: used as they are.
- Home, `~` and `~/games/game`: relative to your home directory. On Windows, `~\games\game` works too.
- `res://`, e.g. `res://src/player`: relative to the root of the project that contains the current directory, like in Godot. `res://` alone is the project root.
- `pkg://`, e.g. `pkg://icons/player.svg`: relative to the root of the package that contains the current directory. `pkg://` alone is the package root.

Forward slashes work on every platform. On Windows, backslashes work too.

Examples, run from `res://src/player`, in a project whose package root is `res://src`:

```sh
gd++ build .                  # the package containing res://src/player, i.e. res://src
gd++ build res://tools        # the package containing res://tools
gd++ clean pkg://             # the package res://src
gd++ vendor --spec my-4.7 --from ~/specs/my-4.7
```

# Paths in config files

`gd++pkg.toml` and the `@icon` annotation store paths too. They must be `res://` or `pkg://` paths, so they don't depend on where you run `gd++`:

- `res://`: the root of the project that contains the package.
- `pkg://`: the root of the package itself.

E.g. `include = "pkg://src/foo.h"` or `@icon("res://icons/player.svg")`. See `gd++ man cpp-classes` and `gd++ man classes`.

# Finding the project

A project is a directory with a `project.godot` file.

- `gd++` checks the current directory, then its parent, and so on, up to the root of the file system.
- The first directory with a `project.godot` file is the project root.
- If projects are nested, the innermost one wins.
- If there is none, the command fails:

```out
[×] Path games is not contained in a Godot project.
```

# Finding the package

A package is a directory with a `gd++pkg.toml` file. It must be inside a project.

- Commands that work on one package, e.g. `build`, `clean` and `doc`, take an optional path.
- They use the package that contains it: the path itself if it's a package root, or else its nearest parent that is one.
- Without a path, they use the current directory. So `gd++ build` builds the package you're in.
- If packages are nested, the innermost one wins.

These need the path of a package root itself, not of a directory inside it:

- `gd++ init PATH --class ...`
- `gd++ rm PATH --class ...`
- `gd++ rm --pkg PATH`

Otherwise, they fail with "There is no GD++ package at ...".

# Paths in messages

- Paths inside the project are `res://` paths, e.g. `res://src/player.gd++`.
- Other paths are relative to the current directory, e.g. `../other_game`.
- `gd++` never prints absolute paths, so logs don't reveal your file system layout, and are safe to share.
- Packages are shown by their path. The package at the project root is `res://` followed by the project directory's name in brackets, e.g. "res:// [my_game]".

# Skipped directories

When `gd++` walks a project, to find packages or source files, it skips:

- Hidden files and directories, whose names start with ".", e.g. `.godot`, `.git` and `.gd++proj`.
- The checked in dependency cache, `res://_gd++proj`.
- Nested Godot projects: directories with their own `project.godot` file, and everything in them.
- When it collects one package's files: nested packages, since their files belong to them.
