Tutorial: make a small networked game

This tutorial builds the network code of a small game with Godot's high-level multiplayer:

- a server that players join,
- players that move on every screen,
- shots that the server checks.

GD++ declares remote functions with `@rpc`, and calls them with `rpc`. Godot's own nodes, like `MultiplayerSpawner`, work as usual. It assumes a project that builds, as in `gd++ man tour`.

# 1. Host and join

A `Lobby` node starts the server, or joins one. A `MultiplayerSpawner` creates the players, on the server and on every client:

```gd++
class_name Lobby
extends Node

enum PORT = 7777

@export var player_scene: PackedScene
@export var spawner: MultiplayerSpawner

on ready {
  assert spawner != nullptr;
  spawner->set_spawn_function(callable_mp(this, &This::create_player));
}

func host() -> void {
  Ref<ENetMultiplayerPeer> peer;
  peer.instantiate();
  peer->create_server(PORT);
  get_multiplayer()->set_multiplayer_peer(peer);
  get_multiplayer()->connect(string_name "peer_connected", callable_mp(this, &This::add_player));
  add_player(1);
}

func join(address: String) -> void {
  Ref<ENetMultiplayerPeer> peer;
  peer.instantiate();
  peer->create_client(address, PORT);
  get_multiplayer()->set_multiplayer_peer(peer);
}

func add_player(id: int) -> void {
  assert spawner != nullptr;
  spawner->spawn(id);
}
```

In the editor:

1. Add the `MultiplayerSpawner` to the scene.
2. Set its spawn path, e.g. to a `Players` node.
3. Pick it for the `spawner` property.

Facts:

- If you forget, `spawner` is `nullptr`. In debug builds, the assertions print an error instead of crashing the game. See "Assertions" in `gd++ man rewrites`.
- Only the server calls `spawn`, with the new player's peer id.
- The spawner then calls the spawn function on every peer, with that id, and adds the node it returns.
- The server's id is always 1.

# 2. Give each player to its peer

Each peer moves its own player, so it must be the multiplayer authority of its player node. The spawn function sets it, on every peer:

```gd++
func create_player(id: int) -> Node {
  Node *player = player_scene->instantiate();
  player->set_multiplayer_authority(id);
  return player;
}
```

# 3. Send the position

The authority moves the player, and sends its position to the other peers:

```gd++
class_name Player
extends CharacterBody3D

@rpc("unreliable_ordered")
func sync_position(pos: Vector3) -> void {
  set_position(pos);
}

on physics_process(delta: float) {
  if (!is_multiplayer_authority()) {
    return;
  }
  Vector2 input = Input::get_singleton()->get_vector(string_name "left", string_name "right", string_name "up", string_name "down");
  set_velocity(Vector3(input.x, 0, input.y) * 5.0);
  move_and_slide();
  rpc sync_position(get_position());
}
```

- `@rpc` marks a function that other peers may call. Without a mode, it's `"authority"`: only the node's authority may call it. So no other peer can move this player.
- `"unreliable_ordered"` fits data sent every frame. A lost packet doesn't matter, since the next one comes soon. But an old one must not overwrite a newer one.
- `rpc sync_position(...)` calls the function on every other peer. A plain call, `sync_position(...)`, would only run it here.

See `gd++ man rpc` for all arguments of `@rpc`.

# 4. Let the server decide

Positions are cheap to trust, but hits aren't: a client could claim anything. So clients only ask the server, and the server decides:

```gd++
var health: int = 100

@rpc("any_peer", "call_local", "reliable")
func request_shot(aim: Vector3) -> void {
  if (get_multiplayer()->get_remote_sender_id() != get_multiplayer_authority()) {
    return;
  }
  Player *target = find_target(aim);
  if (target) {
    rpc target->set_health(target->health - 10);
  }
}

@rpc("any_peer", "call_local", "reliable")
func set_health(value: int) -> void {
  if (get_multiplayer()->get_remote_sender_id() != 1) {
    return;
  }
  health = value;
}

func shoot(aim: Vector3) -> void {
  rpc(1) request_shot(aim);
}
```

`find_target` is a helper that finds the player in the line of fire, e.g. with a raycast.

- `rpc(1) request_shot(aim)` calls the function on the server only.
  - `"any_peer"` lets clients call it, since the server isn't the player's authority.
  - In exchange, the function checks who called it, with `get_remote_sender_id()`. Only the player's own peer may shoot with it.
- `rpc target->set_health(...)` calls the function on every peer, for the target player. It also accepts any peer, so it checks that the server sent it.
- `"reliable"` fits events that must arrive: a lost shot would be a bug.
- `"call_local"` also runs the function on the calling peer. So the host's own player works like everyone else's.
- `rpc` needs the object in a variable, like `target` here, not a call. Write `Player *p = get_player(); rpc p->...`, not `rpc get_player()->...`.

# 5. Test with two instances

Build once:

```sh
gd++ build
```

1. In the editor, open Debug > Customize Run Instances, and run two instances.
2. Host in one.
3. Join `127.0.0.1` in the other.

Both load the same library.

To see the network traffic:

- Trace the remote functions, e.g. `@trace("net")` on `request_shot` and `set_health`.
- Build with `gd++ build --trace net`.
- Each call prints with its arguments, in both instances' output.

See `gd++ man debugging`.

# 6. Across packages

A class of another package, or a script, calls your RPCs through an extern, with a plain `@rpc`:

```gd++
extern Player {
  extends CharacterBody3D
  @rpc func request_shot(aim: Vector3) -> void
}
```

The class that defines the function configures it. So the extern's `@rpc` takes no arguments. See "@rpc" in `gd++ man externs`.
